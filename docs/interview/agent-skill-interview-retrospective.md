# Agent 与 Skill 项目追问备忘

本文从他人复盘中提炼通用问题，供 Agent／Skill 岗位练习。原始项目的参数、样本和指标不能在本仓库复核，因此以下只讲设计方法；不是 Moose 已实现能力的清单，也不沿用他人的提效数字。

先分清三个对象：**Agent** 根据任务决定下一步，**工具**执行一次明确操作，**Skill**保存可复用的说明与步骤。Moose 主要接入代理 CLI，不自己实现下面的完整 Agent 循环或 Skill 评测平台；项目实际边界见[职责说明](project-interview-reference.md#2-哪些是自己做的哪些来自底座)。

## 1. Agent 如何创建子 Agent，谁决定什么时候创建？

例如主 Agent 要同时查两个互不依赖的模块，可以向运行时提交“创建子任务”的工具请求。模型负责提出拆分方案，运行时负责检查权限、并发上限和预算，再创建执行单元。把创建能力做成工具，不代表模型可无限创建进程。

一次创建请求通常需要目标、可访问的上下文和预期输出。它们是设计维度，不是 Claude Code、Codex 的统一参数名；实际接口要查对应实现。

执行链可以这样讲：

1. 主 Agent 判断子问题能独立完成，提出目标及必要上下文。
2. 运行时校验额度、权限与并发，分配子任务 ID，并记录父子关系。
3. 子任务返回带 ID 的结果或错误，主 Agent 汇总并判断整体是否完成。
4. 取消、超时和失败要有传播规则；一个子任务完成不能把父任务直接标为完成。

独立读取适合并行；两个任务都要修改同一文件时，仍需目录隔离或写入协调。子 Agent 数量增加也会增加 token 和汇总成本，不能只看单个任务耗时。

Moose 中是否委派由底座决定，客户端展示活动并提供已接入的控制；Moose 自己调度的是会话队列和后台任务。

## 2. Skill 超过一百个时，怎样控制上下文并选对？

先测描述集合有多大，再决定是否需要检索。数量多不一定超出上下文，描述冗长或边界重叠反而可能先影响选择准确性。

可以先给模型名称、简短描述和使用条件，选定后才加载完整步骤；继续增长时，再按任务筛出候选集合。主 Agent 和子 Agent 不必持有全部 Skill，但裁剪候选时要避免把真正需要的项排除。

例如“读 PDF”和“修改 Word”两个 Skill，应说明输入类型、输出目标及不适用场景。评测集同时包含 PDF、Word、混合任务和两者都不适用的任务，不能只测正向命中。

需要区分三个指标：候选集合有没有包含正确 Skill、最终有没有选对、选对后任务有没有完成。前两个通过仍可能因为步骤过时而执行失败。新增 Skill 后重跑旧案例，才能发现它是否抢走了原本正确的选择。

## 3. Skill 与 Prompt、RAG 有什么关系？

Skill 的说明本身也会成为提示词的一部分。它把使用条件、操作步骤和验证方法组织成可复用内容，并可关联脚本或资源；“用了 Skill”不意味着摆脱了提示词设计。

RAG 是按问题检索并提供资料的方式。举例说，报销流程 Skill 告诉 Agent“先核对票据，再填写，再请用户确认”；检索系统提供最新报销制度。两者可以配合，不能把“流程”和“事实”当成绝对互斥的内容类型。

选择方案时看内容是否经常变化、是否需要检索大量资料、是否有固定验收步骤。不要仅凭名称判断 Skill 一定比长 Prompt 或 RAG 更好。

## 4. 如何从运行记录中优化 Skill？

Trace 是一次任务的执行轨迹：模型请求、工具调用、等待、错误及最终结果。先用它区分耗时发生在哪里，再修改相应步骤。工具服务慢，与模型反复选择错误 Skill，需要不同修复。

一个可复核的过程是：从已获准采集的轨迹中选出失败样本 → 说明具体问题 → 修改 Skill → 在固定案例上回放 → 比较成功率、耗时和 token → 审核后发布。轨迹中的用户输入与凭据需要控制访问和脱敏。

例如原流程重复读取同一文件三次，缓存一次工具结果后可能更快；但若文件会变，缓存也可能降低正确性。比较时固定模型、任务集及工具环境，报告样本量和中位数／P95，同时检查结果质量。没有这些条件，就不报“提升了 30%”。Moose 没有内置这套线上 Skill 优化平台。

## 5. 长任务怎样跨中断继续？

开始前明确目标、可用权限、依赖和验收标准。遇到缺少登录或数据的步骤，应明确记录阻塞原因；是否询问用户取决于是否确实缺少信息，不必对已授权的操作反复确认。

运行中保存已完成事项、产物位置、验证结果和下一步依赖。简单任务用清单即可；复杂任务再记录依赖关系。文件记录是可恢复的说明，不是正在运行的进程，也不能单凭“上次写到提交阶段”就自动再提交一次。

恢复时先核对外部状态，再选择继续点。副作用可能已成功、回执却丢失，因此“重读进度”与“重放操作”必须分开。Moose 的类似例子是[队列与结果未知](project-interview-reference.md#7-排队并行和重启恢复)。

## 6. AI 生成代码怎样验收？

按风险选择检查范围：类型和格式帮助发现基础问题，单元测试验证规则，端到端测试连接界面与后台，真实环境验证原生依赖和外部协议。自动化通过后，仍需看它是否测到了需求，而不是只重复实现。

遇到状态问题时，先重建事件顺序。例如“完成通知先到，启动回复后到”可能让已结束任务被改回运行中；应按执行 ID 限制状态转移，并用受控顺序测试，而不是每隔几秒把异常状态重置一次。

回答质量问题时，选一处自己读过、修改并验证的代码说明。可先练[React 搜索组件审查](react-search-results-code-review.md)：指出竞态、失败路径和数据边界，再给出复现方法，比笼统说“AI 写得很好／很差”更有依据。

## 回答时怎样组织

先讲一个具体问题，再说明机制，接着讲失败时怎么办，最后给验证依据。例如：“多个客户端会重复提醒，所以后台按事件 ID 分配一次；领取后客户端崩溃仍可能漏提醒，因此只承诺去重，不承诺系统必达；用共享后台测试竞争领取与前台抑制。”

工具名称和架构术语只用于帮助解释这条因果链。无法说明原理和证据的模块，先补读代码，再决定是否作为自己的重点经历。
