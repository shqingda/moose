# Agent 与 Skill 项目追问备忘

> 本文整理自他人的面试复盘，供 Agent 或 Skill 相关岗位按需复习，不代表 Moose 的实际实现。工具名称、参数和数字要用自己的项目核实后再讲。

## 一、面试流程与表现

面试从自我介绍开始。由于长时间没有练习，表达中出现重复和停顿，但最终完整讲完。后续准备时应将自我介绍压缩为 60～90 秒，按“个人定位—核心经历—代表项目—与岗位的匹配点”固定结构反复练习。

## 二、项目追问

### 1. Agent 如何动态创建子 Agent？

参考 Claude Code、Codex 的做法，将子 Agent 封装成一个可由模型调用的工具。调用时主要传入：

- `goal`：子 Agent 要完成的任务。
- `fork_context`：是否继承主 Agent 的上下文。
- `pass_through`：是否将子 Agent 的结果直接返回给用户。

核心思路是把“创建子 Agent”纳入普通工具调用流程，而不是在业务代码中写死调度路径。

### 2. 什么时候创建子 Agent？

把创建子 Agent 当作一个工具调用：主 Agent 决定是否调用、创建几个以及如何拆分任务。

系统提示词只提供典型场景，例如：

- 多个相互独立的子问题可以并行探索。
- 同一个问题存在多条值得分别验证的技术路线。
- 某项任务需要隔离上下文，避免干扰主 Agent。

这种方式保留了模型的调度能力，但仍需要通过提示词、权限和并发限制约束成本与风险。

### 3. Skill 数量超过 100 个，如何控制上下文开销？

原项目当时没有做复杂优化，因为 Skill 的简短描述仍能放进可用上下文。复盘中的 token 数字只属于那个项目；换一套 Skill 或模型，需要重新测量。

Skill 的完整内容也不会始终放在所有 Agent 的上下文中：主 Agent 选定 Skill 后，只给执行任务的子 Agent 绑定相关 Skill，使其看到较小的候选集合。

如果 Skill 数量继续增长，可以考虑：

1. 先筛出少量相关 Skill，再让执行任务的 Agent 选择。
2. 合并用途高度重叠的 Skill。
3. 先读简短描述，选中后再读完整步骤。

### 4. 如何保证 Skill 选择准确？

主要从编写规范和上线评测两方面保证：

- Skill 描述尽量边界清晰、彼此正交，减少多个 Skill 同时命中。
- 新增 Skill 时检查它与现有 Skill 的语义冲突。
- 上线前运行选择评测，确认新增 Skill 不会降低现有用例的召回和选择准确率。
- 对容易混淆的 Skill 增加反例和边界用例，而不只是测试正向命中。

选择准确性不能只靠描述设计，还需要持续维护一组覆盖冲突场景的回归集。

### 5. 为什么使用 Skill，而不是只用 Prompt 或 RAG？

Skill 的价值主要有四点：

- **按需加载**：先展示简短描述，用到时再读完整说明。
- **选择边界清楚**：说明何时该用、何时不该用，减少选错。
- **步骤可复用**：保存验证过的操作与检查方法。
- **能力组合**：模型可以组合多个 Skill，完成单个 Skill 无法覆盖的复杂任务。

它并不是天然优于 RAG。Skill 更适合描述“应该怎样做”，RAG 更适合补充“有哪些事实和资料”，两者可以配合使用。

### 6. 如何利用线上数据优化 Skill？

使用 Langfuse 观察包含 Skill 的执行链路，重点关注：

- Trace 总时长。
- 模型反复思考、调用工具的轮数。
- Token 消耗，以及是否存在单步异常增长。
- 工具调用错误率。

优化流程是：抽取一批失败或低效 Trace，让 Agent 分析并修改 Skill，再通过历史用例回放验证，最后由人工审核变更。

原复盘提到整体 Skill 耗时优化约 30%。这是原项目的经验数据，面试中应说明统计口径、样本范围和对照基线，否则不要直接复用该数字。

## 三、AI 辅助开发中的长任务

### 1. 长程任务开始前：先暴露阻塞点

长程 Agent 任务能否顺利执行，关键不只是目标描述，还要提前识别执行路径上的阻塞点，例如：

- 缺少登录态、Cookie 或系统权限。
- 无法访问线上环境或内部服务。
- 测试数据和依赖服务没有准备好。
- 验收标准不明确，Agent 无法判断何时完成。

启动前先让 Agent 反过来追问需求、约束、环境和验收细节。把缺少的权限、数据或判断标准补齐，再开始长任务。

### 2. 运行中：建立基于文件的进度层

对于跨越较长时间和多个步骤的任务，可以用文件记录：

- 已完成的工作和证据。
- 当前进行到哪一步。
- 未完成事项与阻塞原因。
- 后续任务的依赖关系。

简单任务用清单即可；复杂任务再记录哪些步骤依赖前一步、哪些能并行。重点是中断后能看懂进度并继续，不必为了形式引入复杂编排。

### 3. 交付前：沉淀可重复执行的 E2E 测试

测试的重点是可复用、可稳定运行、能够明确判断成败。浏览器任务优先考虑 Playwright 等脚本化方案；只有脚本难以覆盖的交互，再使用 Computer Use。

一个可参考的时间分配是：把较多时间放在环境和验收体系上，再进行开发和集中测试。具体比例取决于任务复杂度，不必机械照搬原复盘中的“2 天环境、1 天开发、2 天测试”。

## 四、如何看待 AI 生成代码的质量

回答时不宜简单说“不关心代码质量”。更准确的表达是：

> 我不会逐行追求人工风格上的完美，但会关注代码是否正确解决用户问题，以及系统是否仍然具备可维护、可扩展和可验证的结构。

需要重点守住三条底线：

1. **功能与验收**：需求是否真正达标，关键路径是否有自动化测试。
2. **系统设计**：核心架构和状态机是否合理，不能依赖大量兜底逻辑掩盖设计缺陷。
3. **长期演进**：新增功能是否持续放大耦合、分支和隐式状态，最终让产品需求被技术债拖累。

典型反例是：状态机出现问题后，只增加兜底逻辑和定时修复任务。局部补丁可能缓解现象，但如果异常不断出现，更应该重新检查状态定义、事件来源、状态转移条件以及一致性边界。

因此，AI Coding 的质量策略可以概括为：**产品结果优先，架构边界兜底，自动化测试验收。**

## 五、值得借鉴的回答框架

面对项目追问，可以按下面四层回答：

1. **先讲结论**：用了什么机制，解决了什么问题。
2. **再讲实现**：关键对象、参数、调用链或状态流转。
3. **补充边界**：哪些由模型决定，哪些由系统约束；当前规模下为何可行。
4. **最后讲验证**：使用什么指标、评测或测试证明方案有效。

不要只报工具名或概念。面试官继续追问时，应能说明真实的调用过程、失败场景、取舍依据和数据口径。
