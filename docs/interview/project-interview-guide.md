# Moose 项目面试指南

按“**做了什么 → 为什么这样做 → 失败时怎么办 → 怎样验证**”准备项目。先讲清下面这条主线；遇到具体追问，再查[实现细节和源码入口](project-interview-reference.md)。这里的回答口径以你实际参与的工作为准，功能范围以[能力表](../providers/native-capabilities.md)和当前源码为准。

## 一分钟介绍

> Moose 是我开发的 AI 编程工作台，有桌面和本机 Web 入口。用户选项目、开会话，把开发任务交给 Codex、Grok Build、Pi 或 OpenCode 等本机代理，并在同一处查看回复、工具活动、审批和代码改动。
>
> 我负责客户端交互、CLI 协议适配、任务调度、持久化和 Git 工作流。模型推理、代理内部的工具调用与子代理委派由接入的 CLI 负责。技术栈是 Electron、React、TypeScript 和 SQLite。
>
> 项目最难的是把不同 CLI 的事件接成一致的使用流程，同时保证长任务、同目录并发和异常恢复不会让用户误以为任务已经完成或没有执行。

开场讲用途、职责和一个难点即可。对方追问时，从下面三件事里挑自己最熟的展开：**任务链路、流式状态、并发与恢复**。项目价值是让多项目、多会话的状态、审批和 Git 改动更容易追踪；没有实测的提效比例就不报数字。

## 哪些是 Moose 做的

| Moose | 接入的 CLI / 外部工具 |
| --- | --- |
| 输入与队列、会话和消息记录、目录调度 | 模型推理、决定和执行代理工具 |
| 展示审批并将答案送回原请求 | 发起审批或提问，并继续原生会话 |
| Git 改动预览、版本核对、worktree 生命周期 | Git 实际修改索引、创建提交与工作目录 |
| 展示子代理关系及受支持的控制 | 是否委派、怎样运行子代理 |

Moose 自己启动的后台 Shell 命令由 Moose 管理，不属于代理内部的工具调用。本地存储也不等于离线推理：CLI 仍可能把请求发给服务商。不同底座能显示在同一界面，不代表它们都有 Plan、插话或原生历史等相同能力。[完整能力表](../providers/native-capabilities.md)列明了差异。

## 一条任务怎样走

以“修复登录按钮并补测试”为例：

1. 页面提交文字和本次附件等信息。后台校验会话和参数，先把输入写进 SQLite 队列。`send` 返回表示 **Moose 已接收**，不是代理已完成。
2. 调度器检查这个会话的**实际工作目录**是否空闲。同一目录里的 Moose 任务串行；不同目录可以并行。若准备 CLI 时用户取消，开始前还会重新核对队列和占用状态。
3. 真正开始时，数据库用事务完成出队、写入用户消息和运行状态。Moose 分配 `runId`，适配器创建或恢复 CLI 的原生会话。
4. CLI 持续返回文字、工具活动、审批或提问。适配器翻译成统一事件；后台保存，页面更新。审批回答要送回**这一轮的原请求**，不能当成下一条聊天消息。
5. 收到真正的完成、失败或取消信号后，后台保存最终状态、让旧审批失效、释放目录，再调度下一条。

这条链路最容易讲错的是三个时刻：**入队、CLI 接收、执行结束**。请求的成功响应不能替代任务完成事件。源码从 [service.ts](../../electron/service.ts) 的 `send`、`drain`、`execute` 看起，再看 [store.ts](../../electron/db/store.ts) 和 [适配器接口](../../electron/providers/types.ts)。[详细调用链](project-interview-reference.md#4-从按下发送到任务结束)保留了各步骤与代码入口。

## 四个值得深入讲的问题

### 1. 不同代理怎样共用一套页面？

Codex、Grok、Pi、OpenCode 的启动方式、原生会话、增量格式和完成信号各不相同。每个适配器负责读懂自己的协议，向公共服务报告回答、工具、审批和结束等事件。公共服务只处理排队、记录和通知。这样新增一种 CLI 时，不必把各家判断写进一个大执行函数。

统一的是**页面认识的事件**；协议里的特殊语义仍留在适配器。例如有的完成通知并不代表整轮已经稳定结束，恢复会话时还可能回放旧历史。没有原生插话能力，就保留普通排队，不用取消重启冒充插话。被问具体底座时，查[协议与能力细节](project-interview-reference.md#5-不同代理如何接进同一套界面)。

### 2. 流式消息怎样保持一致？

一轮执行会产生多条消息：回答、工具、审批要分别更新。`runId` 关联本轮，事件 key 找到同一条记录，`seq` 防止旧版本覆盖新版本。文字增量用追加，最终完整文本用覆盖，否则最终答案可能重复显示。

输出很碎时，后台先合并，约每 80 毫秒批量保存和推送；审批等关键状态及时刷新。代价是突发崩溃时，最后还在内存中的少量增量可能丢失。切换会话后，前端用请求代次和会话 ID 丢掉迟到的旧查询。长历史按游标分页，再减少无变化消息的重渲染；**分页不是严格虚拟列表**，不能声称万条消息同时渲染仍不卡。[流式与 React 细节](project-interview-reference.md#6-流式消息和-react-页面如何保持一致)。

### 3. 为什么按目录排队，重启后能恢复什么？

两个会话即使名字不同，也可能同时改 `App.tsx`。Moose 按规范化后的实际工作目录互斥；同一项目若要并行改代码，可建不同的 Git worktree。这个约束只管 Moose 自己的任务，外部编辑器和终端仍能修改文件，因此提交前要重新检查仓库状态。

队列先入库，执行开始时的事务保护数据库记录；它不能把 CLI 请求和文件修改一起变成原子操作。后台重启后，可以恢复历史、队列和原生会话 ID，但已死亡的进程不会复活。旧普通队列先暂停，由用户决定是否继续。若写请求可能已成功、只是回执丢失，就标为**结果未知**，不自动再做一次。[并发和恢复细节](project-interview-reference.md#7-排队并行和重启恢复)。

### 4. 用户确认的还是刚才那份内容吗？

审批、Plan 批准和 Git 提交都有“用户预览后内容发生变化”的风险。点击时由后台再核对会话、执行、请求 ID 或版本：旧审批不能批准新任务，旧计划版本不能执行，Git 预览过期则要重新确认。只把按钮置灰不足以防迟到请求。明确拒绝与结果未知也要分开显示；超时不能证明外部操作没有发生。[具体案例](project-interview-reference.md#16-面试里值得展开的四个问题)。

## 架构、安全与技术取舍

React 渲染进程负责交互，Electron 主进程负责窗口和系统能力，独立本机后台负责 CLI、SQLite、调度和 Git。桌面页面通过 preload / IPC 调用业务；Web 页面通过 HTTP 请求和 SSE 收事件，两者复用业务服务。安装版普通关窗只断开客户端；后台还活着时任务继续，重新打开再读快照与消息。[进程与 Web 入口](project-interview-reference.md#3-为什么分成三类进程)。

TypeScript 约束开发时的方法与参数，Zod 等运行时校验处理页面传来的真实数据。页面不直接获得 Node、文件系统或进程权限；主进程检查请求来源，后台再核对业务状态。同步 SQLite 操作在后台进程，不阻塞窗口主进程，但仍可能阻塞后台自身，所以历史要分页并测慢操作。[安全边界](project-interview-reference.md#14-输入体验和安全边界)。

**为什么 Electron？** 复杂时间线、Markdown、diff 和表单可以复用 React，也方便连接本机 CLI；代价是包体和进程资源开销。首屏代码和发行包曾做按需加载与内容裁剪，但小样本测量没有证明启动速度显著变快。[测量口径与数字](project-interview-reference.md#electron-启动慢包体积大内存高你怎么优化)。

**为什么 SQLite？** 这是本机单实例后台，需要持久化历史、队列，并在开始执行时一起更新几项状态。若以后数据规模让同步查询影响后台响应，再根据慢查询和实际延迟调整；不把 WAL 当成无限并发写入的保证。

**为什么不盲目重试？** 请求 ID 要配合持久化记录和内容核对才有用。即使如此，SQLite、CLI、Git 和远端没有一个共同事务；“外部成功、本地没收到回复”仍可能发生。对这种写操作先让用户核对，而不是声称严格只执行一次。

## 怎样证明自己做过

准备一个短演示：发任务 → 看流式文字和工具活动 → 处理一次审批 → 看 diff。再准备一个失败场景，例如同目录排队、断连重连或旧审批，说明页面、数据库和外部文件各会是什么状态。真实模型调用前确认登录与额度；也可以用临时仓库和受控测试 CLI 演示，不把模拟结果冒充真实模型输出。

验证分层讲：协议夹具检查消息顺序和错误路径；业务测试检查状态规则；桌面 / Web 流程检查用户操作；真实 CLI 验证特定版本和账号；打包验收检查开发环境之外的路径、签名与依赖。每层只证明对应边界，测试数量和性能数字引用[测试指南](../testing.md)与对应[发布记录](../releases/)。

AI 辅助开发可以直接说明。更有说服力的是挑一处你亲自审查、改过并验证的代码，讲清“发现什么问题、为什么改、怎么证明修好了”。自己还不理解的模块不要写成重点经历。[简历示例和演示细节](project-interview-reference.md#18-简历写法演示和最后复习)可按实际工作筛选使用。

面试前至少打开 [service.ts](../../electron/service.ts)、[store.ts](../../electron/db/store.ts)、[providers/types.ts](../../electron/providers/types.ts) 和 [workspace.ts](../../src/lib/workspace.ts)。能顺着一条真实任务讲清这四处如何配合，比背完整功能清单更有效。
