# Moose 项目面试指南

本文是项目面试的主线材料，以 **Moose 0.23.1** 的实现为准（核对日期：2026-10-09）。准备每个话题时，都按“**做了什么 → 为什么这样做 → 失败时怎么办 → 怎样验证**”四步组织。先把本文讲顺；被问到具体细节时，再查[追问资料](reference/README.md)。

回答以你实际参与的工作为准；某项功能是否支持，以[能力表](../providers/native-capabilities.md)和当前源码为准。

## 一分钟介绍

> Moose 是我开发的 AI 编程工作台，有桌面应用和本机 Web 两个入口。用户选择项目、新建会话，把开发任务交给 Codex、Grok Build、Pi 或 OpenCode 这些本机代理 CLI，然后在同一个界面里查看回复、工具活动、审批和代码改动。
>
> 我负责客户端交互、CLI 协议适配、任务调度、持久化和 Git 工作流。模型推理、工具调用和子代理委派由接入的 CLI 负责。技术栈是 Electron、React、TypeScript 和 SQLite。
>
> 最难的部分是把不同 CLI 的事件接成一致的使用流程，同时在长任务、同一目录并发和异常恢复时，不让用户误以为任务已经完成，或者误以为任务没有执行。

开场讲清用途、职责和一个难点就够了。对方追问时，从**任务链路、流式状态、并发与恢复**里挑自己最熟的展开。项目价值是让多项目、多会话的状态、审批和 Git 改动更容易追踪；没有实测过提效比例，就不要报数字。

## 哪些是 Moose 做的

| Moose 负责 | 接入的 CLI 或外部工具负责 |
| --- | --- |
| 输入与队列、会话和消息记录、按目录调度 | 模型推理，决定调用哪些工具并执行 |
| 展示审批，把用户的选择送回原请求 | 发起审批或提问，然后继续原生会话 |
| Git 改动预览、提交前核对、worktree 生命周期 | Git 实际修改索引、创建提交和工作目录 |
| 展示子代理关系和受支持的控制 | 是否委派、怎样运行子代理 |

三个容易说错的边界：

- Moose 只管理自己启动的后台 Shell 命令；代理在工具调用里启动的进程由底座管理。
- 数据存在本机，不等于离线推理，CLI 仍会把请求发给模型服务商。
- 不同底座显示在同一个界面里，不代表它们都支持 Plan、插话或原生历史等能力。具体差异见[能力表](../providers/native-capabilities.md)。

## 一条任务怎样走完

以“修复登录按钮并补测试”为例：

1. **入队**：页面提交文字、附件等信息。后台校验会话和参数后，先把输入写进 SQLite 队列。`send` 请求返回只表示 **Moose 已收到**，不表示代理做完了。
2. **调度**：调度器检查这个会话的**实际工作目录**是否空闲。同一目录里的代理任务串行，不同目录可以并行。准备 CLI 是异步的，期间用户可能取消，所以准备完成后还会重新核对队列和目录占用。
3. **开始执行**：数据库在一个事务里完成出队、写入用户消息和更新运行状态。Moose 分配 `runId`，适配器创建或恢复 CLI 的原生会话。
4. **执行中**：CLI 持续返回文字、工具活动、审批或提问。适配器把它们翻译成统一事件，后台保存，页面更新。审批的回答要送回**这一轮的原请求**，不能当成下一条聊天消息。
5. **收尾**：收到真正的完成、失败或取消信号后，后台保存最终状态、让旧审批失效、释放目录，再调度下一条。

这条链路最容易讲混的是三个时刻：**入队、CLI 开始处理、执行结束**。请求的成功返回不能代替任务完成事件。

读源码时，从 [service.ts](../../electron/service.ts) 的 `send` 请求处理开始，再看 [session-execution.ts](../../electron/session-execution.ts) 的 `drain` 和 `execute`，然后是 [store.ts](../../electron/db/store.ts) 和[适配器接口](../../electron/providers/types.ts)。各步骤对应的代码入口见[详细调用链](reference/01-project-overview.md#4-从按下发送到任务结束)。

## 四个值得深入讲的问题

每点先用两三句讲清边界，机制和失败路径到链接里展开。

### 1. 不同代理怎样共用一套页面？

每个 CLI 一个适配器，只把「回答、工具、审批、结束」报给公共服务；排队和落库不按厂商分叉。统一的是页面认识的事件，不是各家协议。Pi 要等 `agent_settled` 才算结束，没有原生插话的底座只走普通队列，不用取消后重跑冒充插话。见[协议与能力](reference/02-agents-and-streaming.md#5-不同代理如何接进同一套界面)。

### 2. 流式消息怎样保持一致？

同一轮用 `runId` 归在一起，同一条记录用事件 key 和 `seq` 合并，大约每 80 毫秒批量落盘，审批立刻刷新。切换会话后用请求代次丢掉迟到结果。这不是虚拟列表，不能说一万条同时渲染也不卡。见[流式与 React](reference/02-agents-and-streaming.md#6-流式消息和-react-页面如何保持一致)。

### 3. 为什么按目录排队？重启后能恢复什么？

代理任务按实际工作目录互斥，并行改同一项目要用不同的 Git worktree。队列先写入数据库；重启能读回历史和原生会话 ID，已经退出的进程不会复活。回执丢了标成结果未知，不自动再执行。见[并发和恢复](reference/03-execution.md#7-排队并行和重启恢复)。

### 4. 用户确认的还是刚才那份内容吗？

审批、计划和提交都在点击时再核对版本：旧按钮不能批准新操作，置灰挡不住迟到的请求。明确拒绝和结果未知分开，超时不能证明外部操作没发生。案例见[四个可展开的问题](reference/06-interview-expression.md#16-面试里值得展开的四个问题)。

## 从用户体验切入时，怎样讲出工程细节

前端岗位从一个用户动作讲起：找回旧回答、多个窗口只提醒一次、点开的文件是不是这一份、断线后写操作成功了没有。搜索、通知、预览和错误分类的实现与验证都在[第 19 节](reference/07-search-notice-preview.md#19-搜索通知和文件预览怎样串起用户体验)，这里不重复那张表。

## 架构、安全与技术取舍

| 被问到 | 先说这一句 | 接着补上的限制 |
| --- | --- | --- |
| 为什么分成三个进程 | React 管交互，主进程管窗口和系统能力，本机后台管 CLI、SQLite、调度和 Git。桌面走 preload／IPC，Web 走 HTTP 和 SSE，业务服务是同一套 | 安装版关窗只是断开客户端。细节见[进程与 Web 入口](reference/01-project-overview.md#3-为什么分成三类进程) |
| 安全边界在哪 | TypeScript 约束开发时的类型，Zod 校验页面真实传来的数据。页面没有 Node、文件系统或进程权限 | 主进程检查请求来自哪个窗口，后台再核对业务状态。同步 SQLite 在后台，不卡窗口，但可能卡住后台自己，所以历史要分页。见[安全边界](reference/05-security-and-verification.md#14-输入体验和安全边界) |
| 为什么用 Electron | 时间线、Markdown、diff 和表单可以复用 React，也方便接本机 CLI | 代价是包体和运行开销。首屏代码小过，小样本没有证明启动明显变快。见[性能追问](reference/06-interview-expression.md#electron-启动慢包体积大内存高你怎么优化) |
| 为什么用 SQLite | 本机单实例后台，要存住历史和队列，并在开始执行时一次改好几项状态 | 同步查询若拖慢后台，再按慢查询调整。WAL 不代表写入可以无限并发 |
| 为什么不自动重试 | 写操作先让用户核对，不声称保证只执行一次 | SQLite、CLI、Git 和远端没有共同事务。请求成功了、本地没收到回复，这种情况仍然可能发生 |

## 怎样证明是自己做的

**准备一个短演示**：发任务 → 看流式文字和工具活动 → 处理一次审批 → 看 diff。再准备一个失败场景，比如同目录排队、断线重连或旧审批，说明此时页面、数据库和磁盘上的文件分别是什么状态。调用真实模型前先确认登录和额度；也可以用临时仓库和受控的测试 CLI 演示，但不要把模拟结果说成真实模型的输出。

**分层讲验证**：协议夹具检查消息顺序和错误路径；业务测试检查状态规则；桌面和 Web 的端到端测试检查用户操作；真实 CLI 验证特定版本和账号；安装包验收检查开发环境之外的路径、签名和依赖。每一层只证明它覆盖的那部分。测试数量和性能数字引用[测试指南](../testing.md)和对应版本的[发布记录](../releases/)。

**AI 辅助开发可以直接说**。更有说服力的是挑一处你亲自审查、修改并验证过的代码，讲清“发现了什么问题、为什么这样改、怎么证明修好了”。自己还没读懂的模块，不要写成重点经历。[简历示例和演示安排](reference/06-interview-expression.md#18-简历写法演示和最后复习)可按实际情况筛选。

面试前至少打开 [service.ts](../../electron/service.ts)、[session-execution.ts](../../electron/session-execution.ts)、[store.ts](../../electron/db/store.ts)、[providers/types.ts](../../electron/providers/types.ts) 和 [workspace.ts](../../src/lib/workspace.ts)。能顺着一条真实任务讲清这几处怎样配合，比背完整功能清单更有用。
