# 七、看见慢、拆开包 · 下

> 承接 [上篇](07-toolchain-1.md)。对应答案第 6、8、9 题。
> 读完要能讲清：页面慢和模型慢为什么要分开记；一条日志怎样把一次任务串起来；Vite 的拆包、Tree Shaking、预加载、长期缓存各解决什么，以及包变小为什么还不等于启动变快。

## 1. 先把「慢」拆成阶段

用户说慢，可能是页面主要内容迟迟不出现，可能是点了没反应，也可能是模型半天不出第一个字。合成一个总耗时，就不知道该改渲染、改交互，还是改模型侧。

页面体验用三个指标：

| 指标 | 衡量 |
| --- | --- |
| LCP | 主要内容何时显示出来 |
| INP | 一次交互之后多久能画出响应 |
| CLS | 布局会不会突然挪动 |

**补充知识：** 这三项常被称作 Core Web Vitals。INP 在 2024 年 3 月取代了只看「第一次输入延迟」的 FID。场景题监控章会讲怎样采集；这里先知道它们回答的问题。

模型侧单独记两个时间，再把中间的等待拆开：

```
发送时刻
  → 第一个有效输出     首字时间
  → 生成完成           总耗时
```

总耗时里面可能含着工具执行和等人审批。不拆开的话，用户在看审批卡的时间会被算成「模型很慢」。

```ts
const sentAt = performance.now();
onFirstChunk(() => record('firstChunkMs', performance.now() - sentAt));
onDone(() => record('totalMs', performance.now() - sentAt));
```

按设备、模型、版本分组，看分位数和失败率。平均值会被少数极慢请求拉高，也会把一批失败藏住。失败率要和耗时一起看：很快但经常失败，不是好的体验。

`performance.now()` 是单调时钟，适合量一段间隔。不同进程里它的起点不同，不能把主进程的数字和渲染进程的数字直接相减。这条在监控章还会再出现。

## 2. 结构化日志：用 ID 把一次执行串成时间线

用户说「卡住了」，一条错误字符串通常不够。你要的是：这次请求从入队、开始、工具、审批到失败，中间每步的时间和错误码。

结构化日志就是每条都用固定字段，而不是一句自由文本。固定字段才能按 `runId` 搜索、按错误码统计。

```ts
log({
  event: 'run.failed',
  runId,
  requestId,
  durationMs,
  errorCode,
  version,
});
```

`requestId` 标识一次请求，`runId` 标识一次执行。一次执行里可能有多次工具调用，它们共享 `runId`，各自再有调用 ID（上一章的 `callId`）。

普通日志只留排查需要的摘要。调试日志按需打开，并限制体积。用户输入、密钥、完整回答不要上传。本地为了产品功能把对话存下来，和把原文送到遥测平台，是两件不同的事。

能按 `runId` 还原任务时间线，还不等于记录了用户的每一次点击。点击遥测要另做，而且同样要采样和脱敏。

## 3. 构建：先看首屏装了什么，再决定拆哪一块

开发慢和用户打开慢，不是同一个测量。Vite 在开发时按需编译你改的源码，并预构建依赖，所以启动快。生产才真正打包。开发环境快，不能证明线上首屏小。

生产构建传统上交给 Rollup。Vite 正在转向用 Rust 写的 Rolldown。一个具体项目用的是哪一个，看它锁定的 Vite 版本和配置，不要凭记忆说「Vite 就是 Rollup」。

优化顺序：

```
用打包分析看每个 chunk 里是什么，记下首屏实际下载的 JS
  → 非首屏的面板、编辑器、终端、图表用动态 import 拆出去
  → 保证没人用的代码能被 Tree Shaking 删掉
  → 只预加载马上要用的
  → 产物文件名带内容哈希，便于长期缓存
  → 再用同一条件下打出来的应用，测量真实启动，而不是只看字节数
```

### 代码分割

动态 `import()` 让那一块变成单独的 chunk，用户打开时才下载。确实需要手动分组时再写分包规则。一开始就把每个依赖拆开，会多出很多小请求，首屏不一定更快。

```tsx
const loadReview = () => import('./review-panel');
const ReviewPanel = lazy(loadReview);
<button onMouseEnter={loadReview}>审查</button>
```

悬停时提前下载，点击时更快。所有东西都预加载，等于没有拆包，带宽又被抢回去了。

Vite 会为入口和它的直接依赖自动生成 `modulepreload`。手动预加载只加在「下一步几乎一定用」的地方。

### Tree Shaking

构建时删掉没有被用到的代码。前提是模块能被静态分析：使用 ES Module 的 `import` / `export`，避免整包导入。有副作用的模块（import 时就会改全局、注册什么）要在 `package.json` 的 `sideEffects` 里标明，否则打包器可能把「看起来没人调用、其实 import 就有作用」的文件删掉，或者反过来不敢删。

### 长期缓存

生产文件名带内容哈希。内容不变，哈希不变，浏览器可以缓存很久。HTML 入口自己不要长期缓存，否则用户会一直拿到指向旧哈希的旧 HTML。

三份缓存不要说成一件事：

| 缓存 | 在哪 |
| --- | --- |
| 依赖预构建缓存 | 开发时 Vite 缓存处理好的依赖 |
| 浏览器资源缓存 | 用户机器上，靠文件名哈希 |
| 构建工具缓存 | 加快下一次生产构建 |

### 和 Webpack 的对应关系

新项目默认用 Vite。Webpack 主要还在维护旧项目。会读配置即可，概念是通的。

| 概念 | Vite | Webpack |
| --- | --- | --- |
| 按需拆包 | 动态 `import()` | 动态 `import()`，`splitChunks` 管分组 |
| 预加载 | 自动 `modulepreload` | `/* webpackPrefetch: true */` 这类注释 |
| 文件名哈希 | 默认带哈希 | `[contenthash]` |
| 构建缓存 | 依赖预构建缓存 | `cache: { type: 'filesystem' }` |

包体变小，不能自动证明启动更快。工作区代码如果仍要在登录之后才加载，入口 JS 的减少不一定体现在「可交互时间」上。要用相同条件测量打包后的应用。

## 容易混在一起

**首字时间和 LCP。** 一个是模型输出，一个是页面主要内容。发送按钮出现得很快，模型仍可能很慢。

**任务时间线和点击遥测。** 前者能追一次 Agent 跑到哪。后者才知道用户点了什么。

**开发服务器快，和生产包小。** Vite 开发不把整个应用打成一个包。

**入口字节数，和就绪时间。** 拆出去的代码稍后仍要下载。要测量用户真正等到能用的时刻。

## Moose 这一章实际落在哪

测量数字见 [答案](../07-engineering-toolchain.md) 第 6、8、9 题，以及 [0.23.0 验收](../../../releases/0.23.0-validation.md)。和通用监控方案的差别：

- 没有线上 Core Web Vitals 面板，也没有覆盖每次点击的遥测。一次任务的消息、工具、审批和错误按 `runId` 留在 SQLite。
- 构建是 Vite 加 Rolldown。0.23.2 起服务入口共用 `dist-electron/chunks/`，桌面包不再打两份后台；preload 等其余入口仍是单文件。界面靠 `lazy` 和动态 `import`，不是手动分包表。
- 0.23.0 静态入口 JS 大约少了 69%。工作区仍在认证后加载，同一次记录里就绪时间没有明显变快。入口变小不等于启动变快。

## 本章速记

把整章工程串起来：检查拦住坏代码，测量说明慢在哪，日志能把一次失败对上号，打包决定用户先下载什么。

页面看 LCP、INP、CLS；模型看首字和总耗时，并把工具与审批从总耗时里摘出来，用分位数和失败率而不是单次最快值。日志用 `requestId` 和 `runId` 串起入队到失败，普通日志只留摘要。构建先看分析图，再用动态 `import` 拆非首屏，Tree Shaking 依赖可静态分析的模块，预加载只给马上要用的，长期缓存靠内容哈希，HTML 入口除外。开发快不等于首屏小，入口变小也不等于就绪变快。Moose 没有线上体验面板和点击遥测；任务记录在 SQLite。构建用 Vite 和 Rolldown，服务入口从 0.23.2 起共用一份后台代码，界面靠 `lazy` 把入口从约 730 KB 降到约 224 KB，就绪时间变化不大。
