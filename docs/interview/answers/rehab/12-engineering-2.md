# 十二、发布与业务词汇 · 下

> 承接 [上篇](12-engineering-1.md)。对应原题 44、45、66、68。

## 国际化：句子的语序也会变

把「发送」译成 Send，只是文案。日期怎么写、复数怎么变、一句完整的话里词的顺序、按钮会不会被长翻译撑破，都会随语言变化。

用稳定的 key 管理文案，例如 `composer.send`，不要把中文句子本身当 key。缺失时回退到另一种已有语言，避免页面上直接露出 key。

日期、数字、复数交给 `Intl`。`Intl.DateTimeFormat` 按语言和时区格式化日期。`Intl.NumberFormat` 管数字和货币。`Intl.PluralRules` 判断这种语言里该用单数、复数还是别的类别。

不要把句子拆成单词再拼接。英语是 “3 files”，中文是「3 个文件」，还有的语言复数类别更多。拼接会把语序写死。

默认跟随系统语言，同时允许用户覆盖。还要检查：长文案会不会撑破布局，时区是否正确，读屏软件读到的无障碍文本是否也翻译了。

**Moose：** 有中英文两套词典。语言设置是 system、en、zh-CN。部分日期格式仍然是固定的。不能说所有内容都已完整本地化。

## 灰度：同一个人每次都落在同一组

新版本直接给所有人，出问题影响面就是全部。灰度要控制两件事：有多少人用上了，出问题时能不能马上停。

用稳定的规则分组，例如对用户 ID 做哈希再取模。同一个用户每次访问都落在同一组。如果每次刷新都随机，这个人会在新旧版本之间来回跳。一旦出问题，你也无法复现「他一直在用新版本」。

先选定少量稳定用户用新版本，看错误率、性能和关键业务指标。正常再扩大比例。功能开关可以不发版就关掉新能力。回滚代码之前，确认新版本写入的数据旧版本还能读。

功能开关管的是能力的开闭。它和「安装包已经发出去」不是同一个开关。包已经在用户机器上时，没有开关就只能等下一次发布，或让用户回退安装。

数据兼容要单独想。新版本若写了旧版本不认识的字段，或迁移了格式，只把程序退回去，用户会打不开自己的数据。

**Moose：** 桌面版和独立 Web 安装版共用同一个发布版本。Web 的 `moose update` 由用户主动执行。它不是灰度平台，也不会自动安装升级。讨论稳定分组和自动回滚时，说明那是设计方案，不是 Moose 已有的发布系统。

## 函数式：纯计算放在中间，副作用放在边上

纯函数是：同样的输入，总是同样的输出，并且不修改函数外面的东西。不发请求，不写数据库，不改传入的对象。

把「消息列表怎样合并」写成纯函数，测试只要准备输入、看输出。把「存进数据库」留在系统边界。边界上的代码才需要数据库或网络。

```ts
function newer(old: Message, incoming: Message): Message {
  return incoming.seq > old.seq ? incoming : old;
}
```

这个函数只比较 `seq`。它没有说明消息从哪来，也没有把结果存下去。

函数式风格不要求把每个循环都改成 `reduce`。为了「不可变」把整棵大对象深拷贝一遍，也没有必要。没变的那一条继续用原对象，既没有去改旧对象，又让性能章的 `memo` 认得出来它没变。流式合并和引用稳定，在这里接上。

**Moose：** `mergeMessages` 就是这样的纯函数。按 `seq` 保留较新的记录。没有变化时直接返回原数组。位置发生变化时，才按 `position` 重新排序。存库、订阅和调用代理这些副作用留在 Service 层。

## 领域模型：用业务的词描述规则

业务变复杂以后，如果代码里的名字和业务说法对不上，沟通时要不断翻译。领域模型用业务概念和业务规则描述系统。它不只是列出有哪些对象，还要表达身份、归属、约束和允许的操作。身份是怎样才算「同一条」。归属是谁包含谁。约束是什么组合不允许。允许的操作是在什么状态下可以审批、可以发送。

聊天产品里，项目、会话、消息不是三张随便起名的表。一个会话包含多轮对话，一次执行可能产生多条消息。这些关系就是模型。

规则可以是一个很短的函数，不必为了「领域模型」把每个名词都做成复杂的类：

```ts
function canApprove(run: Run, requestId: string) {
  return run.status === 'waiting' && run.pendingRequestId === requestId;
}
```

这就是一条业务规则：只有还在等待，并且请求 ID 对得上，才能审批。类型章的判别联合是在类型上排除矛盾状态。这个函数是在运行时执行同一条规则。两层都需要。

**Moose：** Project 是工作目录。Session 是一次对话。Message 是对话记录。QueueItem 是等待执行的输入。`runId` 是一次执行。`nativeId` 是代理自己的原生会话。

同一目录下的代理执行互斥。终端和手动命令可以和它在同一目录里并行。这是一条业务约束，不是数据库顺便变成这样。

## 容易答错的地方

翻译文案只是国际化的一块。日期、复数、语序、布局、无障碍文本都算。

灰度分组要稳定。随机会让同一个人跨版本。

功能开关能立刻停掉能力。回滚安装包还要考虑已经写入的数据。

纯函数的核心是相同输入相同输出、不改外部状态。写法可以是普通函数，不必到处用 `reduce`。

没变的部分沿用原引用，仍然是不可变更新。深拷贝会把「没变」变成「全是新对象」，`memo` 就失效了。

领域模型是规则和关系，不是类的数量。规则放在 Service 或 Store 里即可。

Moose 的桌面和 Web 共用版本号，更新要用户主动执行。稳定分组、自动回滚是设计话题，不是现成平台。不要把它们说成 Moose 已经有的发布系统。

## 合上之后能说的几句

十二章的阅读顺序在 [rehab 目录](README.md)。这里只收本篇四句。

国际化用稳定 key 和 `Intl`，别拆开句子硬拼。Moose 有中英词典和 system、en、zh-CN，日期并未全部本地化。

灰度用稳定分组和功能开关，回滚前确认数据。Moose 不是灰度平台。`moose update` 由用户执行。桌面和 Web 共用版本。

纯函数把合并这类计算和存库分开。`mergeMessages` 按 `seq` 留新的，没变就返回原数组。

领域模型描述身份、归属和允许的操作。Project 是目录，Session 是对话，`runId` 是一次执行。同一目录的代理执行互斥，终端和手动命令仍可并行。
