# 三、状态：谁拥有数据，什么能存下来

> 对应答案：[03-state-management.md](../03-state-management.md)，原题 1、2、5、6。
> 读完要能讲清：状态按归属和变化频率拆开；快照里能有什么；「已经收到请求」和「已经生成结果」差在哪；React 19 那几个 API 各管哪一段等待。

## 这章在解决什么问题

聊天页里的数据不是一种东西。输入框每个按键都变，设置几乎不变，消息被后台不停换版本，任务还有排队、执行、中断。全塞进一个大对象，任何一个字段变化，所有读这个对象的组件都可能跟着渲染。关掉页面再打开，你能找回的也只是写进磁盘的记录，不是当时还挂着的网络连接。

这一章的主线是三问：

```
这份数据归谁，变得有多勤？
关掉之后，哪些事实还在，哪些连接必须重来？
用户点了发送，画面上要马上出现的是「真实的等待」，还是「还没发生的回答」？
```

## 1. 按归属和频率拆开

| 状态 | 特点 | 放哪 |
| --- | --- | --- |
| 消息、生成任务 | 服务端事实，后台持续更新 | 共享 store，按 ID 存 |
| 用户设置 | 很少变，很多地方要读 | 共享，但和消息分开 |
| 输入框文字、弹窗开关 | 只有这块界面关心 | 组件自己的 state |

按 ID 存，是为了更新一条时不去碰其他条的对象。组件用 selector 只订阅自己那一条：selector 就是「从整个 store 里挑出我要的那一块」的函数。挑出来的结果如果和上次是同一个引用，订阅者就不必重渲染。

```ts
const message = useChatStore((state) => state.messagesById[id]);
// 更新时只替换 messagesById[id]
// 其他消息保持原来的对象
```

能从已有数据算出来的值，不要再存一份。存了就会出现两份同时改、改了一份忘了另一份。例如「未读条数」如果已经能从消息列表算出来，再存一个 `unreadCount` 就要在每次增删时手动同步。

Zustand 和 Redux Toolkit 都是这种 store 的常见实现：一份共享数据，组件按需订阅。它们解决的是「跨组件共享、又不要所有组件绑在同一份大对象上」。输入框不必为了这个目的进全局 store。

**和上一章片段合并的关系：** 合并算法决定「这条消息的新版本是哪一份对象」。store 决定「谁订阅这份对象」。引用不变，订阅者才能被跳过。性能章会把这一点接到 `memo` 上。

## 2. 快照是事实的记录，不是进程的休眠

快照要回答：关掉再打开，用户还能看到什么。它保存的是数据，不是正在跑的 JavaScript。

适合写进去的：

- 数据版本
- 会话配置
- 消息和消息自己的版本
- 待发送队列
- 最后确认的游标
- 原生会话 ID（用来向底座续接它自己的会话）

不适合写进去的：进行中的 Promise、网络连接、子进程。这些绑在当时的内存和操作系统资源上，序列化不了。新进程要重新建立。

写入时这几样记录要彼此一致。不能队列写进去了、对应消息没写进去，否则恢复出来的世界自相矛盾。这就是事务要保证的事：**几条记录一起成功，或者一起不出现。**

恢复的顺序：

```
读出已持久化的会话、消息、队列
  → 校验，并按版本把旧格式迁过来
  → 原来是 queued / running / waiting 的，标成 interrupted
  → 旧队列先暂停，不要一启动就自动接着跑
  → 页面再拉快照和消息
  → 连接和进程由新进程另行建立
```

```ts
const restoredStatus = ['queued', 'running', 'waiting'].includes(saved.status)
  ? 'interrupted'
  : saved.status;
```

标成中断，是因为你无法证明那次执行还活着。直接标回 running，页面会假装有一个已经不在的任务。

**补充知识：** 「原生会话 ID」指底座（例如某个 Agent CLI）自己记住的会话。恢复它，是请底座按它的方式续上上下文。这和「把 Moose 进程里的 Promise 冻住再解冻」不是一回事。面试材料里也强调过：界面重连、原生会话续接、活进程恢复，是三种能力。

## 3. 立即反馈，是展示已经发生的事

用户点发送之后，模型可能还在排队，或者在等审批。这时可以马上显示的，是已经成立的事实：请求已收下、已进入队列。

不能马上显示的，是还没生成的回答。预画一段虚构的 AI 回复，失败或内容完全不同时，你得把假文字收回来，用户已经把它当成结果看过了。

```
点击发送
  → 立刻显示「已提交 / 排队中」（真实状态）
  → 后台确认后，把这次请求关联到正式任务 ID
  → 收到真实增量，才开始画回答
  → 失败：保留用户输入，让人自己决定要不要重试
```

重试要避免同一件有副作用的事执行两次。切换会话之后，旧会话迟到的结果不能写进当前会话。这和流式章的序号是同一类问题：迟到的数据要核对身份。

**Moose 里和这句话直接对应的事实：** `send` 返回，表示用户输入已经持久化到队列，不表示模型已经回答完。

## 4. React 19：把「等、错、先显示一下」从手写开关里拿出来

发送以前常常手写：`sending` 布尔值、错误字符串、禁用按钮、失败后把列表改回去。React 19 把其中几段变成了内置行为。

| API | 管什么 | 对话里可以怎么用 |
| --- | --- | --- |
| Action（放进 transition 的异步函数） | 执行期间 `isPending` 为真 | 发送期间禁用按钮 |
| `useActionState` | 记住上一次的返回值（结果或错误）和 `isPending` | 显示「发送失败，请重试」 |
| `useOptimistic` | 进行期间先显示临时状态，结束回到真实数据 | 用户刚打的那句话先出现 |
| `<form action={fn}>` | 提交时调用 Action；`useFormStatus` 读提交状态 | 输入框和按钮写成一个表单 |

乐观更新适合**结果基本能预知**的事，比如用户自己的那句话，内容你已经知道。AI 的回答无法预知，不能用它造一句假回复。这正好接上上一节：立即反馈可以，伪造结果不行。

临时消息要带标记，例如 `pending: true`，画成半透明或「发送中」。它只在 Action 进行期间存在：

```
调用 addOptimistic
  → 列表先多出一条临时消息
成功：真实列表到来，临时状态被换掉
失败：没有新的真实数据，临时状态消失（界面上等于撤回）
```

失败时乐观消息会消失，所以输入内容还要留在输入框或错误提示里，否则用户打的字一起没了。自动撤回只收回界面上的临时态，错误文案和重试入口仍要自己做。

```tsx
const [optimistic, addOptimistic] = useOptimistic(
  messages,
  (list, text: string) => [
    ...list,
    { id: 'temp', role: 'user', text, pending: true },
  ],
);

const [error, sendAction, isPending] = useActionState(
  async (_prev: string | null, form: FormData) => {
    const text = String(form.get('text'));
    addOptimistic(text);
    try {
      await api.send(text);
      return null;
    } catch {
      return '发送失败，请重试';
    }
  },
  null,
);
```

`useOptimistic` 的更新要发生在 Action 或 transition 里。在普通点击回调里直接调用，React 会警告，临时状态也不会按预期留住。上面的例子能成立，是因为 `useActionState` 的函数本身跑在 transition 里。

### 手写 sending 和这套 API

| | 手写 `useState` | Actions 一组 |
| --- | --- | --- |
| 进行中 | 自己设 true / false，要记得在失败分支改回去 | `isPending` 跟着 Action 走 |
| 错误 | 自己存 | `useActionState` 的返回值 |
| 先显示用户消息 | 自己插入再自己删 | `useOptimistic` 结束时回到真实数据 |
| 仍要自己做的 | 全部 | 保留草稿、错误文案、不要伪造 AI 回答 |

## 容易混在一起

**全局 store 和组件 state。** 看「还有谁要读」以及「变得勤不勤」。每个按键都进全局消息库，订阅消息的列表会被输入拖着渲染。

**快照和运行中任务。** 快照恢复的是记录。原来进行中的任务在新进程里标成中断，直到你重新核对。

**已入队、生成中、已完成。** `send` 成功只走到第一段。回答文本来自后续事件。

**乐观的用户消息和乐观的 AI 回答。** 前者内容已知。后者是猜测。

## Moose 这一章实际落在哪

逐步写法见 [答案](../03-state-management.md)。不要把通用方案说成已经接上：

| 实际 | 不要说成 |
| --- | --- |
| `useWorkspace` 管快照，`useTranscript` 管当前消息，输入留在组件里 | 用了 Zustand 或 Redux |
| 快照不含全部消息。重启把 queued / running / waiting 标成 interrupted，旧队列先暂停 | 快照能复活进程 |
| `send` 只表示已经入队 | 发送成功等于模型做完了 |
| 依赖是 React 19，但没有 Actions、`useActionState`、`useOptimistic`、`useTransition` | 因为是 React 19 就用了这些 Hook |
| 手写 `sending`，失败留草稿；用户消息等队列写入后的快照出现 | 乐观地显示了还没生成的回答 |

## 本章速记

先按「谁要读、变得多勤」把输入、设置、消息分开，消息按 ID 存，更新一条时别的对象保持原引用。能算出来的不要再存一份。快照只保存可恢复的事实，并用一次一致的写入把会话、消息、队列放在一起；Promise、连接和进程恢复不了，所以重启后把排队、执行、等待标成中断，旧队列先暂停，再由页面重拉。用户点发送后立刻显示的是「已入队」这种已经发生的状态，真实增量到达才显示回答，失败则留下草稿。React 19 的 Action 管进行中，`useActionState` 管结果和错误，`useOptimistic` 只适合预知得了的用户消息，而且要写在 transition 里；AI 回答不能靠它伪造。Moose 用的是 workspace 快照加 transcript，手写 `sending`，消息等队列写入后的快照出现，并没有用上述这几个 Hook。
