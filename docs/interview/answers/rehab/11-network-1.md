# 十一、请求怎么发 · 上：失败之后还剩什么

> 对应答案：[11-scenarios-network-upload.md](../11-scenarios-network-upload.md)，原题 10、17、24、52。下篇讲浏览器怎么认出你。

监控章记下了单次请求的耗时和失败。请求本身怎么发，决定失败的代价是重传整份、还是只重传一块，以及十次失败会不会变成十个弹窗。这一篇按代价往下接：大文件先做到可恢复，重复请求按它怎么重复来处理，批量失败时提示和记录分开，最后才谈每秒请求数太高时谁该限流。

## 大文件先做到失败只重传一块

几个 G 的文件一旦断开就要从头传。分片把文件切成多块，每一块单独确认。它解决的是失败重传和续传，不是把同一条带宽切成几份就会更快。

先向服务端申请 `uploadId`。用 `file.slice` 按偏移取出当前这一片，不要一次读进整个文件。`file.slice` 只划出这一段的视图。限制同时上传的片数。某一片失败只重试这一片。全部完成后，服务端校验并合并。

续传时先问服务端哪些片已经确认，只补剩下的。依据是服务端的确认，不是客户端自己记的进度条。客户端记的进度在崩溃后可能是假的。同一片重复上传，服务端要做成幂等：结果和只传一次一样。同时限制大小、类型和用户配额。

片数是算出来的：文件大小除以分片大小，向上取整，最后一片可以不满。片小，失败只重传一小块，但请求次数多。片大，请求少，失败一次要重传很大一块。还要算上服务端对片数和会话时限的限制、文件哈希的成本、移动端内存。并发数用真实网络和失败率来定，不要抄一个固定的 4 或 6。

10 MB 切成十块，总字节仍是 10 MB。带宽不变时，纯传输时间的下限接近「数据量 ÷ 带宽」。真实耗时还要加上每片的请求开销、校验和合并。片太小或并发太高造成拥塞，会更慢。所以既不能说分片一定快几倍，也不能断言它一定和整文件一样快。

**Moose：** 附件单文件上限 20 MB，先导入本地受控目录，由后台一次导入并保存。Web 按文件逐个提交。没有网络分片上传，也没有分片参数。

## 文件能续传了，普通请求还会因为不同原因发重

用户连点，请求进行中不再接受提交。多个组件同时读同一份数据，共享同一个在途 Promise。搜索词一直在变，取消旧请求，用代次丢掉迟到结果。写操作被提交了两次，服务端用幂等键，同一个键只生效一次。一次要发几百个请求，用有上限的队列，不要 `Promise.all` 一次全放出去。

连点只靠按钮，挡不住脚本、重试或另一个页签。写操作仍要服务端幂等键。

共享在途 Promise：用请求的 key 查一张表，没有才真正发出，并在 `finally` 里删掉。后来的调用方直接拿到表里那个 Promise。同一时刻只会有一次网络请求。

搜索词变了，旧结果已经没用。取消旧请求，并让每次请求的编号递增。响应回来时编号对不上就丢弃。这和流式章丢掉更旧的序号、状态章丢掉别的会话迟到的结果一样，都是在核对「这份数据还是不是当前这次」。

大量请求要限制的是同一时刻在飞的个数。上限 4 时先发 4 个，完成 1 个再取第 5 个。第 2 个失败只记下它的错误，其他继续。队列里优先当前页必需的数据，用户离开后取消已经无用的。

```ts
let next = 0;
async function worker() {
  while (next < tasks.length) {
    const i = next++;
    try {
      results[i] = { status: 'fulfilled', value: await tasks[i]() };
    } catch (reason) {
      results[i] = { status: 'rejected', reason };
    }
  }
}
await Promise.all(Array.from({ length: 4 }, worker));
```

`next++` 发生在 `await` 之前。主线程上这一步不会被另一个 worker 插进来，所以不会两个 worker 领到同一个下标。前端并发上限替代不了服务端限流。收到 429 仍按服务端的指示退避。

**Moose：** 额度查询会合并并发读取。前端的请求代次用来防止旧快照覆盖新快照。这两件解决的问题不同：一个是不要为同一次读取打两次，一个是慢的旧响应不要盖住新的。后台按工作目录串行运行代理任务，不同目录可以并行。这是任务调度，不是包住所有 HTTP 请求的通用队列。

## 请求没有发重，一批一起失败时仍不该弹十次

十个请求因断网一起失败，弹十个相同的 toast，用户无法阅读。网络层仍要如实交出每一个错误。提示层再按错误类型或业务批次收成一句。十条失败记录都留着。给人看的提示可以收成一句，排查用的记录仍是每条一份。

同一批用 `Promise.allSettled`：等全部结束，每一项单独是成功或失败。`Promise.all` 在第一项失败时就拒绝，你拿不到其余项的结算。要「整批结束再提示一次」，用 `allSettled`。

鉴权过期统一去登录页。用户主动取消的请求不弹失败。避免组件内部和全局拦截器各弹一次。

**Moose：** 连接状态和操作错误分开保存。重连成功不能清掉还没处理的保存失败。专门的处理建议依赖稳定的错误码，未知错误会保留详情。没有按业务批次聚合多次请求错误的专用 toast。

## 单批收干净了，每秒的请求数仍可能把某一段打满

QPS 是每秒请求数。大促或热点时变慢，先确认瓶颈在哪一段。只在前端加一个转圈，后台已经过载的事实不会变。

服务端做配额、限流、排队，必要的时候扩容。读请求能缓存的就缓存。非关键任务延后。超出限制时返回明确的重试信息。前端减少重复请求，限制并发。重试时等待逐渐变长，再加一点随机，避免所有客户端在同一秒一起重试。失败时保留用户已经输入的内容。

`Retry-After` 除了纯秒数，还可能是一个日期。只按数字解析会把日期当成无效。自动重试写操作之前，确认它是幂等的，否则可能重复下单。429 表示服务端已经在限，客户端按它说的等。

**Moose：** 目录互斥解决的是本地任务抢同一个工作目录，不是公网 QPS 限流。
