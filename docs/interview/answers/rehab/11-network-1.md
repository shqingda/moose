# 十一、请求怎么发 · 上

> 对应答案：[11-scenarios-network-upload.md](../11-scenarios-network-upload.md)，原题 10、17、24、52。下篇讲同源、Cookie、扫码和 DNS。
> 读完要能讲清：分片解决的是失败后的重传，不是把带宽变大；重复请求有好几种来源，处理不一样；提示可以合并，错误记录不能合并；QPS 高时前端退避替代不了服务端限流。

## 1. 大文件：分片是为了可恢复

几个 G 的文件一旦断开就要从头传，体验很差。分片上传把文件切成多块，每一块单独确认。它解决的是失败重传和续传，不是「把同一条带宽切成几份就会更快」。

```
向服务端申请 uploadId
  → 用 file.slice 按偏移取出当前这一片（不要一次读进整个文件）
  → 限制同时上传的片数
  → 某一片失败只重试这一片
  → 全部完成后，服务端校验并合并
```

续传时先问服务端哪些片已经确认，只补剩下的。依据是服务端的确认，不是客户端自己记的进度条。客户端记的进度在崩溃后可能是假的。同一片重复上传，服务端要做成幂等：结果和只传一次一样。同时限制大小、类型和用户配额。

片数是算出来的：`ceil(文件大小 / 分片大小)`，最后一片可以不满。真正要选的是每片多大。

| 片 | 好处 | 代价 |
| --- | --- | --- |
| 小 | 失败只重传一小块 | 请求次数多，每次请求的开销占比高 |
| 大 | 请求少 | 占内存，失败一次要重传很大一块 |

还要放进权衡的：服务端对片数、单片大小、上传会话时限的限制，文件哈希的计算成本，移动端内存上限。并发数是另一个旋钮，用真实网络和失败率压测，而不是抄一个固定的 4 或 6。

关于速度：10 MB 切成十块，总字节仍是 10 MB。带宽不变时，纯传输时间的下限接近「数据量 ÷ 带宽」。理想情况下，切片和整文件传完的时间可以差不多。真实耗时还要加上每片的请求开销、校验和合并。片太小或并发太高造成拥塞，会更慢。所以既不能说分片一定快几倍，也不能断言它一定和整文件一样快。

```ts
for (let offset = 0; offset < file.size; offset += chunkSize) {
  const part = file.slice(offset, offset + chunkSize);
  await uploadPart(uploadId, offset, part);
}
```

这是串行示意。实际还要并发上限，并在续传前查询已确认的片。`file.slice` 只划出这一段的视图，不会把整个文件读进内存。

**Moose：** 附件单文件上限 20 MB，先导入本地受控目录，由后台一次导入并保存。Web 按文件逐个提交。没有网络分片上传，也没有分片参数。

## 2. 重复请求：先看它是怎么重复的

| 来源 | 处理 |
| --- | --- |
| 用户连点 | 请求进行中不再接受提交 |
| 多个组件同时读同一份数据 | 共享同一个在途 Promise |
| 搜索词一直在变 | 取消旧请求，用代次丢掉迟到结果 |
| 写操作被提交了两次 | 服务端幂等键：同一个键只生效一次 |
| 一次要发几百个请求 | 有上限的队列，不要 `Promise.all` 一次全放出去 |

连点只靠按钮，挡不住脚本、重试或另一个页签。写操作仍要服务端幂等键。

共享在途 Promise：用请求的 key 查一张表，没有才真正发出，并在 `finally` 里删掉。后来的调用方直接拿到表里那个 Promise。这样同一时刻只会有一次网络请求，所有人等同一次结果。

搜索词变化之后，旧结果已经没用。取消旧请求，并让每次请求的编号递增，响应回来时编号对不上就丢弃。这和流式章丢掉更旧的 `seq`、状态章丢掉别的会话迟到的结果一样，都是在核对「这份数据还是不是当前这次」。

大量请求要限制的是**同一时刻在飞的个数**，不是把全部推迟到晚上。上限 4 时先发 4 个，完成 1 个再取第 5 个。第 2 个失败只记下它的错误，其他继续。队列里优先当前页必需的数据，用户离开后取消已经无用的。

```ts
let next = 0;
const results = new Array(tasks.length);

async function worker() {
  while (next < tasks.length) {
    const i = next++;
    try {
      results[i] = { status: 'fulfilled', value: await tasks[i]() };
    } catch (reason) {
      results[i] = { status: 'rejected', reason };
    }
  }
}

await Promise.all(Array.from({ length: 4 }, worker));
```

`next++` 发生在 `await` 之前。JavaScript 主线程上这一步不会被另一个 worker 插进来，所以不会两个 worker 领到同一个下标。`await` 之后才会让出，让别的 worker 继续领。

前端并发上限替代不了服务端限流。收到 429 仍按服务端的指示退避。

**Moose：** 额度查询会合并并发读取。前端的请求代次用来防止旧快照覆盖新快照。这两件解决的问题不同：一个是「不要为同一次读取打两次」，一个是「慢的旧响应不要盖住新的」。后台按工作目录串行运行代理任务，不同目录可以并行。这是任务调度，不是包住所有 HTTP 请求的通用队列。

## 3. 批量失败：提示合并，记录不要合并

十个请求因断网一起失败，弹十个相同的 toast，用户无法阅读。网络层仍要如实交出每一个错误，提示层再按错误类型或业务批次收成一句。

```
每个请求各自返回成功或失败
  → 提示层按「断网」「这批加载」聚合，只弹一次
  → 十条失败记录都留着
```

同一批可以用 `Promise.allSettled`：等全部结束，每一项单独是成功或失败，不会因为第一项失败就丢掉后面的结果。

**补充知识：** `Promise.all` 在第一项失败时就拒绝，你拿不到其余项的结算。要「整批结束再提示一次」，用 `allSettled`。

```ts
const results = await Promise.allSettled([loadA(), loadB(), loadC()]);
if (results.some((item) => item.status === 'rejected')) {
  showToast('部分数据加载失败');
}
```

鉴权过期统一去登录页。用户主动取消的请求不弹失败。避免组件内部和全局拦截器各弹一次。

**Moose：** 连接状态和操作错误分开保存。重连成功不能清掉还没处理的保存失败。专门的处理建议依赖稳定的错误码，未知错误会保留详情。没有按业务批次聚合多次请求错误的专用 toast。

## 4. QPS 高：先找到哪一段过载

QPS 是每秒请求数。大促或热点时变慢，先确认瓶颈在哪一段。只在前端加一个转圈，后台已经过载的事实不会变。

服务端：配额、限流、排队、必要的扩容；读请求能缓存的缓存；非关键任务延后。超出限制时返回明确的重试信息。

前端：减少重复请求，限制并发；重试时退避（等待逐渐变长）加抖动（加一点随机，避免所有客户端在同一秒一起重试）。失败时保留用户已经输入的内容。

```ts
if (response.status === 429) {
  const raw = response.headers.get('Retry-After');
  const seconds = raw && /^\d+$/.test(raw) ? Number(raw) : undefined;
  showRetryAfter(seconds);
}
```

`Retry-After` 除了纯秒数，还可能是一个日期。只按数字解析会把日期当成无效。自动重试写操作之前，确认它是幂等的，否则可能重复下单。

**Moose：** 目录互斥解决的是本地任务抢同一个工作目录，不是公网 QPS 限流。

## 容易混在一起

**分片和加速。** 分片让失败的代价变成「重传一片」，并允许续传。总字节不变，带宽不变，纯传输不会因此变成原来的几分之一。

**客户端进度和服务端已确认的片。** 续传问后者。

**合并读取、丢掉过期响应、目录串行。** Moose 三件都有，各管一类重复或竞争，没有一个通用 HTTP 队列。

**一个 toast 和一条错误日志。** 给人看的提示可以收成一句。排查用的失败记录仍是每条请求一份。

**前端少发，和服务端限流。** 两端都要。429 表示服务端已经在限，客户端按它说的等。

## 上篇收束

上传先拿 `uploadId`，按片确认，失败只重试那一片，恢复时以服务端已确认的片为准。片的大小在请求开销和重传代价之间选，并发另测。重复请求按来源处理：连点禁用、读共享 Promise、搜索用代次、写入用幂等键、海量请求用有上限的 worker。批量失败时网络层不吞错误，提示层才聚合。QPS 峰值先定位瓶颈，服务端限流和排队，前端退避并保留用户输入。Moose 的附件是 20 MB 内一次导入，没有分片；额度查询会合并，快照用代次，代理任务按目录串行；错误和连接状态分开存，没有批次 toast；目录互斥不是公网限流。
