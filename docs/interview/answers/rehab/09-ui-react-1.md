# 场景题：页面交互、浏览器 API 与 React · 上

> 题单，对着说。每题顺序固定：这题在考什么 → 一句话回答 → 展开说明 → 示例 → Moose 里的做法 → 容易答错的地方。对应 [答案](../09-scenarios-ui-react.md)，原题 1、4、8、9、12、14、15、18。下篇是预览、划词、折叠、布局和 React。事实按 Moose 0.23.3。答题稿里写了「没有」的，不要说成已经做了。

## 1. 如何判断用户设备？为什么不再推荐解析 User-Agent？

> **这题在考什么**：做响应式页面、触屏适配或提供下载按钮时，都会想“先判断用户是什么设备”。老办法是用正则解析 User-Agent（浏览器在每个请求里附带的一段标识字符串），但它越来越不可靠。面试官想看你是否明白：目的不同，该看的信息也不同，并且优先用特性检测和媒体查询。

**一句话回答**：先问清楚为什么要判断设备：排版看视口宽度，交互看 `pointer`、`hover` 媒体特性，功能可用性做特性检测；User-Agent 已被浏览器精简和冻结，只适合服务端做统计或粗略适配。

**展开说明**
- 先拆目的。“判断设备”不是一个单独的问题，为了排版、为了识别触屏、为了提供安装包，需要的信息都不一样。
- 布局看视口宽度和媒体查询。排版真正受影响的是可用空间，而不是设备类型。
- 触控交互看 `pointer: coarse`（主要输入是手指这类粗略指针）和 `hover`（能否悬停）媒体特性。有触屏的笔记本、接了鼠标的平板都很常见，按设备名推测会猜错。
- 功能支持做特性检测，也就是直接检查某个 API 是否存在，而不是根据浏览器名推测。
- 为什么不推荐解析 UA：它可以被伪装；而且出于隐私考虑，主流浏览器已经精简并冻结了 UA 字符串，系统版本、设备型号等细节不再如实给出，正则越写越复杂，结果却越来越不准。
- User-Agent Client Hints 是替代方案：JS 里用 `navigator.userAgentData`，服务端通过 `Sec-CH-UA-*` 请求头按需获取。但它目前只有 Chromium 系浏览器支持，Safari 和 Firefox 没有，不能作为唯一依据。
- 服务端解析 UA 只用于访问统计或粗略适配（比如下载页默认推荐哪个安装包），并且始终给用户手动切换的入口。

| 目的 | 该看什么 |
| --- | --- |
| 排版 | 视口宽度、媒体查询 |
| 触控交互 | `pointer`、`hover` 媒体特性 |
| 功能是否可用 | 特性检测 |
| 统计、下载页默认推荐 | 服务端 UA 或 Client Hints，并允许手动切换 |

**示例**：下面的代码用媒体查询判断主要输入方式，用特性检测判断 API 是否可用，没有解析任何设备名。

```ts
// 主要输入是手指这类粗略指针，且不能悬停：按触屏交互处理
const touchFirst = matchMedia('(pointer: coarse) and (hover: none)').matches;
// 直接检查 API 是否存在，而不是猜浏览器
const canShare = typeof navigator.share === 'function';
// Client Hints 只有 Chromium 支持，拿不到时要有兜底
const isMobile = navigator.userAgentData?.mobile ?? null;
```

**容易答错的地方**
- 屏幕宽不能证明是桌面：平板横屏宽度可能很大，桌面浏览器窗口也可能拉得很窄。
- 不要把 `navigator.userAgentData` 当作通用 API，在 Safari 和 Firefox 上它是 `undefined`。
- 媒体查询的结果会变化（比如平板接上鼠标），需要时用 `matchMedia(...).addEventListener('change', ...)` 监听。

## 4. 滚动跟随导航（电梯导航）该如何实现

> **这题在考什么**：长文档侧边的目录会随着正文滚动高亮当前章节，点目录又能跳到对应章节，这就是电梯导航。面试官想看你能否把“点击定位”和“滚动高亮”两个方向都处理好，并照顾到边界情况。

**一句话回答**：章节设稳定 ID，点击目录用 `scrollIntoView` 定位，滚动时用 IntersectionObserver 判断当前章节并更新高亮。

**展开说明**
- 给每个章节设稳定的 ID，目录项和章节靠它一一对应。
- 点击目录时调用 `scrollIntoView` 滚到对应章节。再给章节加 `scroll-margin-top`（滚动定位时在顶部预留的距离），避免标题被固定头部挡住。
- 用户手动滚动时，用 IntersectionObserver（浏览器提供的“元素是否进入可视区域”的观察器）观察各个章节，进入观察范围就更新目录高亮。它比监听 `scroll` 后逐个计算位置更省性能。
- 点击触发平滑滚动的过程中，会依次经过多个章节。这段时间要暂停根据滚动更新高亮，否则高亮会来回跳。
- 还要照顾键盘操作、用户的“减少动画”系统设置，以及滚到页面底部时最后几节不够高、无法进入观察范围的情况。

**示例**：下面的代码在章节进入观察范围时更新目录高亮。`rootMargin` 把判定区域收窄到视口偏上的一条带上。

```ts
const observer = new IntersectionObserver((entries) => {
  // 取第一个进入判定区域的章节
  const current = entries.find((e) => e.isIntersecting);
  if (current) setActiveId(current.target.id);
}, { rootMargin: '-20% 0px -60% 0px' }); // 上方缩进 20%、下方缩进 60%
sections.forEach((section) => observer.observe(section));
```

**容易答错的地方**
- 示例只取第一个命中的章节。实际要规定多个章节同时可见时选哪一个。
- 组件卸载时要调用 `disconnect()` 停止观察。

## 8. 移动端如何实现下拉滚动加载（顶部加载）

> **这题在考什么**：聊天列表向上翻旧消息时，旧消息会插到现有内容上方。如果只是把数据插进列表，用户正在看的那行会被推下去，画面突然一跳。面试官想看你怎么避免重复请求，以及怎么保持阅读位置不动。

**一句话回答**：接近顶部时按游标取更早的一页，用 `loading` 和 `hasMore` 防止重复请求；插入前记下锚点位置，插入后补偿滚动距离，让原来看的内容留在原处。

**展开说明**
- 滚动接近顶部才触发加载，并按游标（上一页最早一条消息的标识）请求更早的一页。游标比页码稳定，中间有新消息也不会错位。
- 用 `loading` 标记防止加载期间重复请求，用 `hasMore` 标记没有更早数据时停止请求。
- 插入旧消息前，记下第一个可见消息及其相对容器的偏移。插入后调整 `scrollTop`，让这条消息仍在原位置，画面就不会跳。
- 简单做法是比较插入前后的容器总高度 `scrollHeight`，把差值加到 `scrollTop` 上。

**示例**：下面的代码在插入旧消息前后，用容器高度差补偿滚动位置。

```ts
const before = list.scrollHeight;        // 插入前的总高度
await loadOlderMessages();
requestAnimationFrame(() => {
  // 新增内容有多高，就往下滚多少
  list.scrollTop += list.scrollHeight - before;
});
```

**Moose 里的做法**：Moose 已有顶部历史分页，但目前通过“加载更早”按钮触发，并不是自动下拉加载。

**容易答错的地方**
- 示例假设 `loadOlderMessages()` 完成时新增 DOM 已经提交。在 React 中仅等待 fetch 完成并不保证这一点，应在提交后的布局阶段按锚点补偿。
- 图片之后才加载完成、改变了高度时，还需要再次校正。

## 9. 判断页签是否为活跃状态

> **这题在考什么**：页面切到后台时，常需要暂停动画或轮询；用户回来时再刷新数据。面试官想看你能否区分“页面可见”和“页面有焦点”，并知道该在这两种状态下做什么、不该做什么。

**一句话回答**：用 `document.visibilityState` 和 `visibilitychange` 判断页签是否可见，用 `document.hasFocus()` 判断是否能接收键盘输入，两者不是一回事。

**展开说明**
- “可见”表示页面仍能被用户看到，“有焦点”表示键盘输入会交给它。切换浏览器页签和把窗口移到后台，不一定是同一种状态。
- `document.visibilityState` 的值是 `visible` 或 `hidden`，状态变化时触发 `visibilitychange` 事件。
- `document.hasFocus()` 判断当前文档是否有焦点。两个窗口并排时，页面可能可见但没有焦点。
- 页面隐藏时可以暂停动画和非必要的轮询，恢复可见时补读期间错过的数据。

**Moose 里的做法**：Moose 会把可见性、焦点和当前会话报告给共享后台，用来抑制正在查看的会话的通知。任务运行由后台管理，不会随页签隐藏而停止。浏览器对后台页签的节流也可能延迟心跳，因此后台对焦点登记设置了有效期。

**容易答错的地方**
- 不能因为页签隐藏就停止后台任务。
- 可见不等于有焦点。

## 12. 页面关闭时执行方法，该如何做

> **这题在考什么**：用户写了一半直接关掉页面，你想在关闭前把草稿存下来。面试官想看你知不知道关闭事件并不可靠，以及正确的保存策略是什么。

**一句话回答**：重要内容在编辑过程中就逐步保存，页面变为 `hidden` 时尽力补存一次，`pagehide` 作补充，`beforeunload` 只在确有未保存内容时用来提示。

**展开说明**
- 关闭页面不是可靠的“最后一次保存机会”。浏览器可能直接结束进程，异步请求也可能来不及发完。所以重要状态要平时就保存。
- 页面的 `visibilityState` 变成 `hidden` 时尽力补存。这是移动端最可靠的时机，因为用户切走后进程随时可能被系统杀掉。
- `pagehide` 事件作为补充，它在页面被卸载或放入往返缓存时触发。
- `beforeunload` 只在确实有未保存内容时使用，用来弹出“确定离开吗”的提示，不适合用来做保存。

**示例**：下面是关页前尽力补存的事件入口写法（示意）。

```ts
document.addEventListener('visibilitychange', () => {
  // 页面被隐藏（切走、锁屏、关闭前）时补存
  if (document.visibilityState === 'hidden') saveDraft();
});
window.addEventListener('pagehide', saveDraft); // 补充入口
```

**Moose 里的做法**：Moose 关闭窗口后，共享后台可以继续工作；崩溃恢复依靠持久化记录，不依靠窗口关闭回调。

**容易答错的地方**
- 关页时发出的异步请求未必能完成。
- 移动端进程被杀时，甚至不会触发任何关闭事件。

## 14. 长文本溢出，展开/收起如何实现

> **这题在考什么**：评论、简介等长文本常默认只显示几行，点“展开”看全文。面试官想看你怎么判断“是否真的溢出”，以及怎么保证收起时不丢原文、交互可访问。

**一句话回答**：收起时用 `line-clamp` 限制行数，展开时显示原文；用 `scrollHeight > clientHeight` 判断是否真的溢出，没溢出就不显示按钮。

**展开说明**
- 只有两个状态：显示前几行，或显示完整原文。收起只是视觉上截断，DOM 里始终保留全文。
- 收起状态用 CSS `line-clamp`（按行数截断并显示省略号）限制行数。
- 用 `scrollHeight > clientHeight` 判断内容是否超出了可见高度。短内容不溢出，就不显示展开按钮。
- 容器宽度、字体或内容变化后，是否溢出可能改变，需要重新判断。
- 按钮加上 `aria-expanded` 属性，让读屏软件知道当前是展开还是收起。展开时尽量保持用户的阅读位置。

**Moose 里的做法**：Moose 的工具记录和思考记录可以折叠，普通回答不是统一截成三行。

**容易答错的地方**
- 复制时应得到完整原文，而不是截断后的内容。

## 15. 如何实现鼠标拖拽

> **这题在考什么**：拖动弹窗、拖动分隔条调整侧栏宽度，都是页面内拖拽；把本地文件拖进页面，则是浏览器的文件拖放。面试官想看你能否分清这两类需求，并把页面内拖拽的细节做扎实。

**一句话回答**：页面元素拖动用 Pointer Events：按下时记录起点并 `setPointerCapture`，移动时更新 `transform`，抬起或取消时清理；系统文件拖入页面则用 drag/drop 事件和 DataTransfer。

**展开说明**
- 用 Pointer Events（统一了鼠标、触屏、触控笔的指针事件），一套代码同时支持多种输入。
- 按下时记录起点和元素原位置，并调用 `setPointerCapture`（让元素在指针移出后仍持续收到移动事件），否则拖得快时指针一离开元素就丢事件。
- 移动时更新 `transform` 而不是 `left/top`，因为 `transform` 不触发重排。需要时用 `requestAnimationFrame` 把多次移动合并到一帧更新，并限制元素不越界。
- 抬起（`pointerup`）或取消（`pointercancel`）时都要清理状态。
- 要区分点击和拖动，比如移动超过几像素才算拖动。触屏上还要设置 CSS `touch-action`，防止浏览器把手势当成页面滚动。重要操作要提供键盘替代方式。

| 需求 | 使用的 API |
| --- | --- |
| 拖动页面元素、调整宽度 | Pointer Events、`setPointerCapture` |
| 把系统文件拖进页面 | drag/drop 事件、DataTransfer |

**Moose 里的做法**：Moose 的文件和审阅共用一个右侧面板，调整宽度用的就是 Pointer Events 和 `setPointerCapture`，还支持用方向键调整；把文件拖入输入区则使用 `DataTransfer.files`。

## 18. ResizeObserver 有什么用？要实时统计浏览器窗口大小该怎么做？
*（合并了原第 18、19 题）*

> **这题在考什么**：需求可能只是“窄屏改成单栏”，也可能真要用到当前宽高；还有一种情况是窗口没变，侧栏展开后中间的终端或图表却变窄了，这时监听 `window.resize` 收不到任何通知。面试官想看你能否分清“窗口尺寸”和“元素尺寸”，并且不用 JS 去做 CSS 就能完成的事。

**一句话回答**：只改布局用 CSS 媒体查询；确实需要窗口宽高时监听 `window.resize` 读取 `innerWidth/innerHeight` 并按帧合并；关心的是某个容器时用 ResizeObserver 观察元素自身尺寸。

**展开说明**
- 如果只是屏幕窄时改变排版，CSS 媒体查询（或容器查询）就能完成，不需要 JavaScript。
- 业务确实要用到窗口宽高时，监听 `window.resize`，读取 `innerWidth` 和 `innerHeight`。`resize` 触发很频繁，用 `requestAnimationFrame` 把同一帧内的多次变化合并成一次更新。
- 手机软键盘弹出和页面缩放影响的是“可视视口”，需要时看 `visualViewport`。
- ResizeObserver 监听的是某个元素自身的尺寸变化。典型场景：侧栏展开后终端或图表容器变宽变窄，但窗口尺寸没变，此时需要观察容器本身，在回调里重新布局（比如让终端重新计算行列数）。
- ResizeObserver 回调中不要反复修改被观察元素的尺寸，否则会循环触发。必要时先比较新旧尺寸，并把写操作放到下一帧。
- 两种监听都要在组件卸载时清理。

| 关心什么 | 用什么 |
| --- | --- |
| 窄屏换排版 | CSS 媒体查询 |
| 窗口宽高数值 | `window.resize` + `innerWidth/innerHeight` |
| 软键盘、缩放后的可视区域 | `visualViewport` |
| 某个容器的尺寸 | ResizeObserver |

**示例**：下面的代码观察终端容器的尺寸，变化时让终端重新适配。

```ts
const observer = new ResizeObserver(() => fitAddon.fit()); // 按新尺寸重算终端大小
observer.observe(container);  // 观察容器，而不是窗口
// 组件卸载时 observer.disconnect()
```

**Moose 里的做法**：
- Moose 的终端视图用 ResizeObserver 来调整终端大小。
- 右侧面板的初始宽度按 `window.innerWidth` 计算，窗口 resize 时重新限制面板宽度；Moose 没有持续上报用户的窗口尺寸。

**容易答错的地方**
- `window.resize` 只能感知窗口变化，容器因布局变化而改变尺寸时它不会触发。
- 能用 CSS 解决的排版问题，不要用 JS 监听尺寸再改样式。
