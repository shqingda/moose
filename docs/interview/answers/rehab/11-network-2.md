# 十一、浏览器怎么认你 · 下

> 承接 [上篇](11-network-1.md)。对应原题 33、34、64、65。
> 读完要能讲清：跨域加载和跨域读取差在哪；Cookie 的每个属性控制什么，什么情况下两个网站共享不了；扫码登录里二维码为什么不能是登录凭据；DNS 改了为什么不会立刻对所有人生效。

## 1. 同源策略限制的是读取

同源指协议、域名、端口都相同。同源策略限制脚本去读另一个源的响应内容。它不禁止页面加载一切跨源资源。

以另一台主机上的同一张图片为例：

| 操作 | 结果 |
| --- | --- |
| `<img src="https://cdn.example/a.png">` | 通常可以显示 |
| `fetch` 之后读取内容 | 需要 CDN 用 CORS 允许当前页的源 |
| 画进 Canvas 再读像素 | 还要满足跨源图片的读取条件，否则画布被污染，读像素会失败 |

`<img>`、`<link rel="stylesheet">`、经典的 `<script>` 可以直接引用 CDN，浏览器会加载并使用。模块脚本（`type="module"`）、字体、Canvas 像素另有跨源限制。

CORS 是服务端明确授权「这个源可以读我的响应」，常见响应头是 `Access-Control-Allow-Origin`。没有这层授权，`fetch` 读跨源内容会失败，尽管一张 `<img>` 可能已经把同一 URL 显示出来了。

CSP 是站点自己声明允许从哪些地址加载资源。它可能直接拦住 CDN，即使同源策略本允许嵌入。两套规则叠在一起。

图片能显示，也不等于能拿到完整的资源计时。计时细节还要 `Timing-Allow-Origin`（见监控章）。

**Moose：** Web 的页面和 API 由同一个本机服务提供。CSP 默认只允许加载本站资源。目前不依赖跨域 CDN。

## 2. Cookie：设置时的属性和之后带回的值

服务端用 `Set-Cookie` 告诉浏览器保存什么、何时过期、向哪里送。属性只出现在设置的时候。之后浏览器发出的 `Cookie` 请求头，通常只带名称和值。

| 属性 | 作用 |
| --- | --- |
| `Domain` | 哪些域名会收到。不设就只属于当前主机 |
| `Path` | 哪些路径下的请求会带上 |
| `Expires` / `Max-Age` | 过期时间或有效秒数。都不设就是会话 Cookie，会话结束即失效 |
| `Secure` | 只在 HTTPS 下发送 |
| `HttpOnly` | JS 不能用 `document.cookie` 读到 |
| `SameSite` | 跨站请求带不带：`Strict`、`Lax`、`None` |
| `Partitioned` | 按顶层站点分区存放（CHIPS），用于第三方嵌入 |

`HttpOnly` 只禁止脚本读取。浏览器在符合规则的请求里仍会自动带上。`Path` 不是安全隔离：不要指望靠路径挡住同一站点上的其他页面。

有共同父域时，`Domain=example.com` 可以让 `a.example.com` 和 `b.example.com` 都收到。`a.com` 和 `b.com` 这种无关域名不能共享同一个 Cookie。跨站登录的做法是：统一身份服务完成跳转，各站点再各自建立自己的会话。

跨站还受浏览器隐私策略影响。Safari 和 Firefox 默认就会拦截或隔离第三方 Cookie。不要说「所有浏览器已经彻底移除了第三方 Cookie」，策略并不相同。`SameSite=None` 必须同时带 `Secure`。`Partitioned` 让嵌入场景下的 Cookie 按顶层站点隔开，具体效果以各浏览器为准。

跨源请求若要带 Cookie，前端要打开凭证，例如 `fetch` 的 `credentials: 'include'`，服务端也要返回允许凭证的 CORS 头。只加一边是不够的。

```http
Set-Cookie: moose_session=<随机值>; HttpOnly; SameSite=Strict; Path=/; Secure
```

**Moose：** Web 的 `moose_session` 没有设置 `Domain`，是当前主机的 Cookie，没有做跨子域共享，也没有设置过期时间。通过 HTTP 访问时不会设置 `Secure`。之后的请求只带回 `Cookie: moose_session=<随机值>`，后台再检查这个值是不是有效会话。

## 3. 扫码登录：二维码只是一次等待的编号

电脑上的网页要登录，手机已经登录了同一个账号。二维码如果直接等于长期凭据，被人拍照就能冒用。它只应该让手机找到「这台电脑正在等的那一次登录」。

```
电脑向服务端申请扫码会话
  → 服务端给出不可预测、短期、一次性的标识
  → 电脑把标识画成二维码（里面没有长期凭证）
  → 已登录的手机扫码，展示将要登录的设备，用户点确认
  → 服务端记下授权
  → 电脑用轮询或推送得知结果，再建立电脑自己的登录会话
```

会话要过期、只能用一次，并绑定发起请求的那台电脑。否则一个二维码可以被另一台机器拿去完成登录。

**Moose：** 当前没有扫码登录。上面是设计方案，不是项目功能。

## 4. DNS：先把名字变成地址

浏览器拿到网址后，要先知道域名对应哪个网络地址，才能建立连接。DNS 只负责找地址，不负责网址后面的路径。路径是连上之后 HTTP 的事。

| 记录 | 给出什么 |
| --- | --- |
| A | IPv4 地址 |
| AAAA | IPv6 地址 |
| CNAME | 这个名字是另一个域名的别名，还要再解析那个名字 |

查找会经过好几层缓存：浏览器、操作系统、递归解析器（运营商或公共 DNS）。缓存没有命中时，递归解析器再去问权威 DNS 上的记录，并按 TTL 缓存。TTL 是这条记录建议的缓存时长。

```
浏览器缓存
  → 操作系统缓存
  → 递归解析器缓存
  → 未命中：问权威服务器
  → 得到 A / AAAA（CNAME 则先跳到目标名）
  → 按 TTL 缓存
  → 然后才是建立连接和 HTTP
```

CDN 可以借助解析策略，把用户指到较近或较空闲的节点。所以同一个域名在不同网络里解析出的 IP 可以不同。

因为有多层缓存，改了域名解析之后，不会立刻对所有人生效。还没过期的缓存会继续用旧地址。

这一题的答案没有写 Moose 的 DNS 配置。不要把通用解析过程说成项目里的实现。

## 容易混在一起

**加载和读取。** 图能显示，是加载。`fetch` 读正文、Canvas 读像素，是读取，要额外授权。

**Set-Cookie 和 Cookie 请求头。** 属性在设置时。之后带回的多半只有名字和值。

**HttpOnly 和「不会发送」。** 脚本读不到，浏览器仍会带上。

**会话 Cookie 和设了 Domain 的 Cookie。** 不设过期，是会话期。不设 Domain，是当前主机。两件独立。

**二维码和登录凭据。** 二维码只标识一次待确认的会话。长期凭证在用户确认之后，发给电脑自己的会话。

**DNS 和 HTTP。** DNS 结束于「知道 IP」。页面路径、Cookie、TLS 都在后面。

## 本章速记

浏览器允许嵌入很多跨源资源，但脚本要读取内容就需要 CORS；CSP 还可以再限制加载来源。Cookie 在 `Set-Cookie` 时声明域名、路径、寿命、是否仅 HTTPS、脚本能否读取、跨站是否携带。不设 `Domain` 就只属于当前主机，无关的两个域不能直接共享，登录要靠统一身份服务跳转后各自建会话。扫码时二维码里只放短期一次性的会话标识，手机上的用户确认之后，电脑再建立自己的会话。DNS 经多层缓存把名字解析成 A / AAAA 或顺着 CNAME 再查，并按 TTL 缓存，所以修改不会立刻全球生效。Moose 的页面和 API 同源，CSP 默认只许本站，不依赖跨域 CDN；`moose_session` 是当前主机的会话 Cookie，HTTPS 下才带 `Secure`，没有扫码登录。
