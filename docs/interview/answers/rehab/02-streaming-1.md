# 二、流式 · 上：把字节变成可靠事件

> 对应答案：[02-streaming.md](../02-streaming.md) 第 1、3 题。下篇讲 Markdown、渲染优先级和半截 JSON。
> 读完要能讲清：组帧、按类型分发、续接是三件不同的事；怎样才算「生成完成」；序号怎样去重和发现缺号；一条回复里多个片段怎样合并。

## 这章在解决什么问题

模型不是一次性交回整段文字。数据以字节到来，中间会断线，断线后服务端可能还在生成。前端要同时避免三件事：把半包当成一条消息、把重复的增量再拼一遍、把「连接断了」当成「回答写完了」。

先把四个词分开。后面所有规则都挂在这四个词上。

| 词 | 是什么 |
| --- | --- |
| 字节 | 网上实际到的原始数据，可能卡在一个汉字的中间 |
| 帧 | 按协议切出来的一条完整消息，SSE 里用空行结尾 |
| 事件 | 帧里写明的类型：一段正文、一个错误、一次结束 |
| 片段 | 业务上的一块内容：一段正文、一次工具记录、一张表 |

```
字节  --组帧-->  帧  --按类型-->  事件  --按身份合并-->  片段  --按显示顺序-->  页面
```

## 1. 组帧：半行留下，空行才算一条

SSE（Server-Sent Events）是服务器单向推文本事件的约定。一条事件长这样，空行表示这条结束：

```
id: 3
event: response.output_text.delta
data: {"delta":"你"}
<空行>
```

一次 `read()` 不一定读到这条空行。也可能读到半行，甚至读到一个汉字的半个字节。

**补充知识：** UTF-8 里一个汉字常常占 3 个字节。两次读取可能把这 3 个字节拆开。如果每次都把字节直接按文本解码，拆开的那半会变成乱码，而且乱码补不回来。

`TextDecoder` 的 `{ stream: true }` 会把没凑齐的字节留到下一次。应用自己还要把「没遇到空行的半行文本」留在缓冲区里：

```ts
buffer += decoder.decode(chunk, { stream: true });
const frames = buffer.split('\n\n'); // 空行才是事件边界
buffer = frames.pop() ?? '';         // 最后一段可能没写完
```

组帧时还有三件容易漏的小事：

- 换行要兼容 `\r\n`，上面为了短，只按 `\n` 示意。
- 同一条事件里可以有多行 `data:`，拼回正文时用换行把它们连起来。
- 缓冲区里最后一段在空行出现之前，都不能解析。

**为什么要先组帧再谈业务？** 如果按「每次 read 到的字符串」去 `JSON.parse`，半包必然解析失败，一个事件被拆成两次 read 时又会漏字段。组帧把「传输切分」和「业务含义」隔开。

## 2. 按事件名分发，不要在正文里找结束标记

早期 OpenAI Chat Completions 用 `data: [DONE]` 表示结束。2025 年 3 月的 OpenAI Responses API，以及 Anthropic Messages API，改成在 `event:` 行写事件名，`data:` 里放 JSON。

客户端认的是事件名：

| 事件名 | 含义 | 客户端 |
| --- | --- | --- |
| `response.output_text.delta` | 一小段新文字 | 追加到当前片段 |
| `response.completed`、`message_stop` | 这次生成正常结束 | 标记完成，关连接，清监听 |
| `error` | 服务端或模型报错 | 显示错误，保留已收到的文字 |
| 不认识的名字 | 协议以后新加的 | 忽略并记一笔，不要因此中断 |

正文里完全可能出现 `[DONE]` 这几个字符。在正文里搜索它，会把一句普通的话当成结束。新接口根本不发这个标记。

三种失败也要分开说，因为用户下一步不同：

| 情况 | 回答的状态 | 下一步 |
| --- | --- | --- |
| 网络断开，没收到结束事件 | 不完整 | 重试或重新拉取，不能当成写完了 |
| JSON 解析失败 | 这条帧坏了 | 按协议错误处理 |
| 模型或服务端 `error` 事件 | 业务失败 | 提示原因，保留已有文字 |

连接关掉时如果从来没走过「完成」分支，就标成未完成。

## 3. 序号、重连、去重、缺号

服务端为一次生成分配 `runId`，为每条增量分配递增序号，并写进 SSE 的 `id:` 行。

浏览器原生 `EventSource` 重连时，会自动带上请求头 `Last-Event-ID`，告诉服务端「我最后看到的 id」。这只是客户端的声明。服务端要自己存着可补发的事件，才能从那个 id 之后接着发。客户端单靠序号，找不回已经丢掉、而服务端又没留底的内容。

客户端收到后仍要自己检查：

```
序号 <= 已处理的最大序号    丢掉（重连常把最后一条再送一遍）
序号 == 已处理 + 1          按顺序应用
序号跳了                    中间丢了，补读或整份重拉，不能干等
```

例子：断线前处理过 1、2。重连收到 2、3：丢掉 2，接上 3。如果直接收到 4，说明 3 没了。

重连还有一层更重要的含义：**把通道接回来，不是再提交一次生成。** 用户点停止，要另外发取消请求。取消和重连如果混成一个动作，断线一次就会把任务停掉，或者把同一段话生成两遍。

```
发送任务（一次）
  → 订阅事件流
  → 断线：只重连这条流，用序号续上
  → 用户停止：另发取消，等服务端确认任务停了
```

## 4. 多个片段：身份、顺序、追加还是替换

一轮回答里可能同时有正文、工具记录和表格。网络包的到达顺序，不一定是页面上的显示顺序。不同片段的文字也不能拼进同一条消息。

给三层身份：

| 身份 | 区分什么 |
| --- | --- |
| `runId` | 这一轮任务 |
| `partId` | 这一轮里的正文、代码或表格 |
| 片段内序号 | 这一片段里的第几段增量 |

同一 `partId` 按序号追加，重复序号丢掉。不同 `partId` 分开存。显示顺序另记一份，不能用「谁先到网卡」代替。

缺号时：协议允许补发就补发；不允许就重新读完整状态。不能无限等那个永远不来的序号。

工具参数如果是结构化 JSON，没收全之前只缓存，不能拿半截去执行。下篇讲半截 JSON 时会把这条说透。

上游有两种发法，合并算法不一样：

| 上游发来的 | 你该怎么做 |
| --- | --- |
| 增量：只有新的一小段 | 按序号接在这个片段后面 |
| 快照：整条内容的最新版 | 用新版本换掉旧记录，不要再拼接 |

把快照再拼接一次，文字会重复。把增量当成整段替换，文字会丢。

## 容易混在一起

**一次 read、一条 SSE、一个业务事件。** read 是传输切出来的块；空行才切出一条 SSE；事件名才告诉你这是增量、错误还是结束。

**结束、出错、断开。** 只有明确的结束事件代表正常完成。`error` 是业务失败。套接字关掉而没有结束事件，是不完整。

**重连、补拉、重新生成、取消。** 重连接的是通道；补拉要服务端留着事件；重新生成是一次新任务；取消是另一条命令。

**追加和替换。** 先看这条数据是增量还是整条快照。

## Moose 这一章实际落在哪

以下只复述 [答案](../02-streaming.md) 第 1、3 题。

- Web 用原生 `EventSource` 订阅 `/api/events`（`src/lib/web-api.ts`）。服务端 `electron/web-server.ts` 只写 `data:` 行，内容是 JSON 业务事件，不写 `event:` 和 `id:`，也不用 `[DONE]`。
- 断线后浏览器会自动重连。连接恢复时，页面重新拉取快照，再按消息 ID 和 `seq` 只接受较新的版本。服务端不会按 `Last-Event-ID` 补发每一条增量。
- 和 CLI 之间，`electron/providers/rpc.ts` 先按换行拆出完整 JSON，再分成响应、通知和审批请求。
- 消息 ID 用 `runId:event.key` 生成。同一条记录更新时 `seq` 递增。页面按 ID 和 `seq` 合并，再按 `position` 排序。收到同一条的 `seq=6` 和 `seq=8` 时保留 8。
- 推给页面的是整条消息的新版本，所以是**替换旧记录**，不是把两份正文拼起来。

通用 SSE 客户端里的 `event:`、`id:`、`Last-Event-ID` 补发，是设计讲法。Moose 的 Web 事件流没有这三样。

## 上篇收束

先把字节留到帧完整，再按事件名决定追加、报错还是完成。序号用来丢掉重复、发现空洞。空洞补不回来，是因为服务端没留可重放的事件，不是因为客户端「再解析一次」就能变出来。多个片段各自有身份；增量才追加，快照是整条替换；显示顺序单独记。通道重连、重新生成、用户取消，是三个动作。
