# 二、流式 · 上：把字节变成可靠事件

> 对应答案：[02-streaming.md](../02-streaming.md) 第 1、3 题。下篇才处理 Markdown 和半截 JSON。

上一章的 `StreamEvent` 假设你已经拿到一条完整事件。网上到的是字节，可能断在一个汉字中间，也可能断线之后服务端还在生成。这一章按到达的顺序讲：先拼成帧，再认出事件，再用序号接上，最后才把一轮里的多个片段分开存。

四个词后面会反复用。字节是原始数据。帧是按协议切出来的一条完整消息，SSE 里用空行结尾。事件是帧里写明的类型。片段是业务上的一块内容，比如一段正文、一次工具记录、一张表。

## 半行留下，空行才算一条帧

SSE（服务器单向推文本事件）里，一条事件长这样，空行表示结束：

```
id: 3
event: response.output_text.delta
data: {"delta":"你"}
<空行>
```

一次 `read()` 不一定读到空行。UTF-8 里一个汉字常常占 3 个字节，两次读取可能把它拆开。每次都把字节直接当文本解码，拆开的那半会变成乱码，而且补不回来。

`TextDecoder` 的 `{ stream: true }` 把没凑齐的字节留到下一次。应用自己还要把没遇到空行的半行文本留在缓冲区里：

```ts
buffer += decoder.decode(chunk, { stream: true });
const frames = buffer.split('\n\n');
buffer = frames.pop() ?? '';
```

换行要兼容 `\r\n`，上面为了短，只按 `\n` 示意。同一条事件里可以有多行 `data:`，拼回正文时用换行连起来。最后一段在空行出现之前不能解析。

如果按「这次 read 到的字符串」去 `JSON.parse`，半包必然失败，拆成两次 read 的事件又会漏字段。先组帧，传输怎么切和这条消息是什么意思就分开了。

## 帧有了，再按事件名决定它是增量、结束还是报错

早期 OpenAI Chat Completions 用 `data: [DONE]` 表示结束。2025 年 3 月的 Responses API，以及 Anthropic Messages API，改成在 `event:` 行写事件名，`data:` 里放 JSON。客户端认事件名，不在正文里找标记。

`response.output_text.delta` 是一小段新文字，追加到当前片段。`response.completed` 和 `message_stop` 表示这次生成正常结束，然后关连接、清监听。`error` 是服务端或模型报错，显示错误，保留已收到的文字。不认识的名字是协议以后新加的，记一笔就行，不要因此中断。

正文里完全可能出现 `[DONE]` 这几个字。拿它当结束，会把一句普通的话截断。新接口根本不发这个标记。

三种失败的下一步不同，所以不能合成一句「出错了」。网络断开、又没收到结束事件，回答是不完整的，要重试或重新拉取。JSON 解析失败，是这条帧坏了。`error` 事件是业务失败，提示原因，已有文字留着。连接关掉时如果从来没走过完成，就标成未完成。

## 事件能认了，断线之后靠序号知道接到哪

服务端为一次生成分配 `runId`，为每条增量分配递增序号，写进 SSE 的 `id:` 行。

浏览器原生 `EventSource` 重连时会带上 `Last-Event-ID`，表示「我最后看到的 id」。这只是客户端的声明。服务端自己留着可补发的事件，才能从那个 id 之后接着发。客户端单靠序号，找不回已经丢掉、而服务端又没留底的内容。

收到之后仍要自己看。序号小于等于已处理的最大序号，丢掉。重连常常把最后一条再送一遍。序号正好是已处理加 1，按顺序用。序号跳了，中间丢了，补读或整份重拉，不能干等。

断线前处理过 1、2。重连收到 2、3：丢掉 2，接上 3。如果直接收到 4，说明 3 没了。

重连接的是这条流，不是再提交一次生成。用户点停止，要另外发取消。两件事混在一起，断线一次就会把任务停掉，或者把同一段话生成两遍。

## 一条回复里有多块内容时，再给每块一个身份

上面的序号管的是「这一次生成的第几条事件」。一轮回答里可能同时有正文、工具记录和表格。网络包谁先到，不一定是页面上的顺序。不同块的文字也不能拼进同一条消息。

所以在 `runId` 下面再加两层。`partId` 区分正文、代码或表格。片段内序号区分这一块里的第几段增量。同一 `partId` 按序号追加，重复序号丢掉。不同 `partId` 分开存。显示顺序另记一份。

缺号时，协议允许补发就补发；不允许就重新读完整状态。不能无限等一个不来的序号。

工具参数如果是 JSON，没收全之前只缓存。半截能不能拿去执行，下篇再说。这里先记住：没收全就不要跑。

上游还有两种发法，接法相反。增量只有新的一小段，按序号接在后面。快照是整条内容的最新版，用新版本换掉旧记录。快照再拼接，文字会重复。增量当成整段替换，文字会丢。

## Moose 里实际是这样

只对得上 [答案](../02-streaming.md) 第 1、3 题。

- Web 用原生 `EventSource` 订阅 `/api/events`（`src/lib/web-api.ts`）。服务端 `electron/web-server.ts` 只写 `data:` 行，内容是 JSON 业务事件，不写 `event:` 和 `id:`，也不用 `[DONE]`。
- 断线后浏览器会自动重连。连接恢复时，页面重新拉取快照，再按消息 ID 和 `seq` 只接受较新的版本。服务端不会按 `Last-Event-ID` 补发每一条增量。
- 和 CLI 之间，`electron/providers/rpc.ts` 先按换行拆出完整 JSON，再分成响应、通知和审批请求。
- 消息 ID 用 `runId:event.key` 生成。同一条记录更新时 `seq` 递增。页面按 ID 和 `seq` 合并，再按 `position` 排序。收到同一条的 `seq=6` 和 `seq=8` 时保留 8。推给页面的是整条消息的新版本，所以是**替换旧记录**，不是把两份正文拼起来。

上面讲的 `event:`、`id:`、按 `Last-Event-ID` 补发，是通用客户端的做法。Moose 的 Web 事件流没有这三样。
