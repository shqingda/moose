# 二、流式处理与实时通信 · 上

> 题单，对着说。每题顺序固定：这题在考什么 → 一句话回答 → 展开说明 → 示例 → Moose 里的做法 → 容易答错的地方。对应 [答案](../02-streaming.md) 第 1、3 题。下篇是 Markdown、渲染优先级和半截 JSON。事实按 Moose 0.23.3。答题稿里写了「没有」的，不要说成已经做了。

## 1. 请设计一个 SSE 客户端：能断线重连、消息去重，并按事件类型识别“生成完成”和“出错”。

*（合并了原第 1、8 题）*

> **这题在考什么**：网络断开时，服务端可能还在继续生成。重连后把已收到的文字再拼一遍，回答会重复；漏掉一段，回答会缺字。另外，“一次读到的数据”不等于“一条完整事件”，结束和报错也不能靠在正文里搜字符串判断。面试官想看你能否把组帧、按类型分发、续接三件事分开做对。

**一句话回答**：先按 SSE 规则把字节流组装成完整事件，再按事件类型分发；每条增量带序号，重连时用 `Last-Event-ID` 或序号续接并丢弃重复；只有收到明确的结束事件才算完成，连接断了却没收到它，就按“不完整”处理。

**展开说明**
- **组帧**：用流式 `TextDecoder` 解码，`{ stream: true }` 保证一个汉字的字节被拆到两次读取时不会变成乱码。保留没读完的半行，遇到空行才算一条事件结束；同一事件里的多行 `data:` 用换行合并；换行符要兼容 `\r\n`。
- **按类型分发**：`data: [DONE]` 是早期 OpenAI Chat Completions 接口的约定。OpenAI Responses API（2025 年 3 月发布）和 Anthropic Messages API 改用带类型的 SSE 事件，用 `event:` 行写明事件名，`data:` 里是 JSON。客户端应该按事件名分发，而不是解析正文内容。

| 事件 | 含义 | 客户端动作 |
| --- | --- | --- |
| `response.output_text.delta`（OpenAI） | 一小段新文字 | 追加到当前片段 |
| `response.completed`（OpenAI）、`message_stop`（Anthropic） | 本次生成正常结束 | 标记完成，关闭连接，清理监听 |
| `error` | 服务端或模型报错 | 显示错误，保留已收到的文字 |
| 不认识的事件名 | 新版本协议加的类型 | 忽略并记录，不要报错中断 |

- **不完整的流**：连接断开、但没收到结束事件，说明回答可能缺了一截。要标成“未完成”，提示重试或重新拉取，不能当作正常结束。网络断开、解析失败、模型报错三种情况要分开提示。
- **续接与去重**：服务端为一次生成分配 `runId`，为增量分配递增序号，并写进 SSE 的 `id:` 行。原生 `EventSource` 重连时会自动带上请求头 `Last-Event-ID`，告诉服务端“我收到哪里了”。客户端仍要检查：序号小于等于已处理的就丢弃，跳号就说明中间丢了，要补读或重新拉取完整结果。
- 举例：断线前已处理 1、2；重连后收到 2、3，丢掉重复的 2，接上 3。如果直接收到 4，说明 3 丢了。

**示例**：下面演示组帧、按事件名分发和序号去重（解析示意，以 `\n` 为换行符）。

```ts
buffer += decoder.decode(chunk, { stream: true }); // 新数据接到缓冲区后面
const frames = buffer.split('\n\n');               // 空行分隔完整事件
buffer = frames.pop() ?? '';                        // 最后一段可能不完整，留到下次
for (const frame of frames) {
  const { event, id, data } = parseFrame(frame);    // 多行 data: 在这里合并
  if (id && Number(id) <= lastSeq) continue;        // 重连后收到的重复事件
  if (event === 'response.output_text.delta') append(JSON.parse(data).delta);
  else if (event === 'response.completed') finish(); // 只有它才代表正常结束
  else if (event === 'error') fail(JSON.parse(data));
  if (id) lastSeq = Number(id);
}
// 连接关闭时如果还没调用过 finish()，就标记为“未完成”
```

**Moose 里的做法**：Moose 的 Web 页面用原生 `EventSource` 订阅 `/api/events`（`src/lib/web-api.ts`），服务端（`electron/web-server.ts`）只写 `data:` 行，内容是 JSON 业务事件，不写 `event:` 和 `id:`，也不用 `[DONE]`。断线后浏览器自动重连，连接恢复时页面重新拉取快照，再按消息 ID 和 `seq` 只接受较新的版本；服务端不会按 `Last-Event-ID` 补发每条增量。和 CLI 之间则是 `electron/providers/rpc.ts` 先按换行拆出完整的 JSON，再分发成响应、通知和审批请求。

**容易答错的地方**
- 不能在正文里搜到 `[DONE]` 就当作结束，正文完全可能出现这几个字符；新接口也根本不发它。
- 服务端必须保存可补发的事件，否则客户端单靠序号也找不回遗漏的内容。
- 不要把重连当成重新提交生成任务。用户主动停止时，要另外发取消请求。

## 3. 当 AI 流式返回的数据包含多个独立片段（如文本、代码、表格）时，如何设计 Chunk 合并算法以保证片段完整性？

> **这题在考什么**：一轮回答可能同时产生正文、工具记录和表格。网络包到达的顺序不一定是页面应该显示的顺序，不同内容的文字也不能拼进同一条消息。面试官想看你怎样给片段编身份、决定追加还是替换。

**一句话回答**：给每个片段一个唯一身份和片段内序号，同一片段按序合并、不同片段分开保存，显示顺序单独记录，不依赖网络到达顺序。

**展开说明**
- 先给片段身份：同一轮用 `runId`，每个文本、代码或表格片段用 `partId`，片段内再用序号。
- 相同片段按序号追加，不同片段分别保存，重复发来的序号直接丢弃。
- 发现缺号时，如果协议支持补发就请求补发；不支持就重新读取完整状态，不能无限等待。
- 显示顺序单独记录，不能拿网络到达顺序代替。
- 工具参数这类结构化内容没收全时先缓存，不能拿半截 JSON 去执行。

上游发来的数据形态不同，合并方式也不同：

| 上游发来的是 | 合并方式 |
| --- | --- |
| 增量（只有新增的一小段） | 按序号追加到同一片段 |
| 完整快照（整条内容的最新版本） | 用新版本替换旧内容，不再追加 |

**示例**：下面是 Moose 按整条消息版本合并的关键代码（简化自 `src/lib/transcript-messages.ts`）。

```ts
const old = result[index];
if (old && old.seq >= message.seq) continue; // 旧版本或重复版本，跳过
result[index] = message;                     // 用新版本替换整条记录
// 只有位置真的变化时才按 position 重新排序，而不是按事件到达顺序
```

**Moose 里的做法**：Moose 用 `runId:event.key` 生成消息 ID，同一条记录更新时递增 `seq`；页面按 ID 和 `seq` 合并，再按 `position` 排序。如果收到同一条消息的旧版本 `seq=6` 和新版本 `seq=8`，就保留 8。它传给页面的是整条消息的新版本，所以是**替换旧记录**，不是把两份正文拼起来。
