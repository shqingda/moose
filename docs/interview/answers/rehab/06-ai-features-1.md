# 六、Agent 与成本 · 上：循环在哪转，Token 花在哪

> 对应答案：[06-ai-features.md](../06-ai-features.md) 第 1、3、9 题。下篇讲 Markdown 安全和审批。

## Agent 循环是一轮一轮的判断

用户说「修这个报错」。模型先要读文件，看见内容才决定怎么改，改完可能再跑一次命令。这种往复才叫 Agent 循环：模型给出下一步，可信的一方执行工具，结果交回模型，模型再判断，直到完成或碰到上限。

页面适合把每一步画出来，收集用户的批准或拒绝，发出取消。页面不适合直接执行模型给出的 Shell 或数据库命令。浏览器里的代码用户可以改，命令和凭据放在那里，就等于放在用户能篡改的环境里。执行循环的应是可信后台。

每次任务一个 `runId`，每次工具调用一个 `callId`。结果靠这个 ID 回到原来那次调用。一轮里如果有两个并行的读，必须各记各的结果：一个成功、一个超时，就同时留下「文件内容」和「超时」。只留最后完成的那项，另一项就丢了。

互不依赖的读取可以并行。写入，或要用上一步的结果，按顺序来。

断线之后，有副作用的调用可能已经执行，也可能没有。这种「结果未知」不能盲目重跑，否则写文件、发请求会做第二次。下篇审批里会把「明确拒绝」和「结果未知」再分开。

超时必须通知到工具本身：

```ts
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 10_000);
try {
  return await tool.run(args, { signal: controller.signal });
} finally {
  clearTimeout(timer);
}
```

`AbortController` 发出的是信号。工具要去听 `signal`，自己停下来。如果工具没有这个参数，就要调它专门的停止接口。

`Promise.race` 只是让你这边不再 `await`。底层进程还在跑。超时如果只写了 race，页面以为停了，命令仍可能改完文件。

**补充知识：** `setTimeout` 到点后调用 `abort()`，`finally` 里清掉定时器，是为了成功提前返回时不要留下一个还会响的计时器。计时器要清掉，和业务上的「10 秒」是两件不同的事。

## Token 是模型读到和生成的量

Token 是模型实际读取或生成的内容单位。压缩图片、懒加载路由，让网页下载变小、首屏变快，发给模型的提示词一个字都没少。

| 手段 | 会不会少花 Token | 原因 |
| --- | --- | --- |
| 压缩图片、懒加载页面 | 不会 | 只影响网页下载 |
| 去掉重复的上下文 | 会 | 同样的内容不再送第二次 |
| 只引用相关文件片段 | 会 | 不把整份文件塞进去 |
| 压缩过长的历史 | 会 | 旧对话变短 |
| 限制不必要的输出 | 会 | 生成的内容也算 Token |
| 缓存相同请求 | 会，但有前提 | 请求必须完全相同，而且这次结果允许被下一次复用 |

带了「当前时间」或用户刚改过的文件，看起来像同一句问话，内容已经不同，复用就会答错。

## 上下文窗口是一次能看见的预算

模型一次能看的长度有上限，叫上下文窗口。对话变长以后，不能把最旧的消息一刀切掉。切掉的可能是早先定下的约束，或某次工具的结果。模型会在缺少前提的情况下继续改。

先分预算，再谈压缩。下面的数字只说明分法，不是任何产品的固定配额。例如总预算 8000 token，可以给必需指令 1000，最近对话 3000，相关文件 2000，留给输出 2000。

快要超限时，先去掉重复材料，或只取相关片段。再把较早的历史收成摘要。工具调用和它的结果成对留下。摘要写明已经做出的决定、约束、未完成事项。原文仍留着可核对，因为摘要会漏。

只留下工具调用、丢掉结果，模型不知道那次调用发生了什么。只留下结果、丢掉调用，模型不知道这个结果对应哪一步。所以成对保留。

滑动窗口、抽取关键信息、自动摘要，是三种不同的取舍。窗口是按远近丢掉旧的。抽取是按相关性留下。摘要是用更短的文本代替原文，并接受细节损失。预算分配决定你先用哪一种。

## 容易答错的地方

展示、审批、取消在前端。选工具、跑命令在可信的一侧。

`Promise.race` 只是不再等待。`abort` 或专门的停止接口才是已经停下。

懒加载不减少 Token。少送重复上下文才减少。

摘要进窗口，原文留下核对。不能只留摘要就当历史还在。

## Moose 里实际是这样

以下只对得上 [答案](../06-ai-features.md) 第 1、3、9 题。

- 工具由代理 CLI 决定并执行。Service 保存工具记录，把审批关联到当前 `runId` 和待处理消息。停止时取消任务并关闭适配器。
- 用户把任务交给 Moose，Moose 交给 CLI，CLI 调用工具。工具记录回到 Moose 再展示。需要审批时，用户的选择由 Moose 转给 CLI。审批只在代理提出请求时发生。
- 可以选择文件引用，并显示底座给出的上下文用量。没有自行完成整套 token 裁剪和费用结算。
- 主要恢复底座的原生会话，上下文压缩由底座处理。不要说成 Moose 自己实现了自动摘要。
- 上面 8000 token 的分配是说明分法的例子，不是 Moose 的配额。

`AbortController` 那段是「如果自己实现工具执行」的示意，不是 Moose 的工具运行代码。

## 上篇先记住

循环放在能保管凭据、用户改不了的那一侧。页面负责看见、批准和取消。每次调用单独编号，读可以并行，写要按顺序，超时要真正传到工具。

Token 只跟送进模型和模型写出的内容有关。上下文先给指令、近况、材料和输出预留分预算。超限时先去重、再摘要，工具调用和结果要成对留。

Moose 把执行交给 CLI，自己记记录和审批。用量只显示底座给的数字，压缩也在底座。
