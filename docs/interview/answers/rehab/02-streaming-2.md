# 二、流式 · 下：帧已经是正文了，语法还没写完

> 承接 [上篇](02-streaming-1.md)。对应答案第 2、5、9 题。

上篇停在「一条事件已经完整」。事件里的正文仍可能是没闭合的 Markdown，或者没写完的 JSON。页面如果按完整文档去处理，中间态会一直报错。这一篇接在事件之后：先说正文怎么显示，再说显示太贵时谁该让路，最后说 JSON 中途能给人看、不能拿去做事。

## 先把字攒成当前全文，再按间隔看语法

Markdown 要看到后面的字符，才知道前面几个字符是什么。两个反引号到了，第三个还没来，你不知道这是不是代码块。每来一个字就按完整文档解析，未闭合的代码会被当成普通段落，或者一直报语法错误。

所以上篇的增量先累积成当前全文。按帧，或按一个短间隔，解析这一份全文。没闭合的语法先按「还没写完」显示。生成结束后再完整解析一次。

不要每个字都解析。解析的是整段越来越长的原文，次数如果跟字数一样多，主线程会被占满。

代码块还没收到结束标记，就先把后面的内容当代码显示。结束标记到了，它自然变成普通代码块。这是临时的显示，不是去猜最终文档。

长文本可以缓存已经稳定的前几块，只重新解析尾部。迟来的结束标记可能让前文从「代码」变回「段落」。缓存要允许这个判断被收回。

## 解析已经按间隔做了，输入仍可能被剩下的工作堵住

浏览器里，跑 JavaScript、响应用户输入、把页面画出来，大多挤在同一条主线程上。一段同步代码跑 200 毫秒，这 200 毫秒里打字和点击都要等。

流式回答会不断重新解析、重新渲染。用户这时还要打字、点停止。所以在「少解析」之后，还要分清哪些更新必须马上看见。

`useDeferredValue` 拿一个值，让昂贵的子树先用旧值，空闲时再追上。它适合长回答的 Markdown，不适合输入框自己的文字。`useTransition` 把一次状态更新标成不紧急，可以读 `isPending`。它适合切视图、过滤大列表，同样不适合输入框。

```tsx
const deferredText = useDeferredValue(streamedText);
return <MarkdownView source={deferredText} />;
```

输入框如果也放进 transition，每个按键都变成「可以稍后」，打字会迟。停止按钮必须马上有反应。

这两个 Hook 只改谁先画。它们不会把同步跑 200 毫秒的解析变成异步。解析太重时，还是要减少次数、缓存稳定的块，或把解析放进 Worker（浏览器的后台线程）。

这几样减的东西不同，所以不能互相替代。把多次增量合成一次通知，减的是渲染被触发的次数。`memo` 并且消息对象引用不变，减的是没变化的那一行还要不要重画。`useDeferredValue` 决定输入和昂贵渲染谁先占用这一帧。Worker 决定解析是不是堵在主线程上。下一章的性能会把 `memo` 和引用接上。这里先记住：让路救不了解析本身。

## 正文如果是 JSON，中途的对象只供显示

结构化输出是给模型一份 JSON Schema，要求结果符合这份结构，例如标题、步骤、风险等级。JSON 模式更弱，只保证输出是合法 JSON，不保证字段齐全。

上篇说工具参数没收全就不要执行。原因就在这里：流式过程中你拿到的是没写完的文本，比如 `{"title":"修复登录","steps":["检查`。少了引号和括号，`JSON.parse` 一定失败。每来一段就对全文 `JSON.parse`，只会一直抛错。

提前给人看，有三种做法。容错解析暂时补上缺的引号和括号，得到「到目前为止」的对象。最后一个字段还可能变，`12` 后面可能再来 `3`。只展示后面已经出现逗号或右括号的字段，更稳，进度也更晚才出现。整段等到结束再解析，最简单，中间没有进度。

显示和使用分开。增量到达时，只为了画面做容错解析。流结束之后，再 `JSON.parse` 全文，用 Zod 或同一份 schema 校验。通过了才保存、才触发下一步。失败就提示或重试，不要猜一个结果。

```ts
const Plan = z.object({
  title: z.string(),
  steps: z.array(z.string()),
});

onDelta((text) => {
  raw += text;
  render(parsePartialJson(raw));
});

onDone(() => {
  const result = Plan.safeParse(JSON.parse(raw));
  if (!result.success) return showError(result.error);
  apply(result.data);
});
```

`parsePartialJson` 代表任意容错解析器，不是某份标准库。局部对象会被后面的字节改写，所以不能写入数据库，也不能触发副作用。

工具参数也是一段段来的。OpenAI Responses API 用 `response.function_call_arguments.delta` 送参数片段，最后才有完整参数。半截可以显示「正在准备调用某工具」，不能拿去执行命令或写文件。

结构化输出仍可能因为拒答或截断而不完整。JSON 模式只保证语法。两种都要在结束时再校验。

## Moose 里实际是这样

只对得上 [答案](../02-streaming.md) 第 2、5、9 题。

- 后台每 80 ms 批量保存并推送有变化的消息。前端用 `react-markdown` 渲染当前全文，没有增量 AST 解析器。渲染组件的类型保持稳定，文字增量到来时不会卸载已有的代码块，也不会重新读取本地图片。
- 减轻渲染压力靠批量推送、消息级 `memo` 和分页。没有使用 `useDeferredValue` 和 `useTransition`。
- Moose 不直接调用模型 API 做结构化输出，而是通过标准输入输出和 Agent CLI 通信。
- `electron/providers/rpc.ts` 把输出攒进缓冲区，遇到换行才 `JSON.parse` 一整行，不解析半行。解析失败就报协议错误并关闭连接。缓冲区超过 16 MiB 会中止。解析后用 `record`、`string` 等辅助函数逐个字段收窄类型。
- 以 Codex 为例（`electron/providers/codex.ts`），正文、推理和命令输出按 delta 增量追加。MCP 工具调用的参数取自完整条目，不按片段拼接。
- Zod 主要用于校验页面发来的请求参数（`shared/validation.ts` 的 `validate`），没有对每条 CLI 输出做 schema 校验。

「容错解析半截 JSON 再给页面看进度」是通用讲法。Moose 对 CLI 的规则是凑成一整行再解析，半行不解析。
