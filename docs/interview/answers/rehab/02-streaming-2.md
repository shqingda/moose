# 二、流式 · 下：不完整的内容怎么显示

> 承接 [上篇](02-streaming-1.md)。对应答案第 2、5、9 题。
> 读完要能讲清：Markdown 为什么不能逐字定稿；延后渲染和「把解析变快」是两回事；半截 JSON 为什么可以展示、不能拿去执行。

## 1. 流式 Markdown：语法经常还没写完

Markdown 要看到后续字符，才知道前面几个字符是什么。两个反引号到了，第三个还没来，你不知道这是不是代码块的开头。如果每来一个字就按「已经完整的文档」解析，中间态会不断报语法错误，或者把未闭合的代码当成普通段落。

做法是把三件事分开：

```
增量先累积成当前全文
  → 按帧，或按一个短间隔，解析这一份全文
  → 没闭合的语法先按「还没写完」显示
  → 生成结束后，再完整解析一次
```

不要每收到一个字就解析一次。解析的是整段当前原文，调用次数如果跟字数一样多，主线程会被占满。按帧或固定短间隔合并，算的是同一份越来越长的文本，但次数少得多。

未闭合时给一个临时解释。代码块还没收到结束标记，就先把后面的内容当代码显示；结束标记到了，它自然变成普通代码块。这是显示策略，不是去猜最终文档。

长文本可以缓存已经稳定的前几块，只重新解析尾部。这里有个坑：后面的标记可能改写前面的含义。例如迟来的结束标记让前文从「代码」变回「段落」。缓存要允许尾部影响被收回，不能假设前面永远定稿。

**和上篇组帧的差别：** 组帧解决的是「字节还没构成一条协议消息」。这里解决的是「协议消息已经是正文了，但 Markdown 语法还没闭合」。两层都会看到半成品，处理的位置不同。

## 2. 主线程一次只能认真做一件事

**补充知识：** 浏览器里，跑 JavaScript、响应用户输入、把页面画出来，大多挤在同一条主线程上。一段同步代码跑 200 毫秒，这 200 毫秒里输入和点击都要等。

流式回答会不断触发重新解析和重新渲染。用户这时还要打字、点停止。所以要先分清哪些更新必须马上看见，哪些可以晚一点。

| | `useDeferredValue` | `useTransition` |
| --- | --- | --- |
| 你交给它的 | 一个值 | 一次状态更新 |
| 它做的事 | 让昂贵子树先用旧值，空闲时再追上新值 | 把这次更新标成不紧急，并可读 `isPending` |
| 适合 | 长回答的 Markdown | 切视图、过滤大列表 |
| 不适合 | 输入框自己的状态 | 输入框自己的状态 |

```tsx
const deferredText = useDeferredValue(streamedText);
return <MarkdownView source={deferredText} />;
```

输入框如果也放进 transition，每个按键都变成「可以稍后」，打字会迟滞。停止按钮同理，它必须马上有反应。

这两个 Hook 只改**更新谁先画**。它们不会把一段同步跑 200 毫秒的解析变成异步。解析本身太重时，要另做三件事里的一件：减少解析次数、缓存已稳定的块、或把解析放进 Worker（浏览器的后台线程）。

### 和「批量推送」的差别

| 手段 | 减的是什么 |
| --- | --- |
| 服务端或状态层把多次增量合成一次通知 | 渲染被触发的次数 |
| `memo`，且消息对象引用不变 | 没变化的那一行还要不要重渲染 |
| `useDeferredValue` | 紧急输入和昂贵渲染谁先占用这一帧 |
| Worker | 解析代码是否堵在主线程上 |

下一篇性能章会把 `memo` 和引用稳定性讲透。这里先记住：调度优先级救不了解析算法本身。

## 3. 半截 JSON 可以给人看，不能拿去做事

结构化输出：给模型一份 JSON Schema，要求结果符合这份结构，例如「标题 + 步骤列表 + 风险等级」。JSON 模式更弱，只保证输出是合法 JSON，不保证字段齐全、类型对。

流式过程中你拿到的是还没写完的文本：

```json
{"title":"修复登录","steps":["检查
```

少了引号和括号，`JSON.parse` 一定失败。每来一段就对全文 `JSON.parse`，只会一直抛错。

提前展示有三种常见做法：

| 做法 | 思路 | 代价 |
| --- | --- | --- |
| 容错局部解析 | 暂时补上缺的引号和括号，得到「到目前为止」的对象 | 最后一个字段还可能变，`12` 后面可能再来 `3` |
| 只展示已写完的字段 | 字段后面出现逗号或右括号，才认为它定了 | 实现更多，进度更慢才出现 |
| 整段等结束 | 流结束再解析一次 | 最简单，中间没有进度 |

展示和使用必须分开：

```
每段增量到达
  → 只为了画面，做容错解析或摘出已闭合字段
流结束
  → JSON.parse 全文
  → 用 Zod 或同一份 JSON Schema 校验
  → 通过了才保存、才触发下一步
  → 失败就提示或重试，不要猜一个结果
```

```ts
const Plan = z.object({
  title: z.string(),
  steps: z.array(z.string()),
});

onDelta((text) => {
  raw += text;
  render(parsePartialJson(raw)); // 字段可能缺，也可能还在变
});

onDone(() => {
  const result = Plan.safeParse(JSON.parse(raw));
  if (!result.success) return showError(result.error);
  apply(result.data);
});
```

`parsePartialJson` 代表任意容错解析器，不是某份标准库。局部对象随时会被后续字节改写，所以不能写入数据库，也不能触发副作用。

工具参数也是一段段来的。OpenAI Responses API 用 `response.function_call_arguments.delta` 送参数片段，最后才有完整参数。半截参数可以显示「正在准备调用某工具」，不能拿去执行命令或写文件。

结构化输出仍可能因为拒答或截断而不完整，所以结束时的校验省不掉。JSON 模式只保证语法，不保证字段就是你要的结构。

### 和上篇「工具参数先缓存」的关系

上篇说的是合并算法：结构化片段没收全就不要执行。这一节说的是解析算法：没收全时 `JSON.parse` 会失败，容错结果只供显示。两条是同一条纪律的两侧。

## 容易混在一起

**解析次数和渲染优先级。** 少解析，减少主线程工作量。`useDeferredValue` 让剩下的工作给输入让路。两件都要，互相替代不了。

**局部对象和校验后的对象。** 前者是进度画面，后者才是可以保存的结果。

**JSON 模式和结构化输出。** 前者保证「能 parse」，后者要求「符合 schema」。两者都可能被截断，所以都要在结束时再校验。

## Moose 这一章实际落在哪

以下只复述 [答案](../02-streaming.md) 第 2、5、9 题。

- 后台每 80 ms 批量保存并推送有变化的消息。前端用 `react-markdown` 渲染当前全文，没有增量 AST 解析器。它保持渲染组件的类型稳定，文字增量到来时不会卸载已有的代码块，也不会重新读取本地图片。
- 减轻渲染压力靠的是批量推送、消息级 `memo` 和分页。没有使用 `useDeferredValue` 和 `useTransition`。
- Moose 不直接调用模型 API 做结构化输出，而是通过标准输入输出和 Agent CLI 通信。
- `electron/providers/rpc.ts` 把输出攒进缓冲区，遇到换行才 `JSON.parse` 一整行，不解析半行。解析失败就报协议错误并关闭连接。缓冲区超过 16 MiB 会中止。解析后用 `record`、`string` 等辅助函数逐个字段收窄类型。
- 以 Codex 为例（`electron/providers/codex.ts`），正文、推理和命令输出按 delta 增量追加。MCP 工具调用的参数取自完整条目，不按片段拼接。
- Zod 主要用于校验页面发来的请求参数（`shared/validation.ts` 的 `validate`），没有对每条 CLI 输出做 schema 校验。

「容错解析半截 JSON 再给页面看进度」是通用讲法。Moose 对 CLI 的规则是：凑成一整行再解析，半行不解析。

## 本章速记

流式可以看成四层，不要并成一句「边收边渲染」：

```
字节按空行组成帧，按事件名分发
  → 用 runId 和序号去重、发现缺号；断了又没结束事件就是不完整
  → 片段有自己的身份；增量追加，快照整条替换
  → 正文是 Markdown 时，先累积再按间隔解析，未闭合语法临时显示，结束再解析一次
  → 若正文是 JSON，中途只展示，结束并用 schema 校验后才使用
```

渲染跟不上时，先减少解析次数和保持消息引用稳定；`useDeferredValue` / `useTransition` 只是让输入和停止按钮先被处理。它们不存在于 Moose 当前实现里。Moose 的 Web 流不写 SSE 的 `event:` / `id:`，断线后重拉快照，按消息 ID 和 `seq` 留较新版本；和 CLI 之间则是凑齐一行 JSON 再解析。

重连不是重新生成，断开不是取消，半截 JSON 不是结果，快照不能再拼接。
