## 2. 如何在前端实现一个“流式 Markdown 解析器”，在 AI 逐字输出过程中实时渲染标题、列表、代码块，并避免标签截断？

> **这题在考什么**：Markdown 不是收到一个字就能确定格式的。比如刚收到两个反引号时，还不知道第三个会不会来，也就不知道这是不是代码块。面试官想看你怎样处理“语法还没写完”的中间状态，同时不让页面卡顿。

**一句话回答**：先累积原文，按帧或固定短间隔解析当前全文，未闭合的语法暂时按“未完成”显示，生成结束后再完整解析一次。

**展开说明**
- 不要每收到一个字就解析一次。把增量先攒进原文，再按帧或短时间间隔解析，能明显减少计算量。
- 允许语法暂时不完整。例如代码块还没收到结束标记时，先把后面的内容按代码显示，等结束标记到达后自然变成正常代码块。
- 生成结束后再解析一次全文，确保最终结果正确。
- 长文本解析成本高时，可以缓存已经稳定的前面几块，只重新解析尾部。但要处理“后面的语法影响前面”的情况，比如后来出现的结束标记改变了前文的含义。

**Moose 里的做法**：Moose 后台每 80 ms 批量保存并推送有变化的消息。前端用 `react-markdown` 渲染当前全文，没有增量 AST 解析器；但它保持渲染组件的类型稳定，文字增量到来时不会卸载已有的代码块，也不会重新读取本地图片。

## 5. 在 React 18+中，如何用 useTransition 与 useDeferredValue 优化 AI 流式输出的渲染性能，避免主线程阻塞？

> **这题在考什么**：浏览器主要在同一条线程上处理输入、运行 JavaScript 和更新画面。长回答频繁重新解析时，用户打字或点“停止”就会变卡。面试官想看你能否分清哪些更新必须马上显示、哪些可以晚一点。

**一句话回答**：输入框和停止按钮必须立刻响应，长回答的渲染可以稍后更新；`useDeferredValue` 和 `useTransition` 就是用来降低后者优先级的。

**展开说明**

| Hook | 作用 | 适合用在 |
| --- | --- | --- |
| `useDeferredValue` | 让昂贵组件暂时使用旧值，空闲时再追上新值 | 长回答的 Markdown 渲染组件 |
| `useTransition` | 把某次状态更新标记为不紧急 | 切换视图、过滤列表等非紧急更新 |

- 输入框本身的状态不要放进 `useTransition`，否则打字会有延迟。
- 这两个 Hook 只调整更新的先后顺序。如果一段解析代码同步运行 200 ms，它照样会卡住线程，需要另外减少解析次数、缓存结果或放进 Worker（浏览器的后台线程）。

**示例**：下面把长回答渲染和其他更新分开，回答组件读的是“可以延后”的文本。

```tsx
const deferredText = useDeferredValue(streamedText); // 紧急更新优先，这里可以稍后跟上
return <MarkdownView source={deferredText} />;
```

**Moose 里的做法**：Moose 目前靠批量推送、消息级 `memo` 和分页减轻渲染压力，没有使用这两个 Hook。

**容易答错的地方**
- 这两个 Hook 不会让一段同步运行 200 ms 的解析代码自动变快。

## 9. 模型按 JSON Schema 返回结构化输出时，前端怎样在流式过程中边收边解析、边展示？

> **这题在考什么**：很多功能要求模型返回固定结构，比如“标题 + 步骤列表 + 风险等级”。结构化输出（给模型一份 JSON Schema，要求输出必须符合它）或 JSON 模式（只保证输出是合法 JSON）让结果更好解析，但流式传输时，前端在中途拿到的是一段还没写完的 JSON。面试官想看你怎样提前展示，又不拿半截数据去做决定。

**一句话回答**：中途收到的 JSON 不完整，`JSON.parse` 会直接报错；可以用容错的局部 JSON 解析器或只展示已经写完的字段来提前显示，但要等流结束、用 Zod 等 schema 校验通过后才把结果当真，工具调用的参数同理，没收全绝不执行。

**展开说明**
- 半截 JSON 例如 `{"title":"修复登录","steps":["检查`，少了引号和括号，`JSON.parse` 一定失败。每收到一段就重新 `JSON.parse` 全文，只会不停报错。
- 提前展示有几种做法：

| 做法 | 思路 | 代价 |
| --- | --- | --- |
| 容错局部解析器 | 自动补上缺的引号、括号，得到“目前为止”的对象 | 最后一个字段的值可能还在变，比如数字 `12` 后面还会来 `3` |
| 只展示已写完的字段 | 某个字段后面出现了逗号或右括号，才认为它写完了 | 实现稍复杂，展示会慢一点 |
| 整体等结束 | 流结束后一次解析 | 最简单，但看不到中间进度 |

- 展示和使用要分开：中途对象只用来显示进度。流结束后，用 Zod 或同一份 JSON Schema 校验完整对象，通过了才保存、触发后续动作；失败就提示错误或重试，不要“猜”一个结果。
- 工具调用的参数也是逐段流过来的。OpenAI Responses API 用 `response.function_call_arguments.delta` 事件发送参数片段，最后才有完整参数。半截参数可以显示“正在准备调用某工具”，但绝不能拿它执行命令或写文件。

**示例**：中途只展示，结束后先校验再使用（`parsePartialJson` 代表任意容错解析器）。

```ts
const Plan = z.object({ title: z.string(), steps: z.array(z.string()) });

onDelta((text) => {
  raw += text;
  render(parsePartialJson(raw)); // 只用于显示，字段可能缺失或还在变化
});

onDone(() => {
  const result = Plan.safeParse(JSON.parse(raw)); // 完整后才严格解析和校验
  if (!result.success) return showError(result.error);
  apply(result.data); // 校验通过才真正使用
});
```

**Moose 里的做法**：Moose 不直接调用模型 API 做结构化输出，而是通过标准输入输出和 Agent CLI 通信。`electron/providers/rpc.ts` 先把输出攒进缓冲区，遇到换行才 `JSON.parse` 一整行，绝不解析半行；解析失败就报协议错误并关闭连接，缓冲区超过 16 MiB 也会中止。解析后的数据用 `record`、`string` 等辅助函数逐个字段收窄类型。以 Codex 为例（`electron/providers/codex.ts`），正文、推理和命令输出按 delta 增量追加，MCP 工具调用的参数则取自完整的条目，不按片段拼接。Zod 在 Moose 里主要用于校验页面发来的请求参数（`shared/validation.ts` 的 `validate`），并没有对每条 CLI 输出做 schema 校验。

**容易答错的地方**
- JSON 模式只保证语法合法，不保证字段符合你的结构；结构化输出也可能因为拒答或被截断而不完整，所以最终校验不能省。
- 局部解析得到的对象不能写进数据库或触发副作用，它随时可能被后面的数据改写。
