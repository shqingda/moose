# 九、内容、布局与 React · 下：这段内容还是不是原来那一段

> 承接 [上篇](09-ui-react-1.md)。对应原题 27、28、36、37、41、49、50、60。

上篇选的是观察信号：宽度、视口、焦点、指针、元素盒子。信号对了，内容自己仍会弄错身份。预览的文件、划中的字、折叠起来的按钮、分到的宽度、列表里的那一行、Context 里的那份值，都要问「还是不是原来那一个」。这一篇按这个问法往下接。

## 先决定这份 PDF 要不要自己的界面

「预览」可能只是让用户看，也可能要统一的页码、搜索和标注。只是看，用浏览器自带查看器，`iframe` 或新页签就够。代价是各浏览器界面不统一。要自己的页码和标注，再用 PDF.js。代价是开发和维护更重。

需要登录才能下的文件，用受控地址或带凭证的请求去取，不要把长期有效的秘密放进一个谁都能打开的 URL。若用 `URL.createObjectURL` 生成临时地址，关闭预览时调用 `URL.revokeObjectURL`，否则 Blob 会留在内存里。大文件只渲染看得见的页。还要处理跨域、按字节范围下载、缺字体，以及扫描件里没有可选文字。

## 能打开了，划中的字还要在点菜单之前存下来

浏览器用 `window.getSelection()` 得到当前选区，再用 `getRangeAt` 得到 Range。Range 由起点和终点的节点加偏移组成，可以跨多个标签。`collapsed` 为真表示没有选出文字。

在目标区域听 `contextmenu`。有选区、不是折叠的、起点和终点都在目标里，才阻止默认菜单。先把文字和位置存下来。一点菜单，选区可能就没了。菜单放在鼠标处或选区矩形处，并限制在视口内。Escape 能关掉，并提供键盘入口。

```ts
const selection = window.getSelection();
const range = selection?.rangeCount ? selection.getRangeAt(0) : null;
if (!range || range.collapsed || !root.contains(range.commonAncestorContainer)) return;
const selectedText = selection!.toString();
```

`commonAncestorContainer` 是包住整段选区的那个节点。它不在目标根里，说明选区越过了你的区域。

浏览器上的 Range 是当前 DOM 的选区，DOM 一变就会失效。富文本编辑器内部另有文档模型。加粗、评论都改模型，并进入撤销历史，而不是去拼 `innerHTML`。持久标注要保存模型中的位置或文字锚点，内容变化后按锚点重新定位。

这一题的答案没有写 Moose 的划词菜单。不要把它说成项目已有的功能。

## 选区能定位了，收起的那一块不能再被 Tab 进去

划词要的是「字还在」。折叠要的是「看不见的控件不要还能走到」。标题能用键盘操作，收起之后里面的按钮不能再被 Tab 到。

不需要外部状态时，用原生的 `details` 和 `summary`。浏览器自带基本语义和键盘操作。需要「同时只展开一项」，或展开与否由外部状态决定时，用按钮当标题。`aria-expanded` 表示当前是否展开，`aria-controls` 指向那块面板。加动画时尊重 `prefers-reduced-motion`。

## 折叠的是一块区域，点击「外面」要能判断点在不在这块里面

`details` 自己知道开合。自定义弹层的「点外面就关」，要判断点击目标是不是弹窗的后代。任意层后代、包含它自己，写 `b.contains(a)`。严格的后代、不含自己，再加上 `a !== b`。只是直接子节点，看 `a.parentElement === b`。

`contains` 对自身返回 `true`。拿它当「在里面且不是自己」，会把点在容器上的那一下也算成内部。

Shadow DOM 把组件内部的树封装起来，普通的 `contains` 可能看不到影子树里的节点。事件的 `composedPath()` 返回穿过的完整路径，包含影子树内部。这种时候改看路径。Shadow DOM 是组件把内部节点藏在一棵单独的树里，外面的选择器默认进不去。用了 Web Components 时，「点击是否在组件内」会踩到这里。

## 知道点在哪一块了，这块分到的宽度仍不是写死的

点击判断的是包含关系。布局要问的是剩余空间怎么分。Flex 先看每个子项的基础大小，再把多出来的或不够的空间分下去。`flex: 1` 改的是分配规则，不是宽度 100%。

在常用实现里，它等价于 `flex: 1 1 0%`。有多余空间时可以长大，空间不够时可以缩小，从 0 起参与分配，而不是从内容宽度起。几个子项都是 `flex: 1` 时，通常平分可分配空间。父容器只有一份空间，它们是在分这一份，不是每一项都占满父容器。

Flex 子项默认的最小尺寸是内容本身。一长串不换行的文本会把列撑破。横向布局里给 `min-width: 0`，纵向滚动容器给 `min-height: 0`，它才被允许缩到比内容更小，多出来的交给 `overflow` 滚动。上篇的滚动容器如果被内容撑开，补偿 `scrollTop` 也救不了「根本没有内部滚动」。

```css
.sidebar { flex: 0 0 240px; }
.transcript { flex: 1; min-width: 0; overflow: auto; }
```

侧栏不长大、不缩小、基础就是 240px。主区占剩余，并允许被长内容压到比内容更窄，然后在自己内部滚动。

## 宽度分好了，列表重排时状态还会跟错行

`min-width: 0` 让一块能缩。React 列表还要问这一行是不是原来那一行。每轮渲染用 key 把新旧列表对齐。key 相同，就复用那个组件实例和它里面的 state。

用数组下标当 key，在第一行插入一条，原来的第二行变成第三行。React 仍认为「key 为 1 的那一项还是那一项」，于是旧第二行的输入框内容和展开状态会留在新的第二行上。状态跟着下标走，没有跟着消息走。

```tsx
messages.map((message) => <Row key={message.id} message={message} />)
```

用稳定的业务 ID。不要每次渲染都 `key={Math.random()}`。每一项都会被当成新元素，state 丢掉，DOM 也会整表重建。流式更新应当改消息的内容，而不是换成一个新 ID。ID 一变，行就被卸载，里面的展开状态和代码块一起没了。这和流式章保持渲染组件稳定是同一目的。

## 行的身份稳住了，Context 一变，读它的组件仍会一起更新

key 管的是列表项。Context 把数据传给很深的子组件，不用一层层放 props。值变的时候，所有调用了 `useContext` 的组件都会重渲染。这是机制。故障是把高频数据放进一个大家都读的 Context，导致不相关的组件跟着动。上一章说 `memo` 挡不住 Context，原因就在这里：`memo` 比较的是 props，Context 是组件自己订阅的。

输入中的文字和主题、语言，拆成不同 Context。Provider 只包住需要这份数据的子树。传给 Provider 的对象和函数保持引用稳定。父组件每次渲染都写 `value={{ lang }}`，会得到一个新对象。即使用户没换语言，消费者也会更新。还要按字段订阅时，改用带 selector 的 store。

## 语言和主题拆开以后，颜色仍不要写死在组件里

Context 里放的是「现在用哪一套」。组件如果写死色值，换一套就要改很多处。要一起变的不只是背景，还有文字、边框、焦点和图表。

按语义定义变量。`--surface` 是面板背景，`--text` 是正文，而不是 `--gray-900`。根节点切换 `data-theme`，组件只引用变量。保存用户的选择。system 模式用 `prefers-color-scheme` 跟随系统。在页面第一次画出来之前就加上主题，避免先白后黑。同时检查对比度、焦点样式和图表颜色。

```css
:root { --surface: #fff; --text: #111; }
[data-theme='dark'] { --surface: #171717; --text: #eee; }
.panel { background: var(--surface); color: var(--text); }
```

## Moose 里实际是这样

Moose 的 PDF 是认证后的下载和另存，不内嵌渲染器。图片、文本和代码另有受控预览。工具和思考用 `details` / `summary` 折叠。消息区有 `min-height: 0`，时间线的 key 是 `message.id`。流式更新只改内容，不换这条消息的身份。

语言放在 LocaleContext 里，它只管理语言。切换语言时文案跟着更新，这是预期的。主题是 system、light、dark，手动选择优先于系统。

划词菜单没有写在这组答案里，不要说成已实现。
