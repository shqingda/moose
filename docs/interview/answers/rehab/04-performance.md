# 四、性能：先分清慢在哪一层

> 对应答案：[04-performance.md](../04-performance.md)，原题 1、2、9。
> 读完要能讲清：搜索为什么不能先把一万条搬进浏览器；分页、虚拟列表、按需渲染、`content-visibility` 各减哪一种成本；`memo` 和 React Compiler 都依赖「没变的对象还是原来那个」。

## 这章在解决什么问题

消息一多，慢会出在三个完全不同的地方：

```
存储读太多        一万条先被查出来，再在页面里过滤
DOM 太多          一万个节点都参与布局和滚动
单条渲染太贵      只有一条消息，但里面是数万 token 的 Markdown
```

外加一条独立的问题：你怎么证明它真的快。只报一次最快的数字，说明不了大多数时候怎样。

## 1. 搜索发生在存储层，页面只拿一页

工作分成三步：

```
存储按条件找出匹配
  → 页面只画这一页结果
  → 用户点中某一条，再读它附近的历史
```

先把全部历史拉进浏览器再 `filter`，传输、内存和渲染都在为不可见的行付钱。点中之后再读上下文，是因为搜索结果只是「命中在哪」，阅读要的是前后文。

输入时做防抖：停止输入一小段时间再发请求。每次请求带一个递增的代次，响应回来时如果代次已经旧了，丢掉结果。否则慢的旧关键字会覆盖快的新关键字。

### 参数绑定和通配符是两件事

SQL 的 `LIKE '%关键字%'` 里，`%` 和 `_` 是通配符，不是普通字符。

| 做法 | 防住什么 | 没防住什么 |
| --- | --- | --- |
| 绑定参数 | 用户输入被当成 SQL 执行（注入） | 用户输入的 `%` 仍是「匹配任意内容」 |
| 转义 `%`、`_` 和反斜杠 | 这些字符按字面去匹配 | 注入（所以两件都要做） |

只绑定、不转义时，用户搜一个 `%` 可能命中所有行。

### 怎样报延迟

分层记，不要合成一个「搜索耗时」：

| 层 | 包含什么 |
| --- | --- |
| 后台查询 | 存储自己花的时间 |
| 端到端 | 还要加上防抖等待和传输 |
| 页面渲染 | 结果画出来的时间 |
| 交互是否还在 | 搜索期间终端或输入是否还能响应 |

P95 表示把样本按耗时排序后，大约 95% 的查询不超过这个值。最快的那一次只能说明下限附近发生过，不能代表常见的慢。

**补充知识：** 平均值会被少数极快或极慢的样本拉偏。分位数回答的是「大多数次是不是够快」。

## 2. 少读、少建节点、少做昂贵绘制

三条手段解决的层不同，可以叠在一起，不是三选一。

| 方案 | 解决 | 做法 | 代价 |
| --- | --- | --- | --- |
| 分页 | 一次从存储读太多 | 按游标分批 | 往上插旧消息后，要保住当前阅读位置 |
| 虚拟列表 | DOM 节点太多 | 只挂载可视区及前后少量，其余用高度占位 | 测高、定位、查找、无障碍都变复杂 |
| 按需渲染 | 远处那条渲染太贵 | 看得见的用完整 Markdown，远处先用纯文本或占位 | 切过来时可能闪、可能变高 |
| `content-visibility: auto` | 离屏布局和绘制太贵 | DOM 还在，浏览器跳过离屏布局和绘制 | 节点仍占内存；要给预估高度，否则滚动条乱跳 |

虚拟列表的直觉：一万条、屏幕大约二十条，就只为这二十条和附近几条创建 DOM，滚走再换。占位高度如果和真实高度不一致，滚动会跳。正在生成的消息高度还在变，所以要能重新测量。

虚拟列表会把离屏消息从 DOM 里拿掉。浏览器自带的页内查找（Cmd+F）就搜不到它们，键盘焦点也可能丢。这些要另外做。消息数量不大时，这套复杂度往往比省下的渲染更贵。先用性能数据确认瓶颈在 DOM 数量，再上虚拟列表。

按需渲染改的是**显示方式**，数据层仍保存完整原文。接近视口时提前渲染，避免用户看见闪一下。切换显示时消息的身份不能变，滚动位置也不能跳。

`content-visibility` 是更轻的一档：节点还在，只是离屏时不做布局和绘制。

```css
.message-item {
  content-visibility: auto;
  contain-intrinsic-size: auto 10rem;
}
```

`contain-intrinsic-size: auto 10rem` 的意思是：还没渲染过时按 10rem 估高；渲染过就记住真实高度。没有这个估计，浏览器不知道离屏内容有多高，滚动条长度会错。

向上加载旧消息时，保持用户正在看的那一行不动（状态章和场景题里会写怎么补偿 `scrollTop`）。跳转到某一条时，先按记录读它附近的内容，再滚过去。不要先滚到一个还没加载的空洞。

### 游标分页和页码

**补充知识（答案用了游标，没展开页码的失败方式）：** 页码假设「第 3 页永远是原来那些行」。中间插入或删除后，页的边界会漂。游标记住「从哪一条之后继续」，不依赖中间的总数。Moose 的搜索和历史上翻用的都是这种「从一条记录接着读」的方式，具体字段见下面的 Moose 节。

## 3. 跳过重渲染的前提：没变的还是同一个对象

流式时往往只有最后一条在变。前面几百条不该每次都重新执行组件函数。

`React.memo` 包住组件后，props 和上次比起来一样，就跳过这次渲染。`useMemo` 缓存一次计算的结果，`useCallback` 缓存一个函数的引用。三者都是「输入没变就用上次的结果」。

React Compiler（稳定版在 2025 年 10 月）是构建插件 `babel-plugin-react-compiler`。它在编译时分析组件，在合适的位置自动做上述缓存。

有了编译器，大部分手写缓存可以不写。下面几种仍要手写，或者根本不会被优化：

| 情况 | 原因 |
| --- | --- |
| 项目没开编译器 | 没有自动缓存 |
| 组件违反 React 规则，例如渲染期间改外部变量、改 props | 编译器认为不安全，跳过这个组件 |
| Effect 的依赖、外部库要求「同一个函数始终是同一个引用」 | 手写更可控 |
| 很贵的计算，例如解析长 Markdown | 手写 `useMemo` 把缓存边界标出来，方便检查 |

编译器和 `memo` 都只在**输入没变**时生效。如果每次推送都 `messages.map` 出全新对象，每条的引用都变了，两者都会认为全部要重渲染。

```tsx
setMessages((list) => list.map((m) => (m.id === next.id ? next : m)));
const MessageRow = memo(({ message }: { message: Message }) => (
  <article>{message.text}</article>
));
messages.map((m) => <MessageRow key={m.id} message={m} />);
```

`key` 用稳定的消息 ID。优化之前用 React Profiler 看是哪些组件在重复渲染、一次多久。给每个小计算都套缓存，比较和内存本身也有成本。

`memo` 和编译器都挡不住两样变化：这个组件自己的 props 变了，或者它读取的 Context 变了。Context 的细节在场景题下篇。

### 引用稳定从哪来

它不是 `memo` 变出来的，是更新数据时留出来的。流式章的合并如果「只替换变了的那条，其余原样放回」，这里的 `memo` 才有机会跳过。Moose 的 `mergeMessages` 就是这条链上的数据层。

## 容易混在一起

**搜索 SQL 和历史分页 SQL。** 一个找匹配，一个按顺序翻更早的消息。能翻页不等于能搜索。

**P95 和最好的一次。** 报数字时说清样本、条件和包含了哪些等待（例如防抖算不算进去）。

**分页和虚拟列表。** 前者管读多少条，后者管挂多少 DOM。

**`content-visibility` 和虚拟列表。** 前者节点还在、跳过离屏布局；后者节点被卸掉。页内查找因此表现不同。

**编译器、`memo`、不可变更新。** 前两个是跳过渲染的机制，第三个是它们能跳过的前提。

## Moose 这一章实际落在哪

以下只复述 [答案](../04-performance.md)。

搜索：

- 已实现消息内容搜索。项目名、会话标题、已保存消息的标题和正文都可以匹配，也包含归档会话。用参数化的 `LIKE` 子串查询，没有全文索引。
- 搜索每页 50 条，用排序字段组成游标继续加载。输入防抖 200 ms，过期请求的结果会丢弃。点击结果后按消息的 `position` 读上下文。
- 普通历史向前翻是另一套逻辑，每页 80 条。
- 0.21.0 的本机基准：一万条约 1 KiB 的消息，后端 P95 约 33 ms。0.21.1 的回归测试继续检查 300 ms 预算。这个数字不包含 200 ms 防抖，也不是大数据量下的普遍保证。
- 如果以后扫描拖慢后台，再评估全文索引和中文检索。限制见项目搜索链路文档，教程不另加结论。

长列表：

- 没有虚拟列表，也没有「远处消息改用纯文本」的按需渲染。
- 历史按 `position` 游标分页，每页 80 条，点击「加载更早消息」才读上一页（`electron/db/store.ts`、`src/lib/workspace.ts`）。
- 每条消息外层的 `MessageScrollerItem` 使用 `content-visibility: auto` 和 `contain-intrinsic-size: auto 10rem`（`src/components/ui/message-scroller.tsx`）。
- `TranscriptRow` 用 `memo` 包裹（`src/components/transcript.tsx`）。
- 从搜索结果跳转时，按目标 `position` 读附近内容，再滚动到它。

编译器与引用：

- 没有开 React Compiler：`vite.config.ts` 里的 `@vitejs/plugin-react` 没有配置编译器插件，`package.json` 里也没有 `babel-plugin-react-compiler`。缓存是手写的。
- `src/lib/transcript-messages.ts` 的 `mergeMessages`：旧版本或重复版本直接跳过，只替换真正变化的记录，其他记录保留原对象。
- 传给行的 `onError`、`onEdit` 分别由 `src/lib/workspace.ts` 和 `src/app.tsx` 用 `useCallback` 固定。文件上下文在 `src/components/file-preview.tsx` 里用 `useMemo` 生成。翻译函数是模块级常量。因此一次快照更新不会让所有行的 `memo` 失效。

## 本章速记

慢要先归层：读太多、节点太多、单条绘制太贵、还是主线程被同步解析占住。搜索放在存储里，页面拿一页，点开再读上下文；防抖加上代次，避免旧结果回写。绑定参数防的是注入，转义 `%` 和 `_` 防的是通配符，两件都要。延迟分层测，报 P95，并说明防抖算不算在内。分页减读取，虚拟列表减 DOM，按需渲染减远处的昂贵格式，`content-visibility` 让离屏节点还在但跳过布局。消息不多时，后两种重方案可能比收益贵。无论有没有 React Compiler，只有「没变的消息仍是原来的对象」，`memo` 才跳得过那些行；编译器没开、规则被跳过、或要稳定引用交给外部库时，仍要手写。Moose 的搜索是参数化 `LIKE`、50 条一页、200 ms 防抖；历史是 80 条一页的另一条路径；列表靠分页、`content-visibility` 和手写 `memo`，没有虚拟列表，也没有编译器。
