# 四、性能优化与渲染

> 题单，对着说。每题顺序固定：这题在考什么 → 一句话回答 → 展开说明 → 示例 → Moose 里的做法 → 容易答错的地方。对应 [答案](../04-performance.md)，原题 1、2、9。事实按 Moose 0.23.3。答题稿里写了「没有」的，不要说成已经做了。

## 1. 对话历史达到万条时，怎样做搜索与过滤，并验证实际延迟？

> **这题在考什么**：历史消息多了以后，搜索不能先把一万条都搬进浏览器再过滤。面试官想看你能否把工作分到合适的层，并且用可信的方法测出延迟，而不是只报一个最快值。

**一句话回答**：存储层负责查匹配，页面只显示一页结果，点击后再读取目标消息附近的历史；性能按后台查询、端到端响应和页面渲染分层测，并报 P95。

**展开说明**
- 工作分三步：存储层查出匹配内容，页面展示一页结果，用户点击后再读取目标消息附近的历史。
- 防 SQL 注入和按字面匹配是两个不同问题。绑定参数让输入不会被当成 SQL 执行；转义 `%`、`_` 和反斜杠，才能让这些字符按字面匹配。只做参数绑定的话，用户输入 `%` 仍可能匹配到所有内容。
- 输入时做防抖（停止输入一小段时间后才发请求），并丢弃过期请求的结果，避免旧结果覆盖新结果。
- 性能分层测量：后台查询耗时、包含防抖和传输的响应时间、页面渲染耗时，以及搜索期间终端是否仍然响应。
- P95 表示样本中约 95% 的查询不超过这个耗时。不能只报最快的一次。

**Moose 里的做法**
- Moose 已实现消息内容搜索：项目名、会话标题、已保存消息的标题和正文都可以匹配，也包含归档会话。它用参数化的 `LIKE` 子串查询，没有引入全文索引。
- 搜索每页 50 条，用排序字段组成游标继续加载；输入防抖 200 ms，过期请求的结果会被丢弃。点击结果后，按消息的 `position` 读取上下文。
- 普通历史向前翻页仍是每页 80 条，这是另一套逻辑。
- 0.21.0 的本机基准使用一万条约 1 KiB 的消息，后端 P95 约 33 ms；0.21.1 的回归测试继续检查 300 ms 预算。这个数字不包含 200 ms 防抖，也不是大数据量下的普遍保证。
- 如果数据增长后查询扫描拖慢了后台，再评估全文索引和中文检索方案。源码和限制见[项目搜索链路](../../reference/07-search-notice-preview.md#搜索命中后怎样找到很久以前的消息)。

**容易答错的地方**
- 不能拿历史分页的 SQL 当成搜索实现。
- 参数绑定不等于转义通配符。

## 2. 超长对话和超长 AI 回答怎样做到滚动流畅、定位准确？虚拟列表、按需渲染和分页各解决什么问题？

*（合并了原第 2、5 题）*

> **这题在考什么**：消息越多，页面元素越多，浏览器的布局和滚动负担越重；而且一条数万 Token 的回答即使只算一条消息，Markdown 解析和代码高亮也很昂贵。面试官想看你能否分清“少读数据”“少建 DOM”“少做昂贵渲染”这三层优化，并知道各自的代价。

**一句话回答**：分页控制一次读多少数据，虚拟列表控制页面上有多少 DOM，按需渲染控制远处内容用多贵的方式显示；先用性能数据确认瓶颈在哪一层，再选最简单够用的方案。

**展开说明**

| 方案 | 解决什么 | 做法 | 代价 |
| --- | --- | --- | --- |
| 分页 | 一次从存储读太多数据 | 按游标分批读取 | 要处理“加载更早消息”后的滚动位置 |
| 虚拟列表 | 页面上 DOM 节点太多 | 只挂载可视区域和前后少量内容，其他位置用高度占位 | 高度测量、定位、查找和无障碍都更复杂 |
| 按需渲染 | 远处消息渲染太贵 | 可见的渲染完整 Markdown，远处的先用纯文本或占位 | 切换时可能闪烁或改变高度 |
| CSS `content-visibility: auto` | 离屏内容的布局和绘制太贵 | DOM 还在，浏览器跳过离屏元素的布局和绘制 | 节点仍占内存；要给预估高度，否则滚动条会跳 |

- 虚拟列表举例：一万条消息、屏幕只放得下约二十条，就只为这二十条及附近几条创建 DOM，滚到别处再替换。长消息要按实际高度测量，否则估算高度和真实高度不一致，滚动时会跳。生成中的消息高度还会不断变化，所以要支持重新测量。
- 按需渲染时，数据层照常保存完整原文，只改变显示方式；接近视口时提前渲染，避免用户看到闪烁。切换显示方式不能改变消息身份，也不能让滚动位置跳动。
- 向上加载旧消息时，保持用户当前看到的位置不动。跳转到某条消息时，先按记录读取它附近的内容，再滚动过去。
- 虚拟列表会把离屏消息从 DOM 里移走，浏览器自带的页内查找（Cmd+F）就搜不到它们，键盘焦点也可能丢失，这些都要另外处理。

**示例**：不改列表结构，只用 CSS 让浏览器跳过离屏消息的布局和绘制。

```css
.message-item {
  content-visibility: auto;            /* 离屏时跳过布局和绘制 */
  contain-intrinsic-size: auto 10rem;  /* 没渲染过时按 10rem 估高，渲染过就记住真实高度 */
}
```

**Moose 里的做法**：Moose 没有使用虚拟列表，也没有实现“远处消息改用纯文本”的按需渲染。它做了三件事：历史消息按 `position` 游标分页，每页 80 条，用户点击“加载更早消息”才读上一页（`electron/db/store.ts`、`src/lib/workspace.ts`）；每条消息外层的 `MessageScrollerItem` 带 `content-visibility: auto` 和 `contain-intrinsic-size: auto 10rem`（`src/components/ui/message-scroller.tsx`）；消息行 `TranscriptRow` 用 `memo` 包裹（`src/components/transcript.tsx`）。从搜索结果跳转时，按目标消息的 `position` 读取附近内容，再滚动到它。

**容易答错的地方**
- 分页和虚拟列表不是二选一，前者管读取量，后者管 DOM 数量，可以同时用。
- 消息数量不大时上虚拟列表，多出来的复杂度往往比省下的渲染开销更麻烦。

## 9. 有了 React Compiler，还需要手写 React.memo、useMemo、useCallback 吗？消息列表怎样避免无关重渲染？

> **这题在考什么**：流式输出时往往只有最后一条消息在变，前面几百条不该每次都重新渲染。过去靠手写 `memo`、`useMemo`、`useCallback`；React Compiler 1.0 在 2025 年 10 月发布稳定版后，构建时就能自动做这些缓存。面试官想看你是否知道编译器替你做了什么、没做什么，以及为什么数据引用稳定仍然是前提。

**一句话回答**：开启 React Compiler 后，大部分手写缓存可以省掉；但编译器没开、代码违反 React 规则被跳过、需要给 Effect 或外部库提供稳定引用、需要明确隔开昂贵计算时，仍要手写。无论有没有编译器，更新消息时都要保留未变化消息的对象引用。

**展开说明**
- React Compiler 是一个构建插件（`babel-plugin-react-compiler`），在编译时分析组件，自动缓存组件的渲染结果、计算值和回调，效果相当于在合适的位置自动加了 `memo`、`useMemo`、`useCallback`。
- 仍需要手写的情况：

| 情况 | 原因 |
| --- | --- |
| 项目没开编译器 | 没有任何自动缓存 |
| 组件违反 React 规则（如渲染时修改外部变量、修改 props） | 编译器判断不安全，会跳过这个组件，不做优化 |
| Effect 依赖、外部库要求引用不变 | 需要明确保证“同一个值始终是同一个引用”，手写更可控 |
| 很贵的计算（如解析一段长 Markdown） | 手写 `useMemo` 能清楚标出缓存边界，方便检查 |

- 编译器只能缓存“输入没变”的情况。如果每次推送都把整个消息数组重新生成，每条消息都是新对象，编译器和 `memo` 都会认为全部变了。所以更新一条消息时，要只替换这一条，其他消息保持原对象。
- 消息列表用稳定的消息 ID 作 `key`。优化前先用 React Profiler 查哪些组件在重复渲染、每次耗时多少。

**示例**：只替换变化的那条消息，其他行的引用不变，`memo` 或编译器才能跳过它们。

```tsx
setMessages((list) => list.map((m) => (m.id === next.id ? next : m))); // 未变化的 m 原样保留
const MessageRow = memo(({ message }: { message: Message }) => <article>{message.text}</article>);
messages.map((m) => <MessageRow key={m.id} message={m} />); // key 用稳定 ID
```

**Moose 里的做法**：Moose 没有开启 React Compiler：`vite.config.ts` 里的 `@vitejs/plugin-react` 没有配置编译器插件，`package.json` 里也没有 `babel-plugin-react-compiler`，所以缓存都是手写的。`src/lib/transcript-messages.ts` 的 `mergeMessages` 遇到旧版本或重复版本直接跳过，只替换真正变化的记录，其他记录保留原对象。消息行 `TranscriptRow` 用 `memo` 包裹（`src/components/transcript.tsx`）；传给它的 `onError` 和 `onEdit` 分别由 `src/lib/workspace.ts` 和 `src/app.tsx` 用 `useCallback` 固定，文件上下文在 `src/components/file-preview.tsx` 里用 `useMemo` 生成，翻译函数是模块级常量，因此一次快照更新不会让所有行的 `memo` 失效。

**容易答错的地方**
- 有了编译器也不等于不用关心引用：数据层每次都造新对象，编译器同样救不了。
- `memo` 和编译器都挡不住组件自身 props 或它所用 Context 的变化。
- 不该给每个小计算都手写缓存，缓存本身也有比较和内存开销。
