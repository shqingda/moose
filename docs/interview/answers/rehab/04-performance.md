# 四、性能：引用稳住了，还要看慢在哪一层

> 对应答案：[04-performance.md](../04-performance.md)，原题 1、2、9。

上一章让一条消息变化时，别的消息保持原来的对象。这一章用这个前提往下看慢从哪来。消息一多，慢会出在三个不同的地方：存储一次读太多，页面上节点太多，或者一条消息里的 Markdown 太贵。先归到哪一层，再选手段。只报一次最快的数字，说明不了大多数时候怎样。

## 搜索放在存储里，页面只拿一页

先把一万条搬进浏览器再 `filter`，传输、内存和渲染都在为看不见的行付钱。存储按条件找出匹配，页面只画这一页，用户点中某一条，再读它附近的历史。搜索结果只是「命中在哪」，阅读要的是前后文。

输入时做防抖：停止输入一小段时间再发请求。每次请求带一个递增的代次。响应回来时代次已经旧了，就丢掉。否则慢的旧关键字会盖住快的新关键字。这和前面核对迟到事件是同一类事。

`LIKE '%关键字%'` 里，`%` 和 `_` 是通配符。绑定参数防的是用户输入被当成 SQL 执行。它防不住用户输入的 `%` 仍表示「匹配任意内容」。转义 `%`、`_` 和反斜杠，才能按字面匹配。只绑定、不转义时，搜一个 `%` 可能命中所有行。两件都要做。

延迟要分开记。后台查询是存储自己花的时间。端到端还要加上防抖和传输。页面渲染是结果画出来的时间。另外看搜索期间输入是否还能响应。P95 是把样本按耗时排序后，大约 95% 不超过的那个值。最快的一次只能说明下限附近发生过。平均值会被少数极快或极慢的样本拉偏。

能按顺序翻更早的消息，不等于能搜索。两条 SQL 不是一条。

## 读少了，页面上仍可能节点太多，或单条太贵

分页减的是一次从存储读多少，按游标分批。往上插旧消息后，要保住当前阅读位置。虚拟列表减的是 DOM 节点：只挂载可视区和前后少量，其余用高度占位。代价是测高、定位、页内查找和无障碍都变复杂。按需渲染减的是远处那条有多贵：看得见的用完整 Markdown，远处先用纯文本或占位。切过来时可能闪，也可能变高。`content-visibility: auto` 更轻：节点还在，浏览器跳过离屏布局和绘制。节点仍占内存，还要给预估高度，否则滚动条会乱跳。

这几样可以叠在一起。分页管读多少条，虚拟列表管挂多少 DOM。

一万条、屏幕大约二十条，就只为这二十条和附近几条创建 DOM，滚走再换。占位高度和真实高度不一致，滚动会跳。正在生成的消息高度还在变，所以要能重新测量。虚拟列表会把离屏消息从 DOM 里拿掉，Cmd+F 搜不到它们，键盘焦点也可能丢。消息数量不大时，这套复杂度往往比省下的渲染更贵。先确认瓶颈在节点数量，再上虚拟列表。

按需渲染改的是显示方式，数据层仍保存完整原文。接近视口时提前渲染，避免闪一下。切换时消息的身份不能变，滚动位置也不能跳。

```css
.message-item {
  content-visibility: auto;
  contain-intrinsic-size: auto 10rem;
}
```

`contain-intrinsic-size: auto 10rem` 的意思是：还没渲染过时按 10rem 估高，渲染过就记住真实高度。

页码假设「第 3 页永远是原来那些行」。中间插入或删除后，边界会漂。游标记住「从哪一条之后继续」。向上加载旧消息时，保持用户正在看的那一行不动。跳转到某一条时，先按记录读它附近的内容，再滚过去。

## 节点少了，没变的那一行仍会白画，除非引用还是原来那个

流式时往往只有最后一条在变。前面几百条不该每次都重新执行组件函数。`React.memo` 在 props 和上次一样时跳过这次渲染。`useMemo` 缓存一次计算，`useCallback` 缓存一个函数。三者都是「输入没变就用上次的结果」。

上一章的合并如果每次都造出全新对象，这里的 `memo` 会认为全部变了。引用稳定不是 `memo` 变出来的，是更新数据时留出来的。

```tsx
setMessages((list) => list.map((m) => (m.id === next.id ? next : m)));
const MessageRow = memo(({ message }: { message: Message }) => (
  <article>{message.text}</article>
));
messages.map((m) => <MessageRow key={m.id} message={m} />);
```

`key` 用稳定的消息 ID。优化之前用 React Profiler 看是哪些组件在重复渲染。给每个小计算都套缓存，比较和内存本身也有成本。

React Compiler（稳定版在 2025 年 10 月）是构建插件 `babel-plugin-react-compiler`。它在编译时在合适的位置自动做上面那些缓存。项目没开编译器，就没有自动缓存。组件在渲染期间改外部变量或改 props，编译器认为不安全，会跳过这个组件。Effect 的依赖、外部库要求「同一个函数始终是同一个引用」时，手写更可控。很贵的计算，例如解析长 Markdown，手写 `useMemo` 把边界标出来，方便检查。

`memo` 和编译器都挡不住两样变化：这个组件自己的 props 变了，或者它读取的 Context 变了。Context 留到场景题下篇。
