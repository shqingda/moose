# 五、架构边界：包放在哪，密钥放在哪

> 对应答案：[05-architecture.md](../05-architecture.md)，原题 2、9。
> 读完要能讲清：一个仓库里的目录，和 Monorepo 里的包，差在什么地方；浏览器为什么不能长期保管调用模型的密钥。

这一章只有两个问题，但它们是同一种判断：**能力和秘密要放在改不了、也看不了的那一层。** 目录分得再清，如果浏览器包能 `import` 到 Node 的密钥模块，边界就是假的。前端把模型密钥写进包里，用户打开开发者工具就能拿走。

## 1. Monorepo 是多个包共用一个仓库

一个产品往往同时有桌面应用、网页、后台和两边都要用的类型。放在同一个 Git 仓库里，一次提交可以一起改，锁文件也只有一份，大家装到的依赖版本一致。

Monorepo 额外要求：里面有**多个可以独立管理的包**。每个包有自己的依赖和构建，包和包之间用依赖关系连接，而不是「随便 import 隔壁目录」。

常见切法：

```
apps/web            浏览器能跑的界面
apps/server         持有密钥、记账、转发模型
packages/contracts  两边都要的类型和校验
```

共享契约包里只放两端都需要的类型和校验。浏览器包不能依赖 Node 内置模块或只存在于服务端的库，否则打包失败，或者打包成功了、到浏览器里才崩。

CI 可以顺着包之间的依赖，只检查这次改动影响到的包，不必每次全仓库都跑。

### 目录分层和包分层

| | 同一包里的目录 | Monorepo 的包 |
| --- | --- | --- |
| 例子 | `src/`、`electron/`、`shared/` | `apps/web`、`packages/contracts` |
| 依赖声明 | 整个包共用一份 | 每个包自己声明 |
| 构建 | 通常一起配 | 可以分别构建 |
| 误引用 | 靠约定和打包配置挡住 | 靠包的依赖边界挡住 |

目录用来整理一个应用内部的代码。包用来声明「这一块可以单独安装、单独构建、单独限制能依赖谁」。把三个文件夹放在一个 `package.json` 下面，仓库仍然可以是 workspace 的一员，但那三个文件夹本身不是三个包。

## 2. 长期密钥不要放进浏览器

浏览器里的代码和请求，用户都能看见。写进前端包或打进请求里的长期密钥，已经不是秘密。接多家模型时，先问三句：凭据属于谁、谁有权调用、费用谁付。

常见、也是默认的做法：

```
浏览器只带用户自己的登录态
  → 后端确认这个人有权调用
  → 后端限流、记账
  → 后端用自己保管的长期密钥转发到模型服务商
  → 把模型的响应再转回浏览器
```

浏览器直连模型，只适合两种已经把风险放对位置的情况：

| 情况 | 密钥是谁的 | 费用谁承担 |
| --- | --- | --- |
| 服务商发了权限收得很窄、很快过期的短期凭证 | 短期凭证，泄露窗口小 | 仍按服务商那套凭证的规则 |
| 用户把自己的密钥填进来 | 用户自己的 | 用户自己 |

多家服务商的输入格式和错误码，可以在公共层先收成一种。各模型「能不能用工具、流事件长什么样」这种能力差异，留在各自的适配器里。公共层一上来就写满每家的分支，加一家就要改所有调用方。

**和类型章的关系：** 适配器在运行时把各家字段收成 `AgentEvent` 这种统一形状。架构上则是：统一的是契约，分叉的是能力。两层对着同一件事。

**和状态章的关系：** 浏览器里的「发送成功」仍然只表示你的后端收下了请求。模型有没有跑完，要看后面的流。密钥在后端，不改变这个时间差。

## 容易混在一起

**一个 Git 仓库和一个 Monorepo。** 仓库回答代码放哪。Monorepo 还回答里面有几份可以独立管理的包。

**workspace 和包。** 包管理器的 workspace 可以把多个包列在一个锁文件里。某个应用内部的源码目录，不因为仓库使用了 workspace 就自动变成独立包。

**后端代付和本机 CLI 登录。** 都是「页面不持有模型的长期密钥」，但花钱和登录的主体不同。前者是你的服务用自己的密钥、自己记账。后者是用户机器上的代理 CLI 用它自己的登录态。

## Moose 这一章实际落在哪

以下只复述 [答案](../05-architecture.md)。

- 仓库已有 pnpm workspace，包含应用根包、站点和商店包。应用内部的 `src`、`electron`、`shared` 仍是目录分层，不是三个独立的 package。
- Renderer 不直连模型。它调用本机后台，由代理 CLI 使用自己的登录状态。这和 SaaS 由服务端代付计费的模式不同。

「`apps/web` + `packages/contracts`」那种切法是通用讲法，不是 Moose 的目录。

## 本章速记

Monorepo 是多个可独立声明依赖、可独立构建的包共用一个仓库和一份锁文件；共享包只放两边都要的契约，浏览器包不能带上 Node 依赖。同一包里的 `src`、`electron`、`shared` 是目录，不是三个包。模型的长期密钥放在用户改不了的那一层：通常是后端，先鉴权、限流、记账再转发。只有短期受限凭证或用户自带密钥时，才考虑浏览器直连。多家模型的公共层统一格式和错误，能力差异留在适配器。Moose 的 workspace 里有应用根包、站点包和商店包，应用内部仍是目录；页面不直连模型，而是走本机后台和 CLI 自己的登录，不是服务端代付。
