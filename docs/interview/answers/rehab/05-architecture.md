# 五、架构边界：包放在哪，密钥放在哪

> 对应答案：[05-architecture.md](../05-architecture.md)，原题 2、9。

前面几章把类型、事件和状态放在了不同的模块里。目录分开，还不等于浏览器碰不到密钥。这一章先分清「一个仓库里的目录」和「可以单独限制依赖的包」，再把长期密钥放到用户改不了的那一层。两件事是同一种判断：能力和秘密要放在看不了、也改不了的地方。

## 同一个仓库里，先问它是不是多个包

桌面、网页、后台和两边都要用的类型，放在同一个 Git 仓库里，一次提交可以一起改，锁文件也只有一份。这只说明代码放在一起。

Monorepo 还要求里面有多个可以独立管理的包。每个包自己声明依赖、可以单独构建，包和包之间用依赖关系连接，而不是随便 import 隔壁目录。

常见切法是 `apps/web` 放浏览器能跑的界面，`apps/server` 持有密钥、记账、转发模型，`packages/contracts` 放两边都要的类型和校验。共享包里只放两端都需要的东西。浏览器包如果依赖 Node 内置模块，会打包失败，或者打包成功了、到浏览器里才崩。

CI 可以顺着包之间的依赖，只检查这次改动影响到的包。

`src/`、`electron/`、`shared/` 这种目录，是在整理同一个包里面的代码。整个包共用一份依赖。误引用靠约定和打包配置挡住。把三个文件夹放在一个 `package.json` 下面，仓库可以是 workspace 的一员，那三个文件夹本身仍不是三个包。workspace 只是把多个包列进同一份锁文件。源码目录不会因为仓库用了 workspace 就自动变成独立包。

## 包的边界定了，长期密钥仍不能进浏览器那个包

浏览器里的代码和请求，用户都能看见。写进前端包或打进请求里的长期密钥，已经不是秘密。接多家模型时，先问凭据属于谁、谁有权调用、费用谁付。

常见的做法接在上一节的 `apps/server` 上：浏览器只带用户自己的登录态，后端确认这个人有权调用，再限流、记账，用自己保管的长期密钥转发，把响应转回浏览器。

浏览器直连，只适合两种已经把风险放对位置的情况。一种是服务商发了权限很窄、很快过期的短期凭证。另一种是用户把自己的密钥填进来，费用也由用户承担。

多家服务商的输入格式和错误码，可以在公共层先收成一种。各家能不能用工具、流事件长什么样，留在各自的适配器里。公共层写满每家的分支，加一家就要改所有调用方。类型章里，适配器把各家字段收成同一种事件。这里是同一件事的目录版本：统一的是契约，分叉的是能力。

浏览器里的「发送成功」仍然只表示后端收下了请求。模型有没有跑完，要看后面的流。密钥在后端，不改变这个时间差。

后端代付和本机 CLI 登录，都是「页面不持有模型的长期密钥」。花钱的人不同。前者是你的服务用自己的密钥、自己记账。后者是用户机器上的代理 CLI 用它自己的登录态。

## Moose 里实际是这样

只对得上 [答案](../05-architecture.md)。

- 仓库已有 pnpm workspace，包含应用根包、站点和商店包。应用内部的 `src`、`electron`、`shared` 仍是目录，不是三个独立的 package。
- Renderer 不直连模型。它调用本机后台，由代理 CLI 使用自己的登录状态。这和 SaaS 由服务端代付计费的模式不同。

「`apps/web` + `packages/contracts`」那种切法是通用讲法，不是 Moose 的目录。
