# 十二、改代码的手感 · 上

> 对应答案：[12-scenarios-engineering.md](../12-scenarios-engineering.md)，原题 2、20、25、42、43。下篇讲国际化、灰度、函数式和领域模型。

## 压缩和删除提交：先问这条历史有没有别人在用

连续三次小修正，希望合并请求里只留一条清楚的记录，这是压缩（squash）。某个提交引入了问题、想把它拿掉，是另一件事。两者都可能改写历史：生成新的提交 ID，原来的 ID 不再代表同一条历史。

操作前保持工作区干净，确认基准提交，并留一个备份分支。

未共享的分支上可以改写。`git rebase -i HEAD~N`，其余行改成 `squash` 或 `fixup`，会合成一次。`squash` 保留说明，`fixup` 丢掉说明。`git reset --soft <基准>` 再提交一次，那几次的改动还在暂存区，新提交只有一个。交互式 rebase 里把一行标成 `drop`，是去掉那一次提交。

如果只是希望并进主干时变成一条，可以用平台的 squash merge，不必改自己的分支历史。

已经推送、并且有人基于它开发时，不要改写后强推。移除用 `git revert <commit>`：新增一个提交，内容正好抵消目标那次，旧历史还在，别人的仓库不会对不上。撤销一次合并提交时要加 `-m`，指定以哪一边为主线。

确需更新远端、并且已经和别人协调过，用 `git push --force-with-lease`。它在远端仍是你预期的那次提交时才覆盖。`--force` 不管远端是不是被人更新过。

```sh
git reset --soft HEAD~3 && git commit -m "合并后的说明"
git revert abc1234
git push --force-with-lease
```

第三行只在「改写过已推送分支、而且已经协调」时使用。

后续提交如果依赖被拿掉的改动，revert 和 rebase 都可能冲突，要手解。`git reset --hard` 到目标之前，会把目标之后的所有提交都移走，不能当成「只删其中某一个」。

**Moose：** 提供 Git 改动预览、暂存和提交。提交前会重新检查 HEAD 和暂存区。界面上没有压缩已有提交或撤销指定提交。编辑会话历史也不会回滚工作区文件。

## 哪个提交引入的：二分，而不是逐个回退

一百个提交里逐个 checkout，太慢。`git bisect` 每次检出好坏两点的中间，你判断这一版是好是坏，范围缩小一半。一百个大约七次能定位。

先找一个确定正常的提交，一个确定出错的提交，并准备稳定的复现步骤。然后 `git bisect start BAD GOOD`。每检出一版，复现，再标 `good` 或 `bad`。定位到那一次之后 `git bisect reset`，回到原来的分支。

```sh
git bisect start BAD GOOD
# 复现后：git bisect good  或  git bisect bad
git bisect reset
```

有可重复的测试脚本时，交给 `git bisect run` 自动标记。

环境、依赖和测试数据尽量固定。外部服务一会儿超时一会儿成功，不能用来标 good 或 bad，否则会指到一个无关的提交。

## 减少 if-else：先看分支在表达什么

不是所有 `if` 都该消灭。先分类，再换结构。为了消灭 `if` 而发明一层谁也读不懂的抽象，维护成本会更高。

固定的值映射，例如状态对应文案，用对象表，新增一行即可。不合法就结束，用提前返回，主流程少嵌套。复杂但稳定、还会增加的策略，各自一个命名函数。少量互斥流程，`switch` 就很清楚。

```ts
const label = {
  queued: '排队中',
  running: '执行中',
  waiting: '等待审批',
} as const;

function statusLabel(status: keyof typeof label) {
  return label[status];
}
```

提前返回的形状是：先处理不能继续的情况并 `return`，后面的代码默认前提已经成立。

**Moose：** 不同代理的协议差异放在 Adapter 里，这是有意义的拆分。Service 按请求类型分支，并不天然是坏代码。分支表达的是「这几种请求本来就不同」，不必为了形式统一再包一层。

## 重构：小步，并且不悄悄改变行为

重构通常是为了降低后面的修改成本。例如再加一个代理时，不必把整个页面改一遍。没有具体痛点的重构，容易变成个人偏好。

先指出痛点，比如协议分支散落，或某个函数无法测试。用现有行为和测试当基线。一次只改一类结构，每步都验证。用户可见的行为保持不变。

一次改很多类结构，出了问题就看不出是哪一步改变了行为。抽象好不好，看它是否减少了实际的重复和错误，不看拆出了多少个文件。

**Moose：** 不同代理的协议差异收拢在 Adapter。新增代理时，页面不必到处加分支。

## 删「没人引用」的代码：先核对它是不是真的没人用

文本搜索找不到，仍可能在用。路由配置、动态 `import()`、插件注册、运行时拼出来的 class 名、按文件名自动加载的约定、被外部调用的导出、生成的代码，都是这样。

CSS 尤其要看动态 class，以及页面上是否真的出现，不能只看源码搜索。

先用类型检查、依赖分析和搜索找出候选。再核对真实运行入口和对外 API。然后分批删除。每批跑构建、测试，并看关键页面。

```sh
pnpm typecheck
pnpm lint
pnpm build
```

类型检查能发现删掉之后还在被静态引用的符号。它发现不了只在运行时拼出来的入口。

**Moose：** 用这三条命令发现过一部分失效引用。动态入口仍要人工核对。没有一键清理 JS、TS、CSS 死代码的工具。

## 容易答错的地方

squash 和 drop 改写未共享的历史。revert 在共享历史上新增反向提交。`reset --hard` 会移走后面的一串提交。

`--force-with-lease` 比 `--force` 多检查远端是不是仍是你以为的那次。两者都会改写远端，协调仍然要先做。

bisect 标的是「这个提交的代码好不好」，不是「这次网络好不好」。测试抖动不能拿来标 bad。

按协议或请求类型分开，是在给差异一个位置。散落在页面各处的同类判断，才是重构要收拢的。Adapter 里的分支不是无意义的 if。

动态入口搜不到字符串引用。搜不到，还不等于没人执行。

## 上篇先记住

改历史之前先分清这条提交有没有共享。未共享可以用 rebase 压缩或 drop，也可以 soft reset 后重新提交。已共享用 revert 追加反向提交。确要覆盖远端时用 `--force-with-lease`，并先协调。

定位回归用 bisect，在稳定复现的前提下对半分。代码里的分支按映射、守卫、策略、互斥流程来选结构。协议差异可以收进适配器。重构一次动一类结构，用测试守住行为。删除死代码前核对动态入口，分批用类型检查、lint 和构建验证。

Moose 的 Git 界面做到预览、暂存和提交。提交前复核 HEAD 与暂存区。不在界面里压缩或 revert。编辑会话历史也不会把工作区文件回滚。协议差异在 Adapter。死代码没有一键清理。
