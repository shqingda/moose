## 2. 如何把多次提交压缩成一次？如何移除一个指定的 commit？
*（合并了原第 2、21 题）*

> **这题在考什么**：你连续提交了三次小修正，合并请求里希望只留一条清楚的记录，这就是“压缩提交”（squash）；或者某个提交引入了问题，想把它去掉。面试官想看你会不会操作，更想看你知不知道哪些操作会改写历史，以及提交已经共享时该怎么选。

**一句话回答**：未共享的分支可以用 `git rebase -i` 把提交标成 `squash`/`fixup` 压缩、标成 `drop` 删除，或用 `reset --soft` 后重新提交；已经共享的提交不要改写历史，移除时用 `git revert` 新增一个反向提交，确需更新远端时先协调并用 `--force-with-lease`。

**展开说明**
- 操作前保持工作区干净，确认基准提交，并留一个备份分支。
- 压缩：`git rebase -i HEAD~N` 打开最近 N 个提交的列表，把除第一个外的提交改成 `squash`（合并并保留提交说明）或 `fixup`（合并并丢弃说明）。也可以 `git reset --soft <基准提交>`，改动仍留在暂存区，再提交一次就得到单个提交。
- 如果只是希望合并到主干时变成一条提交，可以直接用平台的 squash merge，不必改写自己的分支。
- 移除已共享的提交：`git revert <commit>` 新建一个提交，内容正好抵消目标提交，历史完整保留，不影响别人。撤销合并提交时要用 `-m` 指定以哪一边为主线。
- 移除未共享的提交：在交互式 rebase 列表里把它标成 `drop` 或删掉这一行。
- 压缩、`drop` 都会生成新的提交 ID，等于改写历史。后续提交依赖被移除的改动时，revert 和 rebase 都可能出现冲突，需要手动解决。

| 方式 | 适用场景 | 代价 |
| --- | --- | --- |
| `rebase -i` 的 `squash`/`fixup` | 压缩自己未共享的提交 | 改写历史 |
| `reset --soft` 后重新提交 | 把最近几次提交合成一次 | 改写历史 |
| `rebase -i` 的 `drop` | 删掉自己未共享分支上的提交 | 改写历史 |
| `git revert` | 撤销已共享的提交 | 多一个反向提交 |

**示例**：下面的命令分别演示压缩最近三次提交和撤销一个已共享的提交。

```sh
git reset --soft HEAD~3 && git commit -m "合并后的说明"  # 三次提交合成一次
git revert abc1234                                      # 新增反向提交，抵消 abc1234
git push --force-with-lease                             # 仅在改写过已推送分支且已协调时
```

**Moose 里的做法**：Moose 提供 Git 改动预览、暂存和提交入口，提交前会重新检查 HEAD 与暂存区；没有在界面上压缩已有提交或撤销指定提交的操作，编辑会话历史也不会回滚工作区文件。

**容易答错的地方**
- 已经推送且有人基于它开发时，不要直接强推，要先协调。必须更新远端时用 `--force-with-lease`（远端没被别人更新时才覆盖），而不是 `--force`。
- `git reset --hard` 到目标提交之前，会连同它后面的所有提交一起移走，不能当作“移除某一个提交”来用。

## 20. 当项目报错，你想定位是哪个 commit 引入的错误的时，该怎么做

> **这题在考什么**：某个功能以前好好的，现在坏了，中间有一百个提交。逐个回退太慢。面试官想看你会不会用 `git bisect` 二分定位，以及怎样保证判断结果可靠。

**一句话回答**：找一个确定正常的提交和一个确定出错的提交，用 `git bisect` 每次检出中间版本复现并标记 `good` 或 `bad`，直到缩小到引入问题的那个提交，最后 `git bisect reset`。

**展开说明**
- `git bisect` 像二分查找：每次检出好坏两点中间的版本，你判断它是好是坏，范围就缩小一半。一百个提交大约七次就能定位。
- 开始前要有一版明确正常的提交、一版明确出错的提交，以及稳定的复现步骤。
- 每次复现后执行 `git bisect good` 或 `git bisect bad` 标记结果。
- 结束后运行 `git bisect reset`，回到开始前所在的分支。
- 如果有可重复的测试脚本，可以交给 `git bisect run` 自动执行和标记。

**示例**：假设 `GOOD` 是正常提交、`BAD` 是出错提交，二分定位的命令如下。

```sh
git bisect start BAD GOOD   # 先写坏的，再写好的
# 每次复现后执行 git bisect good 或 git bisect bad
git bisect reset            # 结束，回到原分支
```

**容易答错的地方**
- 环境、依赖和测试数据要尽量固定。外部服务的波动不能拿来判断提交好坏，否则会标错。

## 25. 如何减少项目里面 if-else

> **这题在考什么**：代码里一长串 `if-else` 看着难维护，但不是所有 `if` 都该消灭。面试官想看你能否先判断这些分支在表达什么，再选合适的结构，而不是为了消灭 `if` 过度抽象。

**一句话回答**：固定值映射改成对象表，异常条件用提前返回，复杂但稳定的不同策略拆成命名函数；真正互斥的流程用 `switch` 也很清楚。

**展开说明**
- 先看分支在表达什么：是固定的值映射、异常条件，还是几种不断增加的业务策略。
- 固定的值映射（比如状态码对应文案）改成对象表，新增一项只需加一行。
- 异常条件用提前返回（guard clause），先处理不合法的情况并 `return`，主流程就不用层层嵌套。
- 复杂但稳定的不同策略，拆成各自命名的函数，每个函数只关心一种情况。
- 真正互斥的几种流程用 `switch` 也很清楚，没必要为了减少 `if` 增加抽象。

| 分支类型 | 推荐写法 |
| --- | --- |
| 固定值映射 | 对象表 |
| 异常条件 | 提前返回 |
| 复杂但稳定的策略 | 拆成命名函数 |
| 少量互斥流程 | `switch` |

**示例**：下面的例子只有固定文案差异，用映射表就能代替多个 `if`。

```ts
// 状态到文案的固定映射
const label = { queued: '排队中', running: '执行中', waiting: '等待审批' } as const;
function statusLabel(status: keyof typeof label) { return label[status]; }
```

**Moose 里的做法**：Moose 把不同代理的协议差异放进 Adapter，这是有意义的拆分；Service 按请求类型分支，并不天然是坏代码。

## 42. 一般是怎么做代码重构的

> **这题在考什么**：项目做久了，加一个小功能就要改一大片代码，这时就需要重构。面试官想看你是否有安全重构的方法，而不是一口气推倒重写。

**一句话回答**：先找出具体的痛点，用现有行为和测试做基线，然后小步修改、每步验证；重构只改代码组织，不悄悄改变用户可见的行为。

**展开说明**
- 重构的目的通常是降低后续修改的成本。例如新增一个代理时，不需要把整个页面都改一遍。
- 先指出具体痛点，比如协议分支散落在各处，或者某个函数很难测试。没有明确痛点的重构容易变成个人偏好。
- 用现有行为和相关测试作为基线，再小步调整，每一步都验证一次。
- 一次只改一类结构问题。这样出了问题，能看出是哪一步改变了行为。

**Moose 里的做法**：Moose 把不同代理的协议差异收拢在 Adapter 层（适配层），新增代理时不需要让页面到处添加分支判断。

**容易答错的地方**
- 抽象的好坏以是否减少了实际的重复和错误来衡量，而不是看拆出了多少个类或文件。

## 43. 如何清理源码里面没有被引用的代码，主要是 JS、TS、CSS 代码

> **这题在考什么**：老项目里积累了很多看似没用的代码，大家都不敢删。面试官想看你知道怎么找出死代码，更重要的是知道哪些“搜不到引用”的代码其实还在用。

**一句话回答**：先用 TypeScript 检查、依赖分析和搜索找出候选，再核对真实的运行入口和外部 API，分批删除，每批都跑构建、测试并检查关键页面。

**展开说明**
- 一段代码搜不到引用，不一定真的没用。路由配置、动态导入（`import()`）、插件注册和运行时拼接的类名，都可能绕过普通的文本搜索。
- 先用 TypeScript 编译检查、依赖分析工具和搜索找出候选代码，再核对真实运行入口和对外暴露的 API。
- CSS 还要检查动态拼出的 class 名，以及页面上是否真的用到，不能只看源码搜索结果。
- 生成的代码、按约定自动加载的文件（如按文件名注册的路由），以及被外部调用的导出，尤其要核实用途。
- 分批删除，每批都跑构建、相关测试，并检查关键页面。

**示例**：删除候选代码后，至少跑一遍项目现有的检查命令：

```sh
pnpm typecheck  # 类型检查，发现失效的导入和引用
pnpm lint       # 代码规范检查
pnpm build      # 确认能正常构建
```

**Moose 里的做法**：Moose 用这三条命令发现了一部分失效引用，但动态入口仍需人工核对。项目没有一键清理 JS/TS/CSS 死代码的工具。
