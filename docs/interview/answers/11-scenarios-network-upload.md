## 10. 大文件上传怎么做？切片大小怎么定，切片真的更快吗？
*（合并了原第 10、11、58 题）*

> **这题在考什么**：上传几个 G 的视频时，网络一断就要从头再传，体验很差，于是会用分片上传。很多人以为分片能“提速”。面试官想看你是否了解分片上传和断点续传的完整流程，知道片大小如何权衡，并明白分片真正解决的是失败重传和续传。

**一句话回答**：先向服务端申请 `uploadId`，按固定大小切片、限制并发上传，失败的片单独重试，恢复时只补传服务端未确认的分片，最后校验合并；带宽一定时分片不会让纯传输变快，它的价值是可恢复和可控并发。

**展开说明**
- 流程：上传前申请一个 `uploadId` 标识这次任务；用 `file.slice` 按需切片，不要一次把整个文件读进内存；限制同时上传的分片数，某一片失败只重试这一片；全部完成后服务端校验并合并成完整文件。
- 断点续传：恢复时先向服务端查询哪些分片已确认，只补传剩下的部分。服务端要让重复上传同一片的结果一致（幂等），并限制文件大小、类型和用户配额。
- 片数是算出来的：真正要选的是每片大小，片数等于 `ceil(文件大小 / 分片大小)`（向上取整，最后一片可以不满）。比如 1 GB 文件每片 1 MB 约一千次请求，每片 100 MB 请求少了，但失败一次要重传很大一块。
- 选片大小要在请求开销、内存占用、失败重传代价和服务端限制（分片数量、单片大小、上传会话时限）之间权衡；还要把文件哈希计算和移动端内存上限算进去。并发数是另一个独立参数，应根据真实网络和失败率压测确定。
- 关于速度：把 10 MB 切成十块，总字节数还是 10 MB。带宽不变时纯传输时间的下限都接近“数据量 ÷ 带宽”，所以“切片和整体上传耗时差不多”在理想情况下基本正确。真实耗时还要加上每片的请求开销、校验和合并；片过小或并发过多造成拥塞，反而更慢。

| 片大小 | 好处 | 代价 |
| --- | --- | --- |
| 小 | 失败只重传一小块 | 请求多，开销占比高 |
| 大 | 请求少 | 占内存多，失败重传代价高 |

**示例**：下面这段串行示意代码演示如何切片；`file.slice` 只截取当前这一块，不会读取整个文件。

```ts
for (let offset = 0; offset < file.size; offset += chunkSize) {
  // 只取当前要上传的这一片
  const part = file.slice(offset, offset + chunkSize);
  await uploadPart(uploadId, offset, part);
}
// 实际实现还要并发控制，并在续传前查询服务端已确认的分片
```

**Moose 里的做法**：Moose 的附件单文件上限 20 MB，先导入本地受控目录，由后台一次导入并保存；Web 上传按文件逐个提交，没有网络分片上传，也没有分片参数。

**容易答错的地方**
- 不能断言分片上传一定与整文件同速，也不能说它一定快几倍。
- 续传的依据是服务端已确认的分片，而不是客户端自己记的进度。

## 17. 如何防止重复请求？页面要同时请求大量接口时怎么控制并发？
*（合并了原第 17、56 题）*

> **这题在考什么**：重复请求有几种来源：用户连点按钮、多个组件同时读同一份数据、搜索框旧请求还没回来又发了新请求；另一类问题是一个页面要加载几百项数据，直接全部发出去会压垮浏览器和后台。面试官想看你能否先分清来源给出对应处理，并能实现一个有上限的并发队列。

**一句话回答**：连点就限制提交，多组件读同一数据就共享在途 Promise，搜索类就取消旧请求并丢弃迟到结果，写操作用服务端幂等键兜底；大量请求不要用 `Promise.all` 一次发出，而是用有并发上限的队列，优先加载必需数据并单独记录每项结果。

**展开说明**
- 用户连点按钮时，在请求进行中限制再次提交。
- 多个组件同时读取同一数据时，共享同一个“在途 Promise”（已经发出、还没返回的请求），后来者直接等待它。
- 搜索词变化时取消旧查询，并用“请求代次”（每次请求递增的编号）丢弃迟到的旧结果，防止旧结果覆盖新结果。
- 写操作要让服务端支持幂等键：同一个键重复提交只生效一次。
- 大规模并发：限制的是同一时刻运行的请求数，而不是把所有请求往后推。上限设为 4 时先发出 4 个，完成 1 个再从队列取第 5 个；第 2 个失败也只记录它的错误，继续处理其余任务。
- 队列里优先加载当前页面必需的数据，用户切走后取消已经没用的请求。并发上限根据实际网络和服务端容量确定。

| 来源 | 处理方式 |
| --- | --- |
| 用户连点 | 请求进行中限制提交 |
| 多组件读同一数据 | 共享在途 Promise |
| 搜索词频繁变化 | 取消旧请求，用代次丢弃迟到结果 |
| 写操作重复提交 | 服务端幂等键 |
| 一次要发几百个请求 | 有并发上限的任务队列 |

**示例**：下面的代码用 4 个 worker 共享一个任务游标，最多 4 个请求同时进行，并保留每一项的结果。

```ts
let next = 0; // 共享游标：下一个待领取的任务下标
const results = new Array(tasks.length);
async function worker() {
  while (next < tasks.length) {
    const i = next++; // 领取任务（JS 单线程，这一步不会被打断）
    try { results[i] = { status: 'fulfilled', value: await tasks[i]() }; }
    catch (reason) { results[i] = { status: 'rejected', reason }; } // 单项失败不影响其他任务
  }
}
await Promise.all(Array.from({ length: 4 }, worker));
```

共享在途 Promise 的写法是：`pending` 表里没有这个 key 才发起请求，并在 `finally` 里删除，其他调用方直接返回表里的 Promise。

**Moose 里的做法**：
- Moose 的额度查询会合并并发读取；前端的请求代次用于防止旧快照覆盖新快照，两者解决的问题不同。
- 后台按实际工作目录串行运行代理任务，不同目录之间可以并行。这是任务调度，不是覆盖页面所有 HTTP 请求的通用并发队列。

**容易答错的地方**
- 对写操作来说，只禁用按钮不够，还需要服务端幂等键。
- 前端控制并发不能代替服务端限流，收到 429 时仍应按服务端指示退避。

## 24. 请求失败会弹出一个 toast,如何保证批量请求失败，只弹出一个 toast

> **这题在考什么**：页面同时发了十个请求，断网时它们一起失败，如果每个都弹提示，用户会看到十个相同的 toast。面试官想看你怎样把提示聚合起来，同时不丢失每个请求的错误信息。

**一句话回答**：网络层如实返回每个请求的错误，提示层再按错误类型或业务批次聚合，只弹一次提示，但每条失败仍各自记录。

**展开说明**
- 网络层不负责弹提示，只把每个请求的真实错误交给上层。这样错误不会被吞掉。
- 提示层按错误类型聚合。比如断网导致十个请求失败，只弹一次“网络不可用”，十条失败仍分别记录。
- 同一批业务请求可以用 `Promise.allSettled`（等所有 Promise 结束，无论成功失败都返回各自结果）汇总，整批结束后提示一次“部分加载失败”。
- 不同错误区别对待：鉴权过期统一跳转登录页，用户主动取消的请求不弹失败提示。
- 避免组件内部和全局拦截器各弹一次，造成重复提示。

**示例**：下面的代码并行加载三项数据，只在整批结束后提示一次，同时保留每项的结果。

```ts
const results = await Promise.allSettled([loadA(), loadB(), loadC()]);
// 只要有一项失败，就提示一次
if (results.some((item) => item.status === 'rejected')) {
  showToast('部分数据加载失败');
}
```

**Moose 里的做法**：Moose 分别保存连接状态和操作错误，重连成功不能清掉尚待处理的保存失败。专门的处理建议依赖稳定的错误码，未知错误会保留详情。目前没有按业务批次聚合多次请求错误的专用 toast 机制。

## 33. 浏览器有同源策略，但是为何 cdn 请求资源的时候不会有跨域限制

> **这题在考什么**：很多人以为同源策略会拦住所有跨域请求，但页面明明能显示 CDN 上的图片和脚本。面试官想看你是否分得清“加载资源”和“用 JS 读取响应内容”是两回事。

**一句话回答**：同源策略主要限制的是跨源“读取”，而不是跨源“加载”；页面可以嵌入 CDN 的图片、样式和经典脚本，但要用 JS 读取它们的内容，就需要 CDN 通过 CORS 明确授权。

**展开说明**
- 同源指协议、域名、端口都相同。同源策略限制的是脚本读取另一个源的响应内容，并不禁止页面加载所有跨源资源。
- `<img>`、`<link rel="stylesheet">`、普通的 `<script>`（经典脚本）都可以直接引用 CDN 地址，资源会被浏览器加载并使用。
- 如果用 `fetch` 去读跨域响应，通常需要 CDN 返回 CORS 响应头（如 `Access-Control-Allow-Origin`），明确允许当前页面读取。
- 模块脚本（`type="module"`）、字体文件和 Canvas 像素读取各有跨源限制。此外，CSP（内容安全策略，由站点声明允许从哪里加载资源）也可能直接拦下资源。

以另一个域名上的同一张图片为例：

| 页面操作 | 结果 |
| --- | --- |
| `<img src="https://cdn.example/a.png">` | 通常可以显示 |
| `fetch('https://cdn.example/a.png')` 后读取内容 | 需要 CDN 通过 CORS 允许当前源 |
| 画到 Canvas 后读取像素 | 还需满足跨源图片读取要求，否则画布会被污染 |

**Moose 里的做法**：Moose Web 的页面和 API 由同一个本机服务提供，CSP 默认只允许加载本站资源。它目前不依赖跨域 CDN 资源。

**容易答错的地方**
- 图片能显示，不代表 JS 能读取它的像素，也不代表能拿到完整的资源计时数据。

## 34. Cookie 由哪些部分组成？能不能在不同域之间共享？
*（合并了原第 34、63 题）*

> **这题在考什么**：登录态和会话安全都离不开 Cookie；公司有多个站点，希望登录一次到处可用，又会问 Cookie 能不能跨域共享。面试官想看你是否清楚每个属性控制什么、Cookie 的作用域规则，以及无关域名之间怎么做单点登录。

**一句话回答**：Cookie 由 `name=value` 和设置时附带的属性组成（`Domain`、`Path`、`Expires/Max-Age`、`Secure`、`HttpOnly`、`SameSite`，部分场景还有 `Partitioned`）；同一父域下的子域可以通过 `Domain` 共享，两个无关域名不能直接共享，通常借助统一身份服务跳转登录后各自建立会话。

**展开说明**
- 服务端通过 `Set-Cookie` 响应头告诉浏览器保存什么、何时过期、向哪里发送。属性只在设置时出现，之后的 `Cookie` 请求头通常只带名称和值。

| 属性 | 作用 |
| --- | --- |
| `Domain` | 哪些域名可以收到；不设时只属于当前主机 |
| `Path` | 哪些路径下的请求会携带它 |
| `Expires` / `Max-Age` | 过期时间或有效秒数；都不设就是会话 Cookie |
| `Secure` | 只在 HTTPS 下发送 |
| `HttpOnly` | 禁止 JS 通过 `document.cookie` 读取 |
| `SameSite` | 控制跨站请求是否携带（`Strict`、`Lax`、`None`） |
| `Partitioned` | 按顶层站点分区存储（CHIPS），用于第三方嵌入场景 |

- 有共同父域时，设置 `Domain=example.com`，`a.example.com` 和 `b.example.com` 都能收到。两个无关域名（如 `a.com` 和 `b.com`）无法共享同一个 Cookie，跨域登录由统一身份服务完成跳转，各站点再分别建立会话。
- 跨站携带还受浏览器隐私策略影响。浏览器对第三方 Cookie 的限制越来越多，Safari 和 Firefox 默认就会拦截或隔离；`SameSite=None` 必须同时带 `Secure`，`Partitioned` 让嵌入场景下的 Cookie 按顶层站点隔离，具体效果以各浏览器实现为准。
- 跨源请求要带 Cookie，前端要设置 credentials（如 `fetch` 的 `credentials: 'include'`），服务端也要返回允许凭证的 CORS 响应头。

**示例**：Moose 在 HTTPS 下设置的响应头可以简化为：

```http
Set-Cookie: moose_session=<随机值>; HttpOnly; SameSite=Strict; Path=/; Secure
```

**Moose 里的做法**：Moose Web 的 `moose_session` 没有设置 `Domain`，是当前主机的 Cookie，没有做跨子域共享；它也没有设置过期时间。通过 HTTP 访问时不会设置 `Secure`。浏览器之后的请求只带回 `Cookie: moose_session=<随机值>`，后台再检查这个值是否属于有效会话。

**容易答错的地方**
- `HttpOnly` 只禁止脚本读取，浏览器仍会自动携带这个 Cookie。
- `Path` 不是安全隔离手段，不能靠它防止其他路径的页面访问 Cookie。
- 不要说“所有浏览器已经彻底移除第三方 Cookie”，各浏览器的策略并不相同。

## 52. 当 QPS 达到峰值时，该如何处理？

> **这题在考什么**：大促或热点事件时请求量猛增，服务开始变慢甚至报错。面试官想看你是否先定位瓶颈，再分清服务端和前端各自该做什么。

**一句话回答**：先定位是哪一段处理不过来；服务端做配额、限流、排队和必要的扩容，读请求加缓存、非关键任务延后；前端减少重复请求、限制并发，并按服务端指示退避重试。

**展开说明**
- QPS 是每秒请求数。请求突增时，先确认瓶颈在哪一段。只在前端加一个转圈动画，解决不了后台已经过载的问题。
- 服务端：做配额、限流、请求排队和必要的扩容；能缓存的读请求做缓存，非关键任务延后处理。超出限制时，返回明确的重试信息。
- 前端：减少重复请求，限制同时发出的请求数；重试时加入退避（每次等待时间逐步加长）和抖动（加一点随机时间，避免大量客户端同时重试）。
- 失败时保留用户已经输入的内容，不要让用户重填。

**示例**：下面这段示意代码演示收到 429（请求过多）时，优先使用服务端给出的等待时间：

```ts
if (response.status === 429) {
  // Retry-After 是服务端建议的等待时间
  const raw = response.headers.get('Retry-After');
  // 这里只处理纯秒数的写法
  const seconds = raw && /^\d+$/.test(raw) ? Number(raw) : undefined;
  showRetryAfter(seconds);
}
```

**Moose 里的做法**：Moose 的目录互斥用来解决本地任务之间的竞争，并不是公网 QPS 限流。

**容易答错的地方**
- 自动重试写操作之前，要确认这个操作是幂等的（重复执行结果相同），否则可能重复下单。
- `Retry-After` 除了秒数，也可能是一个日期格式，不能只按数字解析。

## 64. 扫码登录实现方式

> **这题在考什么**：网页版微信、各类后台都支持手机扫码登录电脑。面试官想看你能否说清楚三方（电脑、手机、服务端）之间的交互流程，以及怎样防止二维码被盗用。

**一句话回答**：电脑先向服务端申请一个短期、一次性的扫码会话，二维码里只放这个会话的标识；已登录的手机扫码后由用户确认授权，电脑通过轮询或推送得知结果，再建立自己的登录会话。

**展开说明**
- 二维码本身不应该等于登录凭据。它只是让手机找到电脑正在等待的那次登录请求，最终授权必须由已登录的手机用户确认。
- 第一步，电脑向服务端申请扫码会话，服务端返回一个不可预测的会话标识，电脑把它显示成二维码。
- 第二步，手机扫码后，显示即将登录的设备信息，由用户点击确认。
- 第三步，服务端记录授权；电脑通过轮询或推送（如 WebSocket）得知已授权，然后建立自己的登录会话。
- 扫码会话要设置过期时间，只能使用一次，并绑定发起请求的那台电脑。

**Moose 里的做法**：Moose 当前没有扫码登录，上面是一套设计方案。

**容易答错的地方**
- 二维码里不能放长期凭证，否则被拍照或截图就可能被冒用登录。

## 65. DNS 协议了解多少

> **这题在考什么**：“从输入网址到页面显示发生了什么”的第一步就是 DNS 解析。面试官想看你是否了解常见记录类型、解析和缓存的过程，以及为什么改了解析不会立刻生效。

**一句话回答**：DNS 把域名解析成记录，A/AAAA 记录给出 IP 地址，CNAME 记录指向另一个域名；解析过程经过多层缓存，缓存失效后由递归解析器查询权威记录，并按 TTL 缓存结果。

**展开说明**
- 浏览器拿到网址后，要先知道域名对应哪个网络地址，才能建立连接。DNS 只负责找地址，不负责网址后面的页面路径。
- 常见记录：A 记录对应 IPv4 地址，AAAA 记录对应 IPv6 地址，CNAME 记录把一个域名指向另一个域名。
- 浏览器、操作系统和递归解析器（如运营商或公共 DNS）都会查询自己的缓存。缓存失效后，递归解析器再去查询权威 DNS 服务器上的记录，并按 TTL（记录建议的缓存时长）缓存结果。
- 拿到 IP 之后，才进入建立连接和 HTTP 通信阶段。
- CDN 可以借助解析策略，把用户引导到较近或较空闲的节点。

**容易答错的地方**
- 因为有多层缓存，修改域名解析后不一定立刻对所有人生效。
