# 原生产品能力实施计划

基线：0.7.0。状态：第一阶段 Codex 原生 Plan 与插话已实现，纳入 0.8.0；第二、三阶段纳入 0.9.0，支持范围及限制见[第二阶段验收](phase-two-testing.md)。第三阶段见[Worktree 验收](phase-three-testing.md)。第四阶段纳入 0.10.0，见[Git 与原生审查验收](phase-four-testing.md)。Grok／Pi 原生 Plan 与第五阶段起仍待实现。对应[能力缺口](native-capabilities.md#优先补齐的产品能力)。

## 接入原则

- 每项能力记录底座、协议版本、支持状态及不可用原因。静态厂商名称不能代替实际能力检测。
- 原生操作经过 adapter、服务层、校验后的 IPC 和界面；不把不同底座包装成它们不具备的相同语义。
- 持久化用户意图和操作结果；重启不自动重放执行、提交、合并等操作。界面区分执行中、明确失败和结果未知。
- 新增能力按领域拆分模块，避免继续把所有逻辑塞进 service、composer 和 provider 主文件。

## 第一阶段：原生 Plan 与运行中插话

### 原生 Plan

本机 Codex 的 `generate-ts --experimental` 已确认包含 `TurnStartParams.collaborationMode`；仓库当前生成命令未启用实验字段。先同步生成方式和类型，再接入原生 `plan`／`default` 协作模式。恢复旧会话时显式设置目标模式，防止规划设置残留到执行阶段。

规划过程保留现有只读权限约束，并处理澄清问题、计划增量和最终计划。计划实体独立保存正文、版本、来源消息及审批状态。用户可修改正文或要求重新规划；批准必须绑定明确版本。执行时将批准的版本传给同一原生会话，恢复会话配置的权限，切换到原生执行模式。按钮重复点击、刷新、重启不能重复发起执行；失败保留可审阅的计划和错误。

Grok 先核对 ACP 握手的模式信息、模式切换和计划审批事件；只有完整流程得到真实 CLI 验证后才开放入口。不能仅凭 Grok 终端支持 `/plan` 就宣称 ACP 产品流程已接通。Pi 未核实前显示不支持。

验收：原生模式参数可核查；未批准不开始执行；修改后只执行批准版本；取消、恢复、重复点击与退出 Plan 均有确定行为。覆盖协议 fixture、服务持久化、Electron 完整流程和真实 CLI 最小验证。

### 运行中插话

运行中的输入提供明确的“立即发送”和“加入队列”语义。首批接入 Codex `turn/steer`，携带当前 `expectedTurnId`，复用正常发送的文本、附件和引用转换。插话沿用当前回合的模型与权限；不能悄悄把模式切换当成插话参数。

服务层核对会话、活动回合和生命周期，在底座确认接收后更新消息状态。底座明确拒绝已结束的回合时保留输入并提示用户选择排队；请求超时或连接断开时标记结果未知，不自动再次发送。停止与插话并发必须有确定结果，原有队列不能被插话误清空。

Grok、Pi 只有在验证对应原生能力后才显示立即发送；其余保持队列。不得用“停止并重启”冒充原生插话。

验收：运行中接收新指令、不创建额外回合；结束竞态、重复点击、断连、附件、权限等待和停止期间的行为受测；不会丢失输入或未经用户选择重复执行。

## 第二阶段：原生会话与子代理面板

状态：已实现 Codex 原生历史、分叉、压缩及子代理面板；Grok 历史回放已实现。恢复关闭子任务需主代理执行，其他不支持的控制明确禁用。真实 CLI 的历史读取已核验，变更流程完成模拟协议及 Electron 回归；真实压缩／新增委派未在本轮消耗模型额度重测。详见[验收说明](phase-two-testing.md)。

先抽取可复用的原生会话读取、分页和生命周期操作，再服务两类入口：

- 原生历史：按底座浏览、预览、导入并关联 native ID；重复导入可识别。显式分叉记录来源与分叉点，原会话保持独立；手动压缩显示运行状态和结果。明确会话分叉本身不隔离代码目录。
- 子代理面板：展示父子关系、状态、可用历史和结果；根据底座实际协议提供打开、发送消息、停止、恢复入口。子会话事件不能结束主任务，审批归属必须清晰。不支持的控制显示原因。

验收：导入幂等、分叉来源可追溯、分页可恢复、子会话生命周期独立；对未知子线程和底座不支持的操作不伪造成功。

## 第三阶段：Worktree 与并行工作

状态：已实现，纳入 0.9.0。受管 worktree 创建、会话实际目录路由、同项目并行、保留／清理、合并预览、冲突处理和重启核对已通过临时真实 Git 仓库与 Electron 验收，详见[第三阶段验收](phase-three-testing.md)。合并目标限项目根目录当前检出分支；新建隔离会话不搬迁旧 native 会话。

增加会话工作目录及受管 worktree 元数据，保留项目根目录用于归属。所有文件引用、终端、diff、代理执行和锁都使用会话实际目录。不同 worktree 可并行，同一实际目录继续串行。

支持从明确 ref 创建、查看状态、保留、清理和合并。创建失败需处理磁盘与数据库不同步；清理前检查活动任务、未提交内容及未合并提交。合并展示目标、变更和冲突，保留可继续解决冲突的状态。

验收：同项目两个 worktree 实际并行且修改隔离；符号链接不绕过目录锁；有未保存工作时不误删；合并冲突及重启恢复可处理。

## 第四阶段：Git 与原生审查

状态：已实现，纳入 0.10.0。逐文件暂存／取消暂存、提交预览及指纹校验、GitHub 草稿 PR／状态、Codex 独立只读 `review/start` 已接通。PR 限同一 GitHub origin 的已推送分支，不自动推送，不支持跨 fork／其他托管平台；审查保留底座返回的文件与行号文本。真实 Git 与模拟 CLI／Electron 验收见[第四阶段验收](phase-four-testing.md)，本轮不调用真实模型或创建真实 PR。

在既有 diff 上增加暂存／取消暂存、提交预览与提交，再接 PR 创建和状态。Git 操作使用结构化参数和已选工作目录。Codex 原生 `review/start` 使用明确的审查目标，将结果与执行会话区分。

验收：暂存范围准确、提交包含预览范围、失败保留输入；PR 目标与分支正确；原生审查结果可定位文件；冲突状态不会被普通提交流程掩盖。

## 第五阶段：配置与扩展管理

先做读取和诊断，展示 MCP、插件、hooks、代理配置的有效来源及错误。再增加底座支持的安装、卸载、启用和认证。写入前验证作用域和格式，保留其他配置；认证凭据不进入聊天记录和日志。

验收：配置错误可定位；用户、项目配置作用域清楚；认证取消与失败可恢复；重载后验证实际生效状态。不同底座能力分别验证，不假定插件包通用。

## 第六阶段：后台终端与定时任务

先提供命令会话列表、输出、输入、停止和退出状态，明确进程由 Moose 还是底座管理。定时任务使用持久化调度记录，定义时区、休眠后补跑、重叠执行、失败和取消语义，并复用工作目录锁。

验收：关闭窗口、重启应用、系统休眠和进程退出后的状态可解释；定时任务不重复执行；排队与并行遵循同一套目录隔离规则。

## 交付节奏

每阶段独立更新能力表、使用说明和验证记录。先运行针对性协议／服务测试，再完成类型检查、lint、完整单测与 Electron 回归。涉及真实协议时做最小 CLI 验证并记录版本、实际事件和限制；涉及打包行为时再验证安装包。

第一阶段优先形成可单独验收的版本。其余阶段在依赖完成后逐项交付，不把尚未接通的接口提前标为支持。
